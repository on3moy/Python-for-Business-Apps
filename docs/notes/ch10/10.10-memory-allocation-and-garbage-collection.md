# 10.10 Memory allocation and garbage collection

Quick detour from writing classes to what's happening underneath them — every object you create, instance or otherwise, has to live somewhere in memory, and Python is handling that for you the whole time.  

**memory allocation:**
The process of an application requesting memory from the operating system and being granted it.  

You've never written a line of code to allocate memory, and you never will in Python — the runtime does it automatically. Build a list and append 100 items to it, and Python quietly requests however much memory those 100 items need.  

```
lst = []
for i in range(0, 100):
    lst.append(i)

# Python allocated space for every one of those 100 items
# without you ever asking it to
```

!!! info " "

    Other languages make you manage this by hand — request memory, use it, free it, and if you forget that last step, the program leaks memory until it crashes. Python spares you that entirely. It's part of why Python code reads shorter than the equivalent in a lower-level language.  

## Garbage collection

**reference count:**
An integer that tracks how many variables currently reference a given object.  

**garbage collection:**
Python's automatic process of freeing memory used by objects once nothing references them anymore.  

Every time you point a variable at an object, that object's reference count goes up. Every time a variable stops pointing at it — reassigned, deleted, out of scope — the count goes down. Hit zero, and the object becomes fair game for the garbage collector.  

??? example "🦖 Example"

    ```
    string1 = 'Python'
    string2 = 'Computer science'
    string3 = string2

    # 'Computer science' now has a reference count of 2

    string1 = 'zyBooks'
    # 'Python' just dropped to a reference count of 0

    string2 = string1
    # 'Computer science' drops to 1 -- string3 still holds it
    ```

    `'Python'` becomes a candidate for deallocation the instant `string1` gets reassigned, because nothing else was pointing at it. `'Computer science'` survives that whole sequence, because `string3` never let go of it.  

!!! note "Reference count hitting 0 isn't the same moment as deallocation"

    Python's garbage collector will eventually clean up an object once its reference count reaches 0, but exactly when that happens can vary across different Python runtime implementations. Don't write code that depends on the precise timing of deallocation — it's an implementation detail, not a guarantee.  

That last point is also why a naive swap like `temp = a; a = b; b = temp` is safe even though, for a split second, you might expect something to hit zero — the reference count math works out because `temp` is holding the reference the whole time nothing else is. It's worth knowing this machinery exists, even though day to day you'll rarely think about it — that's the whole point of Python managing it for you.
