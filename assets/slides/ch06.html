You have never once had to tell Python that a parameter is an integer. That freedom has a name, and it's worth understanding exactly what Python is doing — and not doing — under the hood.

Languages like C++ and Java use static typing instead — every variable and parameter's type gets nailed down in the source code, and the compiler refuses to build the program if it spots a type-unsafe operation before it ever runs. Python skips that check entirely and waits until the code actually runs.

Same function, same plus operator, two completely different behaviors — numeric addition versus string concatenation — because plus itself is polymorphic, and dynamic typing is exactly what lets one function body handle both cases without any extra code.

Polymorphism is the formal name for what we just watched happen. Notice this isn't a special feature of the add function we wrote — it's a property of the plus operator itself, which add merely exposes.

This is the other side of the coin, and it's worth taking seriously. A static-typed language would have caught that mismatch before the program ever ran; Python is perfectly happy to let it through until the exact line where the addition actually executes.

Duck typing is dynamic typing's practical philosophy — Python doesn't ask what an object officially is, it just tries the operation and sees whether the object supports it. We won't build custom objects with that property until later in the course, but the habit of thinking this way starts now.

Every variable you've ever written carries one implicit question: from where in the program can you actually see it? That question is scope, and functions are where it stops being academic.

Up to this chapter, every variable you wrote lived in one flat scope — the whole script. The moment you introduce a function, you get more than one scope in the same program, and knowing which one a name belongs to suddenly matters.

A local variable is temporary by design. It comes into existence the moment its line runs inside the function, and it's cleaned up completely the instant the function hands control back to the caller.

centimeters_per_inch is readable inside the function with no extra syntax at all — reading a global is free. total_inches, on the other hand, doesn't exist at all once you're back outside the function that created it.

Reading a global is automatic; assigning to one from inside a function is not — without that global keyword, Python just creates a brand-new local variable with the same name and throws it away the instant the function returns, leaving the real global untouched.

This is a style habit worth internalizing early. A function whose only visible job is computing a return value, but which quietly also rewrites some global variable behind the scenes, is exactly the kind of surprise that makes a codebase hard to trust.

Most programs put every def block near the top of the file and all the calling code below, which naturally satisfies this rule without you having to think about it — but it is worth knowing the rule exists, for the day you organize a file differently.

Passing a variable into a function does not create a copy of it — Python passes a reference to the same object. Whether that distinction matters depends entirely on whether the object is mutable.

This is the single mental model that explains every surprise in this section. A function call is, underneath, just another assignment statement — the parameter name gets bound to whatever object the caller's argument already points at. What happens next depends entirely on that object.

age = age + 1 doesn't modify the integer 7 in place — integers can't be modified — it creates a brand-new integer object and rebinds the local name age to it. timmy_age, outside the function, never knew any of that happened.

Lists, dictionaries, and other mutable objects behave completely differently. Modifying one in place inside a function is visible everywhere else that object is referenced — there's only ever one object here, cart and my_cart are two names for the exact same list, and no copy was ever made.

Think of a function that "cleans" a list of transaction records by removing duplicates in place. A function with seven parameters is asking for trouble the moment somebody calls it and swaps two arguments by accident. This section is two separate tools Python gives you to make that call safer to write and easier to read.

Order stops mattering entirely once you're using keyword arguments — Python matches each one to its parameter by name, not by position. Notice year showed up first in that call and it still landed in the right slot.

This is a straightforward rule but an easy one to trip over while refactoring a call you're editing live — once you introduce a keyword-style argument, everything after it can be keyword-style too, but nothing positional can sneak back in afterward.

Style has a fallback built right into the definition. A caller who doesn't care about it can just leave it out entirely, and the function quietly falls back to whatever default was written there.

The first call leans entirely on the fallback; the second overrides it explicitly. And that trailing-parameters rule matters: you can't skip a parameter in the middle of the list and expect Python to guess which one you meant to leave out.

This is one of the most notorious gotchas in the entire language, and it catches experienced developers too, not just beginners. The empty list gets built exactly once, at definition time, and every subsequent call that relies on the default keeps appending to that same shared object.

None is immutable and safe to reuse as a default forever, so the trick is to default to None and build the real mutable object fresh inside the function body, on every single call, rather than baking it into the definition line itself.

Combine keyword arguments with default values and you get a function that reads almost like a configuration option — the caller states only what they care about changing and lets everything else quietly fall back to a sensible default.

Sometimes you genuinely don't know ahead of time how many arguments a caller is going to hand you. Python has syntax for exactly that "however many, whatever they are" situation.

bread and meat still get filled the normal way, positionally. Everything else the caller passes just piles up inside args as a tuple, regardless of whether there are zero extra arguments or ten.

Same function definition, two calls with wildly different numbers of extra arguments — args just grows or shrinks to absorb whatever's left over each time.

Where args collects leftover positional arguments into a tuple, kwargs does the same job for leftover keyword arguments — except it lands in a dictionary instead, so you also get a name attached to every extra value.

This is a syntax rule, not a style preference — Python enforces it, and violating it is a straight-up syntax error before your program even runs. args and kwargs aren't reserved words themselves, by the way — the star and double-star are what actually matter to Python; you could call it *condiments instead, if that name fit your function better.

Section 6.1 was firm about this: a return statement hands back exactly one value. So what do you do when a function genuinely has two or three things to report — a mean and a standard deviation, say?

return mean, std_dev builds and returns a tuple with no parentheses needed — the comma alone is what tells Python to create one. This is the one sanctioned way around the one-value rule: pack multiple things into a single container, then return the container.

This is the exact same unpacking mechanism we saw with enumerate back in chapter 5 — a tuple comes back from the function call, and one line splits it apart into two clearly named variables, average and standard_deviation.

The function is still only ever returning one object — that object just happens to hold multiple things. Whether it's two values or five, the mechanism is identical.

A function with a self-explanatory name still doesn't tell a reader everything — what does it assume about its arguments, what does it hand back, are there any gotchas? That's exactly what a docstring is for.

Good practice for a simple function is to keep the docstring on one line, no blank lines surrounding it. It sits in exactly the same place a comment might, but as we're about to see, it isn't the same thing at all.

Longer, more involved functions can use a multi-line docstring instead — describing each parameter and any special rules about how to call it, the way this one flags that only one of coach or first_class should be True.

help isn't limited to functions you write yourself — it works on just about anything, because the language creators wrote docstrings for most of what ships with Python. Try help(math) after class and see everything that comes back.

Comments explain how; docstrings explain what, and they get surfaced automatically by tooling that a comment simply can't reach. That's the real distinction worth remembering, not just the triple-quote syntax.
