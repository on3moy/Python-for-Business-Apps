# 11.3 Overriding class methods  

**override:**  
A derived class defines a method with the same name as one in the base class, and its version wins.  

Because the search starts at the instance's class and works up, the method that runs is always the one closest to the instance.  

```
class Invoice:
    def __init__(self, amount):
        self.amount = amount

    def display(self):
        print(f'Invoice: {self.amount}')

class RushInvoice(Invoice):
    # Lets replace display with our own version
    def display(self):
        print(f'RUSH Invoice: {self.amount * 1.25}')

Invoice(100).display()
RushInvoice(100).display()
```

Output:
```
Invoice: 100
RUSH Invoice: 125.0
```

## Extend instead of replace

Most of the time you don't want to throw the base method away, you just want to add to it. Call the base version first, then do your extra stuff.  

```
class RushInvoice(Invoice):
    def display(self):
        # Lets run the base class version first
        Invoice.display(self)
        print('  (Rush fee applied)')
```

Passing `self` is what lets the base method read the attributes off your object.  

!!! abstract "super()"  

    **super()** is a shortcut for "my base class". `super().display()` does the same thing as `Invoice.display(self)` but you don't type the class name or pass `self`.  
    - `super().__init__(amount)` is the usual way to set up the inherited attributes ✅  
    - Rename the base class later and you don't have to hunt down every call 🤯  

??? example "🦖 Example"  

    ```
    class RushInvoice(Invoice):
        def __init__(self, amount, fee):
            # Lets let the base class handle amount
            super().__init__(amount)
            self.fee = fee

        def display(self):
            super().display()
            print(f'  Rush fee: {self.fee}')

    RushInvoice(100, 25).display()
    ```

    Output:
    ```
    Invoice: 100
      Rush fee: 25
    ```  

## Same call, different behavior

Since each class has its own `display()`, you can loop over a mix of them and not care which is which.  

```
# Lets mix both types in one list
invoices = [Invoice(100), RushInvoice(200, 50)]

for inv in invoices:
    inv.display()
```

Each object runs *its own* version. This is called **polymorphism**, one method name and many behaviors. In reports or ETL code it means you write one loop and let the objects decide how to print themselves.
