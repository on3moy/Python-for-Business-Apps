# 6.1 User-defined function basics

<!--
We start with the vocabulary. A function has moving parts with precise
names, and getting comfortable with that vocabulary now will save us a lot
of confusion later, once real programs have several functions calling each
other.
-->

---

## Stop retyping the same calculation

Copy the same formula into three places in a script, and you will eventually copy it wrong once.

**function:**
A named series of statements you can invoke by name instead of retyping. `def` is the keyword that creates one.

<!--
This is the core motivation, and it is almost embarrassingly simple: naming
a block of code means you never have to retype it, and you only ever have
one place to fix it if it's wrong. Let's see it applied to a genuinely
tedious conversion — Fahrenheit to Celsius, computed in three different
spots in a program.
-->

---

## Wrapping a repeated calculation

```python
# Lets convert Fahrenheit to Celsius, written once
def f2c(f):
    c = (f - 32.0) * (5.0 / 9.0)
    return c

c1 = f2c(f1)
c2 = f2c(f2)
```

The main program no longer cares *how* the conversion happens — only that calling `f2c()` gets it an answer.

<!--
Notice what disappeared from the calling code — no arithmetic, no formula,
just a name and a value going in. That's the whole payoff: the details of
*how* live in exactly one place, and everywhere else just asks for the
result.
-->

---

## Writing the behavior: the function definition

**function definition:**
The `def` line plus the indented block underneath it — this is where you *write* the behavior.

`def f2c(f):` followed by an indented body, same indentation rules as an `if` block or a loop body.

<!--
This is the half of a function you write once. Notice the syntax borrows
exactly the same colon-and-indent pattern we've already used for if blocks
and loops — nothing new to learn there, just a new place to apply it.
-->

---

## Using the behavior: the function call

**function call:**
The function's name followed by `()` — this is where you *use* the behavior. It jumps execution into the function and back.

`f2c(98.6)` is a call; `def f2c(f):` is not.

<!--
Calling and defining are opposite halves of the same coin, and it is easy
to blur them together the first week. The definition is written once,
sitting quietly in your file. The call is what actually makes anything
happen, and you can write that call as many times as you need.
-->

---

## The named input: a parameter

**parameter:**
A named input listed in the function definition — like `diameter` in `def calc_pizza_area(diameter):`.

A parameter behaves like a fresh variable inside the function, and it disappears the moment the function returns.

<!--
Think of a parameter as a placeholder the function definition sets up in
advance, before it has any idea what value will actually show up. That
value only arrives at the moment somebody calls the function.
-->

---

## The value handed over: an argument

**argument:**
The actual value handed to a parameter at call time — like the `12.0` in `calc_pizza_area(12.0)`.

Multiple parameters are matched to arguments by position, left to right, separated by commas.

<!--
Parameter and argument get used almost interchangeably in casual
conversation, but on an exam or in a code review, precision matters —
the parameter is the name in the definition, the argument is the value at
the call site. Let's watch both roles at work in one small function.
-->

---

## Squaring a number

```python
# Lets square whatever gets passed in
def compute_square(num_to_square):
    return num_to_square * num_to_square

num_squared = compute_square(7)
print(f'7 squared is {num_squared}')
```

Output: `7 squared is 49`

<!--
num_to_square is the parameter — it exists only inside this function's
definition. The 7 we hand it at the call site is the argument. And a
function with zero parameters still needs the parentheses in both the
definition and the call, `def calc_something():` and `calc_something()`.
-->

---

## Sending a value back out

**return statement:**
Sends a single value back out of the function to wherever it was called from.

- ✅ `return c` — hands back one object
- ✅ `return (mean, std_dev)` — still one object, a tuple wearing a trench coat
- ❌ thinking `return a, b, c, d` returns four separate things — it's one tuple, one `return`

<!--
Every return statement hands back exactly one object, full stop — the
trench-coat line is worth remembering, because a tuple can smuggle several
values out under that single-object rule. We'll come back to that trick
properly in section 6.15.
-->

---

## No return statement? You still get something

A function with no `return` at all — or a bare `return` with nothing after it — quietly hands back `None`.

Nothing crashes on the spot. The crash, if there is one, shows up later, wherever that `None` gets used in math.

<!--
This is a genuinely sneaky failure mode, and it's worth sitting with for a
moment. The function itself runs fine, top to bottom, no error at all — the
mistake only becomes visible several lines downstream, the first time
something tries to add or multiply that None. We'll see exactly this bug
again in section 6.9.
-->

---

## Functions calling functions

`int(input())` is the smallest example you've already been typing all semester.

`input()` runs first, and whatever it evaluates to gets handed straight to `int()` as an argument.

<!--
Nothing about a function's own body is special — its statements can call
any other function, including one you wrote yourself. Every program of any
real size ends up being a web of small functions calling each other, and
int of input of something is the tiniest possible example of that web.
-->

---

# 6.2 Print functions

<!--
Not every function's job is to hand a value back. Some functions exist
purely to do something — almost always print something — and that's a
perfectly legitimate reason to write one.
-->

---

## Not every function returns something useful

**void function:**
A function with no `return` statement, or only a bare `return`. It still technically returns `None`, but nobody uses that value.

<!--
Void isn't a judgment on the function's usefulness — it just describes
what happens at the return boundary. Printing three lines of formatted
output, over and over, from three different places in a program, is
exactly the kind of job a void function was built for.
-->

---

## A reusable order summary

```python
# Lets print a formatted order summary
def print_summary(oid, items, price):
    print(f'Order {oid}:')
    print(f' Items: {items}')
    print(f' Total: ${price:.2f}')

print_summary(42, 4, 13.99)
```

Output: `Order 42:` then two indented lines below it.

<!--
The function does its job — three formatted print statements — and control
returns right back to the line after the call. Nothing gets handed back
because nothing needs to be.
-->

---

## Why bother with a print function

Write the formatted output once, call it as many times as you need.

If the formatting ever needs to change — adding a `!`, tweaking a label — you fix it in exactly one place instead of hunting down every copy.

<!--
The real payoff shows up on the second and third call, not the first. This
is the same don't-repeat-yourself motivation from 6.1, just applied to
printing instead of returning a computed value.
-->

---

## A menu loop calling a print function

```python
# Lets keep showing a menu until the user quits
def print_menu():
    print("Today's Menu:")
    print(' 1) Gumbo')
    print(' 2) Jambalaya')

while not quit_program:
    print_menu()
```

<!--
print_menu() gets called once per trip through this while loop, and the
main loop itself stays readable because the menu text isn't cluttering up
every iteration of it. This is exactly the kind of function you'd reach for
purely for readability, even with zero repetition — a preview of section
6.4.
-->

---

# 6.3 Dynamic typing

<!--
You have never once had to tell Python that a parameter is an integer.
That freedom has a name, and it's worth understanding exactly what Python
is doing — and not doing — under the hood.
-->

---

## No type declarations, ever

**dynamic typing:**
Determining the type of objects as a program executes, in contrast to static typing, which requires the programmer to declare the type of every variable and parameter in the source code.

<!--
Languages like C++ and Java use static typing instead — every variable and
parameter's type gets nailed down in the source code, and the compiler
refuses to build the program if it spots a type-unsafe operation before it
ever runs. Python skips that check entirely and waits until the code
actually runs.
-->

---

## The same function, two behaviors

```python
# Lets call the same function on numbers, then strings
def add(x, y):
    return x + y

print(add(5, 7))
print(add('Tora', 'Bora'))
```

Output: `12` then `ToraBora`

<!--
Same function, same plus operator, two completely different behaviors —
numeric addition versus string concatenation — because plus itself is
polymorphic, and dynamic typing is exactly what lets one function body
handle both cases without any extra code.
-->

---

## Polymorphism

**polymorphism:**
An operation behaves differently depending on the type of the object it's operating on.

The `+` in the last slide's `add()` function is the clearest possible example — numeric addition on one call, string concatenation on the next.

<!--
Polymorphism is the formal name for what we just watched happen. Notice
this isn't a special feature of the add function we wrote — it's a
property of the plus operator itself, which add merely exposes.
-->

---

## The tradeoff

Dynamic typing buys flexibility — but type errors don't surface until runtime, sometimes only on the one input nobody tested.

`add(5, '100')` runs fine syntactically. It blows up the moment the interpreter actually tries to add an int and a str.

<!--
This is the other side of the coin, and it's worth taking seriously. A
static-typed language would have caught that mismatch before the program
ever ran; Python is perfectly happy to let it through until the exact line
where the addition actually executes.
-->

---

## Duck typing

Python leans on **duck typing** — if an object can be sliced, indexed, and lowercased like a string does, Python treats it like a string, no matter what it's officially called.

"If it walks, swims, and quacks like a duck…"

<!--
Duck typing is dynamic typing's practical philosophy — Python doesn't ask
what an object officially is, it just tries the operation and sees whether
the object supports it. We won't build custom objects with that property
until later in the course, but the habit of thinking this way starts now.
-->

---

# 6.4 Reasons for defining functions

<!--
If 6.1 sold you on don't-repeat-yourself, this section makes the fuller
case for reaching for def even when nothing is actually repeated.
-->

---

## Readability

```python
# Lets see the point of the calls, not the formulas
def steps_to_feet(num_steps):
    return num_steps * 3

steps = int(input('Enter steps walked: '))
print(f'Feet: {steps_to_feet(steps)}')
```

Both a functioned and a flattened version produce identical output — only one tells you, at a glance, what the program is *doing*.

<!--
Flatten this same logic directly into the main program with no functions
at all, and it still runs correctly — but now a reader has to trace every
constant back to figure out its purpose. The function version, by
contrast, reads almost like English: get steps, print feet.
-->

---

## Rule of thumb: keep it under 30 lines

Not a hard rule — a sign that if you're blowing way past it, the function is probably doing more than one job.

<!--
This number isn't sacred, and zyBooks doesn't pretend it is. Treat it as an
early-warning signal: if a function keeps growing well past thirty lines,
that's usually a sign it's quietly become two or three functions wearing
one name.
-->

---

## Modular development

**modular development:**
Dividing a program into separate pieces that can be written, tested, and debugged on their own before being wired together into the final program.

<!--
This is where function stubs, coming up in section 6.6, earn their keep —
you can sketch out the shape of a whole program's functions before any of
them actually work yet, the same way you'd plan a road trip's route before
turning the key.
-->

---

## Avoiding redundant code

`math.sqrt()` is the running example of why this matters at all — a square root calculation you never had to write yourself.

Every function you define is you handing your future self, or a teammate, the same gift.

<!--
Ask the room: would you rather debug your own hand-rolled square root
routine, or trust one that the entire Python community has already tested
for decades? Every function you write and hand off is you doing that same
favor for whoever reads your code next — including future you.
-->

---

# 6.5 Writing mathematical functions

<!--
A function that takes numbers in and hands a number back is the easiest
kind to reason about — it behaves exactly like a math class function
you'd graph, f of x.
-->

---

## A function call resolves to a value first

**A function call evaluates to whatever it returns**, so you can drop it directly into a larger expression the same way you'd drop in a variable.

```python
def compute_square(num_to_square):
    return num_to_square * num_to_square

c2 = compute_square(7) + compute_square(9)
```

Output: `130`

<!--
This is worth sitting with — Python resolves compute_square(7) down to the
plain number 49 before it ever gets to the plus sign. Nesting works the
same way: the innermost call always resolves first, and the result just
becomes another value in the surrounding expression.
-->

---

## What's legal, what isn't

- ✅ `y = 1.0 + square_root(144.0)` — the call resolves to a number first
- ✅ `y = square_root(square_root(16.0))` — nesting works fine
- ❌ `square_root(49.0) = z` — you assign *from* a call, never *to* one
- ❌ `y = print_val(9.0)` — a void function's call is just `None`

<!--
That last line is the sneaky one — print_val looks like it produces
something because it prints something, but assigning its call to y just
captures None, because print_val never actually returns a value.
-->

---

## Bigger math functions lean on smaller ones

```python
import math

def calc_circular_base_area(radius):
    return math.pi * radius * radius

def calc_cylinder_volume(radius, height):
    return calc_circular_base_area(radius) * height
```

<!--
A cylinder's volume needs the area of its circular base, so we write that
once and call it from wherever it's needed — here, just once, but the same
base-area function could just as easily feed a surface-area calculation
too. This is the objects idea from chapter 2 applied at a bigger scale:
calc_circular_base_area doesn't care who's calling it.
-->

---

# 6.6 Function stubs

<!--
You already met the incremental habit back in chapter 5 — build a little,
test it, build a little more. Function stubs are that same discipline
applied specifically to functions you know you'll need but haven't written
yet.
-->

---

## Sketching a function before it works

**function stub:**
A function definition whose body isn't finished — a placeholder that lets you sketch a program's shape before filling in every detail.

```python
def steps_to_calories(num_steps):
    pass
```

<!--
pass does nothing except satisfy Python's rule that a function body can't
be left empty. The rest of a program built around this stub still runs top
to bottom without crashing, even though steps_to_calories isn't actually
implemented yet — calling it just quietly hands back None.
-->

---

## Three ways to stub a function

|Approach|What it does|When to use it|
|-|-|-|
|`pass`|Silently returns `None`|Earliest sketch of a program|
|`print()` + `return -1`|Flags itself loudly|Once other code depends on the return value|
|`raise NotImplementedError`|Halts the program|Rest of the program can't proceed without it|

<!--
Notice these three escalate in how loudly they complain. Start with pass
while you're just laying out a program's shape, move to a printed warning
once other functions start depending on a real return value, and reach for
raise NotImplementedError only when there's genuinely no sensible way to
keep going without this piece finished.
-->

---

## A stub that flags itself

```python
# Lets have an unfinished function announce itself
def steps_to_calories(steps):
    print('FIXME: finish steps_to_calories')
    return -1
```

`pass` and `raise` are both reserved words — same family as `def` and `return`.

<!--
This is the second row of the table made concrete — the function still
returns something, -1, but it also prints a loud, unmissable reminder
every time it's called. A half-finished real function tends to fail in
confusing ways; a stub fails loudly and predictably instead.
-->

---

# 6.7 Functions with branches/loops

<!--
A short section, mostly here to prove a point: nothing about being inside a
function changes the rules you already know about if-else and for loops.
-->

---

## An eBay-style fee calculator

```python
# Lets calculate fees across three price tiers
def calc_ebay_fee(sell_price):
    fee = 0.50
    if sell_price <= 50:
        fee += sell_price * 0.13
    elif sell_price <= 1000:
        fee += (50 * 0.13) + ((sell_price - 50) * 0.05)
    return fee
```

Output: `eBay fee: $9.50` for a `$100` sale.

<!--
This is the exact same tiered-pricing pattern you'd write with a plain
if-elif-else chain outside any function — it just happens to live inside a
def block this time, and it hands back a single fee at the end instead of
printing it directly. Exactly one branch ever runs per call — that's the
whole point of elif.
-->

---

## Why this combination matters for business logic

Fee schedules, tax brackets, shipping tiers, commission structures — almost every "it depends on which range" calculation ends up looking exactly like `calc_ebay_fee()`.

<!--
A branch to pick the right formula, wrapped in a function so the rest of
the program can just ask for the answer — that pattern is going to show up
constantly in business code, well beyond this one eBay example.
-->

---

# 6.8 Functions are objects

<!--
Everything in Python has a type, an identity, and a value — we established
that back in chapter 2. Functions are no exception, and that is a
genuinely strange thing to sit with the first time you hear it.
-->

---

## A def statement creates an object

**function object:**
`def print_face():` doesn't just describe behavior — it creates an actual object, with `print_face` as a name bound to it, the same way `x = 5` binds `x` to an integer.

<!--
Because a function is just an object, you can do ordinary object things to
it — assign it to another name, pass it as an argument, store it in a
list. Let's watch the first of those.
-->

---

## Two names, one function

```python
# Lets bind a second name to the same function
def print_cat():
    print('meow')

func = print_cat
func()
```

Output: `meow`

<!--
func = print_cat has no parentheses, so nothing runs — it just creates a
second name pointing at the exact same function object. func() and
print_cat() are now two different ways to trigger the identical call.
-->

---

## Passing a function as an argument

```python
def print_monkey_head():
    print('( o o )')

def print_figure(face):
    face()
    print('| --|-- |')

print_figure(print_monkey_head)
```

<!--
print_figure never has to know or care which face function it received —
it just calls whatever was handed to it. That's the same flexibility
dynamic typing gives you everywhere else in Python, applied here to
functions specifically.
-->

---

## Don't confuse the object with the call

- ✅ `func = print_cat` — assigns the function object itself
- ❌ `func = print_cat()` — calls it immediately and assigns whatever it *returns*

That missing pair of parentheses is the entire difference between "here's a function to use later" and "run this right now."

<!--
This is the single most common typo in this whole section — one stray
pair of parentheses turns "pass this function around" into "run it right
now and throw away the result." Read your own code carefully whenever
you're handing a function off without calling it.
-->

---

# 6.9 Functions: Common errors

<!--
We all write buggy functions sometimes, and that's okay. This section is
two of the specific ways that's most likely to happen to you this
semester.
-->

---

## Copy-paste errors

Writing a Fahrenheit-to-Celsius function, then copying it to build Celsius-to-Fahrenheit, is a reasonable time-saver — right up until you forget to change every single thing that needed changing.

<!--
Copy-pasting a working function as the starting point for a similar one
is completely normal, professional practice. The danger is entirely in what
gets left behind unchanged, and the return line is where that leftover
almost always hides.
-->

---

## A copy-paste bug in the wild

```python
def fahrenheit_to_celsius(fahrenheit):
    temperature = fahrenheit - 32
    celsius = temperature * (5.0 / 9.0)
    return fahrenheit   # should be return celsius
```

Everything about this *looks* right on a skim — the math is even correct.

<!--
Treat every copy-pasted function as a small crime scene, the same way a
wet road makes you drive more carefully. Check the parameter names, the
variable names, and especially the return line — that is exactly where
leftover old names love to hide.
-->

---

## Returning the wrong variable

The function runs with zero errors, and sometimes even happens to give the right answer by accident — which makes it *harder* to catch, not easier.

<!--
This is the quiet cousin of the copy-paste bug — even without any
copy-pasting involved, grabbing the wrong local variable at the return
line produces a function that runs cleanly and returns a plausible-looking
wrong number. Nothing about running it once will necessarily expose it.
-->

---

## Forgetting to return anything at all

```python
def sqr(a):
    t = a * a
    # forgot: return t
```

Calling `sqr(5)` runs perfectly fine and gives you `None`. No traceback, no red flag — just a silent wrong answer.

<!--
Print the return value the first time you test any new function, even ones
that "obviously" work. print(sqr(5)) showing None instead of 25 is an
immediate, unmistakable tell — much faster than tracing a bug backward from
wherever that None eventually crashes something several lines later.
-->

---

# 6.10 Scope of variables and functions

<!--
Every variable you've ever written carries one implicit question: from
where in the program can you actually see it? That question is scope, and
functions are where it stops being academic.
-->

---

## Scope

**scope:**
The region of a program where a name is visible and usable.

<!--
Up to this chapter, every variable you wrote lived in one flat scope — the
whole script. The moment you introduce a function, you get more than one
scope in the same program, and knowing which one a name belongs to
suddenly matters.
-->

---

## Local variables

**local variable:**
Created inside a function. Its scope is limited to that function — the moment the function returns, the variable is gone.

<!--
A local variable is temporary by design. It comes into existence the
moment its line runs inside the function, and it's cleaned up completely
the instant the function hands control back to the caller.
-->

---

## Global variables

**global variable:**
Created outside of any function. Visible from the point it's assigned all the way to the end of the file, including inside functions.

```python
centimeters_per_inch = 2.54   # global

def height_us_to_cm(feet, inches):
    total_inches = (feet * 12) + inches   # local
    return total_inches * centimeters_per_inch
```

<!--
centimeters_per_inch is readable inside the function with no extra syntax
at all — reading a global is free. total_inches, on the other hand,
doesn't exist at all once you're back outside the function that created
it.
-->

---

## Assigning to a global needs a heads-up

```python
employee_name = 'N/A'

def get_name():
    global employee_name
    employee_name = input('Enter employee name: ')
```

Delete the `global` line and this silently prints `N/A` no matter what you type.

<!--
Reading a global is automatic; assigning to one from inside a function is
not — without that global keyword, Python just creates a brand-new local
variable with the same name and throws it away the instant the function
returns, leaving the real global untouched.
-->

---

## Use global sparingly

Reserve global variables for constants that don't depend on any function — things like `centimeters_per_inch`.

A function that reaches out and rewrites global state has a side effect that's easy for a reader to miss entirely.

<!--
This is a style habit worth internalizing early. A function whose only
visible job is computing a return value, but which quietly also rewrites
some global variable behind the scenes, is exactly the kind of surprise
that makes a codebase hard to trust.
-->

---

## Functions have scope too

A function must be *defined* — its `def` block evaluated — before it can be called.

Calling it above its own `def` raises `NameError: name '...' is not defined`.

<!--
Most programs put every def block near the top of the file and all the
calling code below, which naturally satisfies this rule without you having
to think about it — but it is worth knowing the rule exists, for the day
you organize a file differently.
-->

---

# 6.11 Namespaces and scope resolution

<!--
Section 6.10 told you where a variable is visible. This section is the
mechanism underneath that — how Python actually keeps track of it all.
-->

---

## Namespace

**namespace:**
A mapping of names to objects — literally a dictionary under the hood, where the keys are the names you typed and the values are the objects they're bound to.

```python
print(globals())
my_var = 'This is a variable'
print(globals())
```

<!--
globals() shows you the global namespace directly, and locals() does the
same for whichever local namespace is currently active. Watching my_var
appear the instant it's assigned is the whole trick — a namespace only
knows about a name after that name's first assignment.
-->

---

## Where Python looks for a name

When the interpreter hits a name in your code, it checks namespaces in a fixed order.

**scope resolution:**
The process of checking local, then global, then built-in namespaces to find where a name is defined.

If the name isn't found anywhere in that chain, you get `NameError`.

<!--
This search order is fixed and predictable, and it is worth memorizing
because it explains a surprising number of "why did that variable come
from over there" moments. If a name shows up nowhere in that chain, that's
exactly when NameError fires. Let's look at the three stops in that
search, in order.
-->

---

## The search order

|Order|Namespace|Contains|
|-|-|-|
|1|Local|Inside the currently running function|
|2|Global|Everything outside any function|
|3|Built-in|`int()`, `str()`, `list()`, `range()`, …|

<!--
Python checks these three, in this exact order, every single time it
resolves a name. Local first, because that's the narrowest and most likely
match if you're inside a function; built-in last, because you'd rather
your own code win over Python's defaults whenever there's a conflict.
-->

---

## Watching a local namespace come and go

```python
daily_cals = 2300

def roll():
    number = 1
    return number

roll()
```

`daily_cals` lives in the global namespace. `roll()`'s local namespace, holding `number`, is deleted the moment it returns.

<!--
Every call to roll builds a fresh local namespace from scratch, and that
namespace is torn down completely the instant the function hands back its
result — daily_cals, sitting quietly in the global namespace the whole
time, is never touched.
-->

---

## Shadowing a built-in

Defining a function called `list()` doesn't crash anything — your `list` simply shadows the built-in for the rest of the file.

**It's legal, and it's also a great way to confuse yourself later.**

<!--
Because local beats global beats built-in in that search order, a name you
define anywhere in your own code will always win over Python's own
built-ins if they happen to collide. Legal, occasionally useful, and worth
naming things carefully to avoid by accident.
-->

# 6.12 Function arguments

<!--
Passing a variable into a function does not create a copy of it — Python
passes a reference to the same object. Whether that distinction matters
depends entirely on whether the object is mutable.
-->

---

## Pass-by-assignment

**pass-by-assignment:**
Python's argument-passing model — calling a function binds the parameter name to the same object the argument refers to, exactly like an ordinary assignment statement would.

<!--
This is the single mental model that explains every surprise in this
section. A function call is, underneath, just another assignment statement
— the parameter name gets bound to whatever object the caller's argument
already points at. What happens next depends entirely on that object.
-->

---

## Immutable arguments are safe

```python
def birthday(age):
    age = age + 1

timmy_age = 7
birthday(timmy_age)
print(f'Timmy is {timmy_age}')
```

Output: `Timmy is 7`

<!--
age = age + 1 doesn't modify the integer 7 in place — integers can't be
modified — it creates a brand-new integer object and rebinds the local
name age to it. timmy_age, outside the function, never knew any of that
happened.
-->

---

## Mutable arguments are not safe

```python
def add_item(cart):
    cart.append('tacos')

my_cart = ['chips']
add_item(my_cart)
print(my_cart)
```

Output: `['chips', 'tacos']`

<!--
Lists, dictionaries, and other mutable objects behave completely
differently. Modifying one in place inside a function is visible
everywhere else that object is referenced — there's only ever one object
here, cart and my_cart are two names for the exact same list, and no copy
was ever made.
-->

---

## Protecting a mutable argument

If you need to hand a list to a function but don't want it touched, pass a copy: `my_func(num_list[:])`.

The slice creates a new list object, so whatever the function does to it stays contained.

<!--
Think of a function that "cleans" a list of transaction records by
removing duplicates in place. If you didn't realize it was mutating your
original list, you might reuse that same variable elsewhere in your script
expecting the untouched data — and quietly work with the wrong dataset for
the rest of the program. Passing a slice copy is the fix.
-->

---

# 6.13 Keyword arguments and default parameter values

<!--
A function with seven parameters is asking for trouble the moment
somebody calls it and swaps two arguments by accident. This section is two
separate tools Python gives you to make that call safer to write and
easier to read.
-->

---

## Matching arguments by name instead of position

**keyword argument:**
An argument passed as `name=value` at the call site, matching a parameter by its name instead of by its position in the list.

```python
def print_book(title, author, year):
    print(f'{title} by {author} ({year})')

print_book(year=1954, title='LOTR', author='Tolkien')
```

<!--
Order stops mattering entirely once you're using keyword arguments —
Python matches each one to its parameter by name, not by position. Notice
year showed up first in that call and it still landed in the right slot.
-->

---

## Keyword arguments must come last

You can mix positional and keyword arguments in one call, but every positional argument has to come *before* any keyword argument.

- ✅ `split_check(125.00, tip_percentage=0.15, num_people=2)`
- ❌ `split_check(tip_percentage=0.15, 125.00, num_people=2)`

<!--
This is a straightforward rule but an easy one to trip over while
refactoring a call you're editing live — once you introduce a
keyword-style argument, everything after it can be keyword-style too, but
nothing positional can sneak back in afterward.
-->

---

## A value the caller can skip

**default parameter value:**
A value assigned in the function definition itself, used automatically whenever the caller omits that argument.

```python
def print_date(day, month, year, style=0):
    if style == 0:
        print(f'{month}/{day}/{year}')
    else:
        print(f'{day}/{month}/{year}')
```

<!--
Style has a fallback built right into the definition. A caller who doesn't
care about it can just leave it out entirely, and the function quietly
falls back to whatever default was written there.
-->

---

## Calling with and without the default

```python
print_date(30, 7, 2012)          # style defaults to 0
print_date(30, 7, 2012, 1)       # style explicitly overridden
```

If a parameter has no default, omitting its argument is always an error — only trailing parameters can be skipped this way.

<!--
The first call leans entirely on the fallback; the second overrides it
explicitly. And that trailing-parameters rule matters: you can't skip a
parameter in the middle of the list and expect Python to guess which one
you meant to leave out.
-->

---

## Never use a mutable object as a default

```python
def append_to_list(value, my_list=[]):
    my_list.append(value)
    return my_list
```

That `[]` is created **once**, when the function is defined — not once per call. Every call that skips `my_list` shares the *same* list.

<!--
This is one of the most notorious gotchas in the entire language, and it
catches experienced developers too, not just beginners. The empty list
gets built exactly once, at definition time, and every subsequent call
that relies on the default keeps appending to that same shared object.
-->

---

## The fix: a `None` sentinel

```python
def append_to_list(value, my_list=None):
    if my_list is None:
        my_list = []
    my_list.append(value)
    return my_list
```

Now a fresh list gets built inside the function body, once per call.

<!--
None is immutable and safe to reuse as a default forever, so the trick is
to default to None and build the real mutable object fresh inside the
function body, on every single call, rather than baking it into the
definition line itself.
-->

---

## Where this really pays off

If every parameter has a default, a caller can supply just the ones they care about, in any order.

`print_date(style=1)` works fine entirely on its own.

<!--
Combine keyword arguments with default values and you get a function that
reads almost like a configuration option — the caller states only what
they care about changing and lets everything else quietly fall back to a
sensible default.
-->

---

# 6.14 Arbitrary argument lists

<!--
Sometimes you genuinely don't know ahead of time how many arguments a
caller is going to hand you. Python has syntax for exactly that "however
many, whatever they are" situation.
-->

---

## Collecting extra positional arguments

**\*args:**
A parameter prefixed with `*` that collects any extra positional arguments into a tuple.

```python
def print_sandwich(bread, meat, *args):
    print(f'{meat} on {bread}', end=' ')
    if len(args) > 0:
        print('with', *args)
```

<!--
bread and meat still get filled the normal way, positionally. Everything
else the caller passes just piles up inside args as a tuple, regardless of
whether there are zero extra arguments or ten.
-->

---

## Calling it with different counts

```python
print_sandwich('sourdough', 'turkey', 'mayo')
print_sandwich('wheat', 'ham', 'mustard', 'tomato', 'lettuce')
```

Output: `turkey on sourdough with mayo` then `ham on wheat with mustard tomato lettuce`

<!--
Same function definition, two calls with wildly different numbers of
extra arguments — args just grows or shrinks to absorb whatever's left
over each time.
-->

---

## Collecting extra keyword arguments

**\*\*kwargs:**
A final parameter prefixed with `**` that collects any extra *keyword* arguments into a dictionary, with the argument names as keys.

```python
def print_sandwich(meat, bread, **kwargs):
    print(f'{meat} on {bread}')
    for category, extra in kwargs.items():
        print(f' {category}: {extra}')
```

<!--
Where args collects leftover positional arguments into a tuple, kwargs
does the same job for leftover keyword arguments — except it lands in a
dictionary instead, so you also get a name attached to every extra value.
-->

---

## Order matters

`*args` and `**kwargs`, in that order if you use both, must come **last** in the parameter list.

- ✅ `def f(arg1, arg2, *args, **kwargs):`
- ❌ `def f(*args, arg1, arg2):`

<!--
This is a syntax rule, not a style preference — Python enforces it, and
violating it is a straight-up syntax error before your program even runs.
args and kwargs aren't reserved words themselves, by the way — the star and
double-star are what actually matter to Python; you could call it
*condiments instead, if that name fit your function better.
-->

---

# 6.15 Multiple function outputs

<!--
Section 6.1 was firm about this: a return statement hands back exactly one
value. So what do you do when a function genuinely has two or three things
to report — a mean and a standard deviation, say?
-->

---

## Packing several values into one tuple

```python
# Lets return both a mean and a standard deviation
def get_grade_stats(scores):
    mean = sum(scores) / len(scores)
    tmp = sum((s - mean) ** 2 for s in scores)
    std_dev = (tmp / len(scores)) ** 0.5
    return mean, std_dev
```

<!--
return mean, std_dev builds and returns a tuple with no parentheses
needed — the comma alone is what tells Python to create one. This is the
one sanctioned way around the one-value rule: pack multiple things into a
single container, then return the container.
-->

---

## Unpacking it back into two names

```python
average, standard_deviation = get_grade_stats(
    [75, 84, 66, 99, 51, 65])
print(f'Average: {average}')
```

**unpacking:**
Assigning multiple variables at once from a single sequence, matching each in order.

<!--
This is the exact same unpacking mechanism we saw with enumerate back in
chapter 5 — a tuple comes back from the function call, and one line splits
it apart into two clearly named variables, average and
standard_deviation.
-->

---

## What's legal here

- ✅ `return mean, std_dev` — one tuple, two values inside it
- ✅ `average, std = get_grade_stats(scores)` — unpacked into two names
- ❌ thinking `return a, b` is two separate return statements

Nothing stops you from returning three, four, or more values the same way.

<!--
The function is still only ever returning one object — that object just
happens to hold multiple things. Whether it's two values or five, the
mechanism is identical.
-->

---

# 6.16 Docstrings and help()

<!--
A function with a self-explanatory name still doesn't tell a reader
everything — what does it assume about its arguments, what does it hand
back, are there any gotchas? That's exactly what a docstring is for.
-->

---

## A string that documents a function

**docstring:**
A string literal placed as the very first line inside a function's body, wrapped in triple quotes, describing what the function does.

```python
def num_seats(airliner_type):
    """Determines number of seats on a plane"""
    # function body...
```

<!--
Good practice for a simple function is to keep the docstring on one line,
no blank lines surrounding it. It sits in exactly the same place a comment
might, but as we're about to see, it isn't the same thing at all.
-->

---

## A multi-line docstring for a bigger function

```python
def ticket_price(origin, destination, coach=True, first_class=False):
    """Calculates the price of a ticket between two airports.

    Arguments:
    origin -- code of origin airport
    destination -- code of destination airport
    """
```

<!--
Longer, more involved functions can use a multi-line docstring instead —
describing each parameter and any special rules about how to call it, the
way this one flags that only one of coach or first_class should be True.
-->

---

## help() reads the docstring for you

Pass any object into `help()` and Python prints out whatever documentation is attached to it — for a function, that means its docstring plus its parameter list.

`help(str)` and `help(math)` work the same way on things you didn't write.

<!--
help isn't limited to functions you write yourself — it works on just
about anything, because the language creators wrote docstrings for most of
what ships with Python. Try help(math) after class and see everything
that comes back.
-->

---

## A docstring is not a `#` comment

A `#` comment is invisible to everything except a human reading the source file.

A docstring is an actual string object attached to the function — tools like `help()`, and IDE tooltips, can read it **programmatically**.

<!--
Comments explain how; docstrings explain what, and they get surfaced
automatically by tooling that a comment simply can't reach. That's the
real distinction worth remembering, not just the triple-quote syntax.
-->

---

# 6.17 Engineering examples

<!--
Two worked examples to close out the chapter — the exact same tools from
6.1 through 6.16, just applied to actual physics formulas instead of
pizzas and sandwiches.
-->

---

## The ideal gas law, solved for temperature

```python
gas_constant = 8.3144621  # Joules / (mol*Kelvin)

def convert_to_temp(pressure, volume, mols):
    """Convert pressure, volume, and moles to a temperature"""
    return (pressure * volume) / (mols * gas_constant)
```

Output: `Temperature = 593.01 K`

<!--
gas_constant is defined once as a global variable outside the function —
exactly the case from section 6.10 where a global is genuinely the right
call, because it's a physical constant, not something any function should
ever be modifying.
-->

---

## A projectile's position over time

```python
def trajectory(v, angle_deg, t):
    angle = math.radians(angle_deg)
    x = v * t * math.cos(angle)
    y = (v * t * math.sin(angle)) - (0.5 * 9.81 * t * t)
    return x, y

x_loc, y_loc = trajectory(50, 45, 2)
```

<!--
Since the function needs to hand back both coordinates at once, it leans
on the exact same trick from section 6.15 — pack them into a tuple. A for
loop calling this once per second, checking y_loc greater than zero after
each call, is exactly how you'd generate the object's full path — and the
loop stays short precisely because all the math lives inside the function
instead of getting rewritten every iteration.
-->
