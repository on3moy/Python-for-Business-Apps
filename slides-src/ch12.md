# 12.1–12.2 Handling exceptions

<!--
We begin with the core mechanic: the try and except pair, and how to be specific about which errors you are prepared to handle.
-->

---

## What a crash looks like

```python
# Lets ask for a sales amount
sales = int(input('Enter sales: '))
print(sales * 0.07)

# If the user types 'lots', the script stops
```

Output: `ValueError: invalid literal for int() with base 10: 'lots'`

<!--
Here is the problem we are solving. The user types the word "lots" where we wanted a number, and int() raises a ValueError. An exception, formally, is an error that occurs while the program runs and halts it unless we handle it. Ask the room: how often does real user input look exactly the way you expected? Rarely. Hold that thought as we advance.
-->

---

## try and except

```python
try:
    # Lets put the risky code here
    sales = int(input('Enter sales: '))
    print(sales * 0.07)
except ValueError:
    # Lets run this only if the conversion failed
    print('Could not calculate tax')
print('Still running!')
```

<!--
Risky code goes in the try block. If anything inside raises, Python abandons the rest of the try block, jumps to the matching except, and then continues below it. The line after the except always runs. A common misconception worth addressing: Python never returns to the line that failed. If you want to ask the user again, wrap the try in a while loop, exactly as we did with input validation in chapter five; a short invoice-amount loop is in the notes. Note also that I named ValueError here rather than leaving the except bare; the next slide explains why.
-->

---

## Multiple handlers

```python
try:
    revenue = float(input('Revenue: '))
    units = int(input('Units sold: '))
    print(revenue / units)
except ValueError:
    print('Please enter numbers only')
except ZeroDivisionError:
    print('Units must be more than 0')
```

<!--
One try can fail in more than one way, and each failure deserves its own message. Python checks the except blocks from top to bottom and runs the first match. If the remedy is identical for several types, you may group them in a tuple, for example except open-paren KeyError, ValueError close-paren, which is useful when a missing price and a malformed price both default to zero. If no handler matches, you have an unhandled exception: Python prints the traceback and halts. The full list of built-in exceptions is linked in the notes; a table of the five most common ones is there too.
-->

---

## Avoid the bare except

- `except:` catches everything, including your own typos ❌
- `except ValueError:` names what you expect ✅
- A `NameError` swallowed silently costs you an hour 😓

<!--
A bare except is a catchall, and a catchall hides bugs. Suppose you mistype a variable name. Python raises a NameError, your bare except swallows it, and you spend the afternoon wondering why nothing works. The rule is simple: name the exception you expect. Students will notice the notes use a bare except in the very first example; that was purely to keep the introduction simple, and we do not carry the habit forward.
-->

# 12.3–12.4 Raising exceptions

<!--
Now we turn from catching errors to creating them, and then follow an exception as it travels through function calls.
-->

---

## raise

```python
try:
    discount = float(input('Discount (0 to 1): '))
    if discount < 0 or discount > 1:
        # Lets raise our own error with a message
        raise ValueError('Discount must be between 0 and 1')
    print(f'Price: {100 * (1 - discount)}')
except ValueError as err:
    print(err)
```

<!--
Python is not the only one permitted to cause an exception; you may do so deliberately with raise. Observe how the normal path reads top to bottom, get the discount, print the price, while the validation stays out of the way instead of burying the logic in nested if and else. Which type should you raise? Choose the built-in that best describes the problem: a bad value is a ValueError, a bad type is a TypeError. If nothing fits, we will define our own at the end of the chapter.
-->

---

## Naming it with as

- `except ValueError as err:` creates the variable `err`
- `print(err)` shows the message you passed to `raise`
- Same message, new place: it travels from `raise` to the handler

<!--
The as keyword gives the caught exception a name so that you can inspect it. In the previous slide, err held the string we handed to raise. This is how a deep check in your code gets to speak to the user through a handler elsewhere. Ask the room: where does the message originate, and where is it displayed? They are different places, and that separation is the point.
-->

---

## Errors travel up the call chain

```python
def get_salary(pay):
    if pay < 0:
        # Lets raise and leave the function
        raise ValueError('Negative salary')
    return pay
try:  # The handler lives out here
    print(get_salary(-5))
except ValueError as err: print(err)
```

<!--
Exceptions become genuinely powerful once functions are involved. When a function raises and does not handle the exception, it exits at once, and Python looks for a handler in the caller, then the caller's caller, all the way up. Think of a manager chain: the analyst meets a problem, cannot fix it, and passes it upward until someone with authority picks it up. Note that raise does not require a try inside the function. Put the try and except where you actually know what to do about the error.
-->

---

## Why not return -1?

- Returning `-1` forces every caller to remember an `if` check ❌
- Forget once, and `-1` quietly flows into your math ❌
- `raise` makes the caller handle it or stop loudly ✅

<!--
The alternative design is for get_salary to return a sentinel such as negative one. It looks harmless, but it makes correctness depend on every caller's diligence, and a single omission lets a bogus value corrupt a calculation without a sound. An exception fails loudly, which in business software is precisely what you want. Silent wrong answers are the expensive kind.
-->

# 12.5 Using finally

<!--
Some actions must occur regardless of what happened above them. For those, Python provides finally.
-->

---

## finally always runs

```python
report = None
try:
    report = open('sales.txt')
except FileNotFoundError:
    print('No sales file found')
finally:
    # Lets always close, even after a crash
    if report: report.close()
```

<!--
Closing a file or a database connection is the classic case. The finally block is attached to the try, placed after any except blocks, and runs whether or not an exception occurred. Why the check for None? If open itself fails, report never received a file, and calling close on None would raise a brand new error inside finally. So we initialize to None first and test. The notes add a ValueError handler for malformed lines and a small divide function that prints its result in finally; that makes a good exercise to try live if time permits.
-->

---

## When finally runs

- No error: after the `try` finishes ✅
- Handled error: after the `except` runs ✅
- Unhandled error: runs first, then the exception keeps going ✅
- Even when `try` exits via `break`, `continue`, or `return` ✅

<!--
The guarantee is unconditional, and that is why it is trusted for cleanup. Walk through the four cases deliberately. The unhandled case is the subtle one: finally runs first, and only then does the exception continue to propagate. Pause here and ask whether anyone can think of a resource in their own projects that must always be released.
-->

# 12.6 Custom exception types

<!--
Finally, we close the loop with chapter eleven: inheritance applied to errors.
-->

---

## Your own named error

```python
# Lets define our own error, inheriting from Exception
class NegativeBalanceError(Exception):
    pass

try:
    raise NegativeBalanceError('Balance cannot be negative')
except NegativeBalanceError as err:
    print(err)
```

<!--
Built-in exceptions do not always describe what went wrong in your business. A custom exception is simply a class that inherits from Exception, which should feel familiar from our work on derived classes. The word pass is sufficient because a class body requires at least one statement. In the notes the raise sits inside an if that tests for a balance below zero. Naming convention: end with Error.
-->

---

## Carrying extra information

```python
class NegativeBalanceError(Exception):
    def __init__(self, message, balance):
        super().__init__(message)
        # Lets keep the bad value for the handler
        self.balance = balance
```

<!--
Custom exceptions are usually tiny, but when the handler needs more than a message, store it as an attribute. Here the offending balance travels with the exception, so the handler can log or display it. This is the same super dot init pattern we used in the inheritance chapter, now serving error handling.
-->

---

## Why not just ValueError?

- `except NegativeBalanceError` catches only that problem ✅
- A `ValueError` handler catches every bad value in the block ❌
- pandas and requests define their own for this reason

<!--
The case for specificity: a handler for ValueError would also swallow bad values you never intended to handle, reintroducing the very problem we saw with the bare except. A named exception lets the handler be precise. This is why mature libraries such as pandas and requests ship their own exception types.
-->
