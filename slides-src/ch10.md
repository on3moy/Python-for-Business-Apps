# 10.1 Classes: introduction

<!--
Before we write a single line of class syntax, we need the idea straight:
what is an object, and why bother grouping things into one instead of
just carrying a pile of separate variables around. This section is short
on purpose -- one real idea, dressed in two examples.
-->

---

## Why bother grouping things

- An **object** bundles data and the operations on it into one unit
- You already talk this way at work: "the customer," not "the string in
  B2 and the number in C2"
- Ask which pieces belong together: do they describe the same thing, and
  get used together?

<!--
Your brain already does this grouping without any code involved. Nobody
describes a customer record as a loose string and a loose number sitting
in two spreadsheet cells -- you say "the customer," and that one word
carries a name, a phone number, a balance, and whatever you're allowed to
do with them, all bundled together. A class is the code version of that
same instinct.

The test for what belongs together, if you want a rule of thumb: for a
used-car inventory program, sticker_price and days_on_lot both describe
one car, so they belong on one object. today's_temperature does not
describe the car at all, no matter how related it feels, and it stays
out.

One term worth planting here without a slide of its own: abstraction, or
information hiding -- an object exposes a handful of operations and
hides the rest, the same way an oven gives you a temperature knob and
hides the heating element. We'll see exactly what that hiding looks like
in code a few sections from now, in the interface section.
-->

---

## You've been using objects the whole time

```python
# Lets look at what Python built for you already
mystr = 'Hello!'
print(mystr.isdigit())
print(mystr.lower())
```

Output: `False` then `hello!`

<!--
Every string you've ever created is already an object. The value
'Hello!' and the functions that operate on it -- isdigit, lower, and
every other string method -- are bundled together into one str object
the moment you write mystr = 'Hello!'. You've been instantiating Python's
built-in type all semester without ever calling it that.

The rest of this chapter is about writing your own version of exactly
this: a type you design, with data and behavior that make sense for your
own business problem, instead of borrowing Python's.
-->

# 10.2–10.3 Writing a class

<!--
Now we write one. The class keyword, the constructor every class needs,
the self parameter that shows up in every method, and then instance
methods -- behavior that lives with the data instead of floating around
elsewhere in the file. We'll also look at the single most common mistake
beginners make with classes, which is forgetting that self parameter.
-->

---

## The `class` keyword

```python
class Time:
    """ A class that represents a time of day """
    def __init__(self, hours, minutes):
        self.hours = hours
        self.minutes = minutes
```

`__init__` is the constructor — it runs automatically on every new instance

<!--
class opens a new type definition, and __init__ is a special method
Python calls a constructor -- it runs the instant a new instance is
created, and it's where you set up the instance's starting state.

self is the first parameter of every method a class defines, and it's
Python's automatic reference to the specific instance the method was
called on. You never pass an argument for self yourself -- Python
inserts it the moment you call a method on an instance. Hold onto that
sentence; it explains the classic bug we'll hit in two slides.
-->

---

## Instantiation

```python
# Lets create two separate Time instances
time1 = Time(7, 30)
time2 = Time(12, 45)
print(f'{time1.hours}:{time1.minutes}')
print(f'{time2.hours}:{time2.minutes}')
```

Output: `7:30` then `12:45`

<!--
Writing Time(7, 30) calls __init__ behind the scenes and hands back one
instance -- a specific object built from the class's blueprint. Creating
one is called instantiation, and it reads exactly like a function call.

The part worth pausing on: time1 and time2 each keep their own separate
copy of hours and minutes. The dot in time1.hours is the attribute
reference operator, and changing time2 never touches time1 -- they share
a blueprint, not any data. Naming convention, said once and not dwelled
on: capitalize each word in a class name, no underscores -- Time,
LunchMenu, PDFFileContents.
-->

---

## Instance methods carry behavior with the data

```python
class Time:
    # __init__ sets self.hours and self.minutes
    def print_time(self):
        print(f'{self.hours}:{self.minutes}')

Time(7, 15).print_time()
```

Output: `7:15`

<!--
The __init__ is elided to a comment here so the method stays in focus --
it assigns self.hours and self.minutes exactly as you saw two slides ago.

print_time is an instance method -- a function defined inside the class,
called on an instance with dot notation. This is where a class starts
pulling its weight: the formatting logic doesn't live somewhere else in
the file waiting to be called with the right variables passed in, it
travels with the data itself.

Notice print_time still takes self as its first parameter, even though
Time(7, 15).print_time() is called with an empty argument list. Python
quietly binds self to that instance for you, which is exactly what lets
the method reach self.hours and know whose attribute to grab.
-->

---

## Forgetting `self` is the classic mistake

```python
def calculate_pay(self):  # correct
    return self.wage * self.hours_worked

def calculate_pay():      # forgot self -- breaks
    return self.wage * self.hours_worked
```

`alice.calculate_pay()` on the broken version: `TypeError: takes 0 positional arguments but 1 was given`

<!--
Walk through that error message slowly, because it's confusing the first
time you see it. "1 was given" is Python quietly inserting alice as an
argument the instant you call the method on an instance -- the method
body just wasn't written to accept it. Every method you write needs self
first, no exceptions, and __init__ is not special in this regard --
it's a method too, just one Python happens to call automatically.

Worth one sentence and no slide: methods with double underscores on
both sides, like __init__, are called special methods -- they signal
built-in behavior to Python. We'll meet several more of those later in
the chapter: __str__, __lt__, __add__. Keep double underscores out of
your own regular names so you never collide with one by accident.
-->

# 10.4 Class and instance object types

<!--
A program with a class actually has two kinds of objects in play: the
class object itself, and however many instances you build from it. They
don't always store attributes the same way, and mixing that up is a
real source of bugs, so we'll look at each side with its own example.
-->

---

## A class attribute is shared

```python
class MarathonRunner:
    race_distance = 42.195  # kilometers, same for everyone

    def __init__(self):
        self.speed = 0

print(MarathonRunner.race_distance)
print(MarathonRunner().race_distance)
```

Output: `42.195` then `42.195`

<!--
race_distance is defined in the body of the class itself, not inside
__init__, which makes it a class attribute -- it lives once, in the
class's own namespace, and every instance shares that exact same copy.
When you write runner1.race_distance, Python checks runner1's own
namespace first, doesn't find it there, and falls back to
MarathonRunner's namespace. That fallback is why an instance can read a
class attribute it never explicitly stored on itself.
-->

---

## An instance attribute is not

```python
runner1 = MarathonRunner()
runner1.speed = 7.5
runner2 = MarathonRunner()
runner2.speed = 8.0
print(runner1.speed, runner2.speed)
```

Output: `7.5 8.0`

<!--
speed is set with self.speed inside __init__, so each instance gets its
own private copy the moment it's created -- changing runner1.speed never
touches runner2.speed. That's the instance attribute half of the
distinction: constants and shared configuration belong at the class
level, but anything that varies from one object to the next -- and
methods, which live in the class namespace by default anyway -- needs
self.attr inside a method.

One warning worth saying out loud without a slide: if a class and one of
its instances both define an attribute with the same name, the
instance's version always wins when you read self.attr. Good practice
is just to avoid the collision -- pick different names for class-level
constants and instance-level data.
-->

# 10.5 Putting it together: two classes

<!--
Real business programs usually need more than one class working
together -- one class managing a collection of instances of another.
Let's build a small consulting-invoice system to see the pattern.
-->

---

## `LineItem` knows only its own job

```python
class LineItem:
    def __init__(self, description, hours, rate):
        self.description = description
        self.hours = hours
        self.rate = rate

    def total(self):
        return self.hours * self.rate
```

<!--
LineItem knows nothing about invoices at all -- it only knows how to
describe itself and total itself up, and that's deliberate. Keeping it
narrow is what lets you reuse it somewhere else later -- a time tracker,
a quote generator -- without dragging invoice logic along with it.
-->

---

## `Invoice` manages a list of `LineItem`s

```python
# Lets bill Acme Corp for two pieces of work
invoice = Invoice('Acme Corp')
invoice.add_item(LineItem('Data pipeline setup', 8, 125))
invoice.add_item(LineItem('Dashboard build', 12, 100))
print(f'{invoice.client_name} owes ${invoice.grand_total():.2f}')
```

Output: `Acme Corp owes $2200.00`

<!--
Invoice holds a plain list of LineItem instances in self.items.
add_item() appends to that list, and grand_total() sums each item's own
total() without needing to know how any individual item computes it --
it just calls .total() and trusts the answer back.

That's the whole pattern: a LineItem and an Invoice are genuinely
different things with different jobs, one describing a single billed
task and the other managing a collection of them. Splitting them keeps
each class small enough to reason about. This is exactly how you start
modeling real business shape -- an order and its line items, a cart and
its products, a roster and its students.
-->

# 10.6 Class constructors

<!--
Every __init__ so far has taken no parameters besides self and hardcoded
a starting value. That's rarely how you actually want to build an
object -- usually you know some of the data up front, at the moment
you create the instance. Two slides: constructors with required
parameters, then constructors with defaults.
-->

---

## Constructor parameters, filled in at creation

```python
class RaceTime:
    def __init__(self, start_time, end_time, distance):
        self.start_time = start_time
        self.end_time = end_time
        self.distance = distance

jason = RaceTime('3:15', '7:45', 26.21875)
```

<!--
Instantiation now requires arguments, exactly like calling a function
does. Each argument gets saved onto the instance with self.attr = attr,
so any method you write later -- print_pace, say -- can read it straight
back. This is the far more common shape than the empty constructors
we've written up to now.
-->

---

## Default parameter values work the same as in a function

```python
class Employee:
    def __init__(self, name, wage=8.25, hours=20):
        self.name = name
        self.wage = wage
        self.hours = hours

tricia = Employee('Tricia', 12.50, 40)  # manager, overrides both
```

`Employee('Todd')` alone gets the part-timer defaults

<!--
The same rule from regular functions carries straight over: parameters
without a default are required and come first, parameters with a
default are optional and can be overridden positionally or by name.
Employee('Jason', hours=40) overrides only hours by name and keeps the
default wage -- all three call shapes are valid, and which one you reach
for is just about how much you actually need to say.
-->

# 10.7 Class interfaces

<!--
Not every method a class defines is meant for a caller to touch. This
section is about the convention Python uses to mark the difference, and
the vocabulary -- interface versus implementation -- for why that split
matters at all.
-->

---

## The underscore marks "internal, don't call this"

```python
class RaceTime:
    def print_pace(self):
        h, m = self._diff_time()
        print(f'Avg pace: {(h*60+m)/self.distance:.2f}')

    def _diff_time(self):
        """Internal helper -- not part of the interface"""
        return (self.end_hrs - self.start_hrs, self.end_mins - self.start_mins)
```

<!--
The class interface is the set of methods a caller is meant to use --
for RaceTime, that's __init__ and print_pace. _diff_time leads with an
underscore on purpose: it signals to anyone reading the class that this
is internal plumbing, called only from inside the class itself.

Python has no true private methods -- race._diff_time() still works if
someone types it, the underscore doesn't block access, it just tells the
reader "don't." Good practice is to respect that signal on classes you
didn't write, and add it yourself on anything you don't want other code
depending on.

This is also the entire payoff of the class interface as a concept, a
class being how you implement what the notes call an abstract data
type: as long as print_pace and __init__ keep behaving the same way
from the outside, you're free to rewrite _diff_time completely -- swap
the algorithm, fix a bug in it, whatever -- and nothing that already
calls RaceTime has to change a single line. Ask the room: why bother
with this if Python can't actually enforce it? Because the goal was
never to stop a determined coworker, it's to communicate intent, so a
future reader knows exactly what they're safe to depend on.
-->

# 10.8–10.9 Customizing your class

<!--
Print an instance right now and you get something like
<__main__.Toy object at 0xb74cb98c> -- not useful to anyone. This section
is where the special methods from 10.3 start earning their keep: define
the right one, and Python calls it for you automatically whenever you
print, compare, or do arithmetic with your objects.
-->

---

## `__str__` controls what `print()` shows

```python
class Toy:
    # __init__ sets self.name and self.price
    def __str__(self):
        return f'{self.name}: ${self.price:.2f}'

print(Toy('Monster Truck', 14.99))
```

Output: `Monster Truck: $14.99`

<!--
The __init__ is elided here to keep the method in focus -- it sets
self.name and self.price exactly the way you've seen all chapter.

The instant print(truck) runs, Python calls truck.__str__() for you and
prints whatever string comes back -- you never call __str__ yourself,
Python does it on your behalf the same way it calls __init__ on your
behalf at creation time.
-->

---

## Overloading `<` for your own type

```python
class Time:
    def __lt__(self, other):
        if self.hours != other.hours:
            return self.hours < other.hours
        return self.minutes < other.minutes

times = [Time(10, 40), Time(12, 15), Time(9, 15)]
print(min(times))
```

<!--
Operator overloading means redefining what a built-in operator does for
instances of your own class. t < min_time silently calls
t.__lt__(min_time) -- self is the left operand, other is the right one --
and once __lt__ returns True or False correctly, a whole ecosystem of
built-in tools starts working on your class for free: sorted(), min(),
max(), all without writing them yourself.

Warn them: nothing stops __lt__ from implementing something that isn't
actually "less than." Only overload an operator when the resulting
behavior would be obvious to someone reading a < b in your code --
otherwise write a named method instead.
-->

---

## Six rich comparison methods cover every operator

| Method | Operator |
|-|-|
| `__lt__` / `__le__` | `<` / `<=` |
| `__gt__` / `__ge__` | `>` / `>=` |
| `__eq__` / `__ne__` | `==` / `!=` |

Define only the ones your class actually needs

<!--
Don't read this table row by row -- it's a reference, and the notes
carry the full version. The one useful pattern: less-than, less-or-
equal, greater-than, greater-or-equal, equal, not-equal, each pairing an
underscore method with the symbol you already know. Define __lt__ and
__eq__ and you've covered most of what sorting and searching ever ask
for.
-->

---

## Arithmetic operators, guarded with `isinstance()`

```python
def __sub__(self, other):
    if isinstance(other, int):
        return Time24(self.hours - other, self.minutes)
    if isinstance(other, Time24):
        return Time24(self.hours - other.hours, self.minutes - other.minutes)
    raise NotImplementedError
```

<!--
+, -, *, and / can be overloaded too, through __add__, __sub__, __mul__,
and __truediv__ -- the full list, including __abs__, __int__, and
__float__, is in the notes and you implement only what your class
actually needs.

The wrinkle arithmetic introduces that comparison didn't: __sub__ fires
whenever the left operand is a Time24, even in time1 - 1, so without a
check it would crash trying to read .minutes off a plain integer.
isinstance(value, Type) checks what you actually got before you assume
it has the attributes you expect -- guard the type first, then branch on
what the right-hand side actually is.
-->

# Recap

- An object bundles data and behavior; a class is the blueprint
- `__init__` and `self` set up and refer to one instance
- Class attributes are shared; instance attributes belong to one object
- One class can manage a collection of another — `Invoice` and `LineItem`
- `__str__`, `__lt__`, `__sub__` teach your objects to print, compare, and add

<!--
Walk back through the arc once before questions: an object is data and
behavior bundled into one unit, a class is how you define that bundle
yourself, and self is what lets one set of methods serve every instance
you create from it. Class attributes are shared across every instance,
instance attributes belong to exactly one. Classes compose -- Invoice
managing a list of LineItems is the shape almost every real business
program eventually takes. The underscore convention communicates intent
even without enforcing it. And the special methods -- __str__, __lt__,
__sub__ -- are how your own types plug into print(), sorted(), min(),
and ordinary arithmetic the same way Python's built-in types already do.

That's the whole toolkit for building your own types. Questions before
we move on?
-->
