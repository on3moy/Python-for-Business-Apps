# 11.1–11.2 Derived classes and attribute lookup

<!--
We begin with the core mechanic: how one class inherits from another, and how Python finds what it needs on an inherited object.
-->

---

## Inheritance in one slide

- *Base class*: the class being inherited from
- *Derived class*: inherits everything, adds its own variations
- Methods and attributes arrive for free
- Any class can be a base class, unchanged

<!--
Ever copied a class, changed two lines, and called it a new class? Inheritance exists so that you never have to. The base class is the original; the derived class receives its attributes and methods automatically and adds whatever is different. Notice that the base class does not need to be modified at all, which is what makes this safe.
-->

---

## Deriving a savings account

```python
class Account:
    def __init__(self):
        self.owner, self.balance = '', 0
# Lets derive by putting the base class in parentheses
class SavingsAccount(Account):
    def __init__(self):
        Account.__init__(self)  # Lets call the base constructor
        self.rate = 0.0
```

<!--
A SavingsAccount is really an Account with an interest rate on top. It inherits owner, balance, and any methods such as display without our retyping them. Point out the parenthesized base class on the class line, and the explicit constructor call on the fourth line of the derived __init__.
-->

---

## Call the base constructor yourself

- Methods are inherited automatically
- Instance attributes are **not**: only `__init__` creates them
- Skip `Account.__init__(self)` and `owner` never exists
- Result: an `AttributeError` the moment you touch it

<!--
This is the most common inheritance bug. Methods come along for free, but instance attributes exist only because a constructor ran and created them. If your derived constructor does not hand the new object to the base constructor, the base attributes are simply never made. Ask the room what error they would see; the answer is AttributeError.
-->

---

## Where does Python look?

```python
class Employee:
    def info(self): print('works here')
class Manager(Employee):
    def assign(self): print('assigning')
class Director(Manager): pass
boss = Director()
boss.assign()  # Lets find it on Manager
boss.info()    # Lets climb up to Employee
```

<!--
The search order is the instance, then its class, then each base class going up the inheritance tree, stopping at the first match. Think of asking your manager a question: if they do not know, they ask their manager. Here boss.info searches Director, then Manager, then Employee, where it finally succeeds. Also mention that a class can have many derived classes, and a derived class can itself be a base class. Multiple base classes come up shortly in the mixin section.
-->

# 11.3 Overriding class methods

<!--
Because the search stops at the first match, a derived class can quietly replace behavior. That is overriding.
-->

---

## Override a method

```python
class Invoice:
    def __init__(self, amount): self.amount = amount
    def display(self): print(f'Invoice: {self.amount}')

class RushInvoice(Invoice):
    # Lets replace display with our own version
    def display(self):
        print(f'RUSH: {self.amount * 1.25}')
```

<!--
The method closest to the instance always wins. A RushInvoice looks in its own class first, finds display, and never reaches the Invoice version. Run both and show the output: Invoice 100, then RUSH Invoice 125.0.
-->

---

## Extend with super()

```python
class RushInvoice(Invoice):
    def __init__(self, amount, fee):
        super().__init__(amount)  # Lets let the base set amount
        self.fee = fee

    def display(self):
        super().display()  # Lets run the base version first
        print(f'  Rush fee: {self.fee}')
```

<!--
Usually you do not want to discard the base method, only add to it. super is a shortcut for "my base class": you do not type the class name or pass self. It is the usual way to initialize inherited attributes, and if you rename the base class later you do not have to hunt down every call.
-->

---

## Polymorphism

```python
# Lets mix both types in one list
invoices = [Invoice(100), RushInvoice(200, 50)]

for inv in invoices:
    inv.display()  # Each object runs its own version
```

One name, many behaviors.

<!--
This is polymorphism. Because each class has its own display, one loop can handle a mixed list and the objects decide how to print themselves. In report or ETL code, this means a single loop and no chain of type checks. Pause here and ask where in a payroll system this would remove an if-else ladder.
-->

<!--

-->

---

"A Manager **is an** Employee" ✅

</div>
<div>

## Has-a: compose
"A Department **has** Employees" ✅

</div>
</div>

<!--
The quick test is to say it aloud. A Manager is an Employee sounds right, so inherit. A Department is an Employee sounds silly, so a Department instead holds a list of Employee objects. Real classes mix both: a Manager is an Employee and also has a list of reports. This echoes the collection class from chapter 10 where one class held many instances of another.
-->

---

## A mixin adds a few methods

```python
class ExportMixin:
    def to_csv(self): print(f'{self.title},{self.rows}')

class Report:
    def __init__(self, t, r): self.title, self.rows = t, r
# Lets mix in the extra
class SalesReport(Report, ExportMixin): pass
SalesReport('Q3', 250).to_csv()
```

<!--
A mixin is a small class that adds methods to whatever uses it and is not meant to be instantiated alone. Think of Excel add-ins: the workbook works without them, but plug one in and you gain features. Listing several base classes is multiple inheritance. You write to_csv once rather than copying it into five report classes, and each class takes only what it needs.
-->

---

## Order matters

- Base classes are searched **left to right**
- `SalesReport(Report, ExportMixin, EmailMixin)`
- Two mixins with `send()`? The first listed wins
- The other is silently ignored

<!--
Python checks the bases in the order written. If two mixins define the same method name, the first one wins and nothing warns you about the other. Keep method names unique, or be deliberate about the order in the parentheses.
-->

# 11.6 Testing with unittest

<!--
Last topic. Change one class and you may break three others without knowing it. A test suite you can rerun in seconds is the fix.
-->

---

## Your first test class

```python
import unittest

class TestInvoice(unittest.TestCase):  # Lets inherit TestCase
    # Lets name methods test_ so they run
    def test_with_tax(self):
        self.assertAlmostEqual(Invoice(100).with_tax(), 110)

unittest.main()  # Lets run every test
```

Output: `.` is a pass, `F` is a fail.

<!--
Unit testing means testing individual pieces, such as one method at a time. TestInvoice is itself a derived class, so the chapter is already paying for itself. Any method starting with test_ runs. In the notes there is a deliberately failing example that prints a dot for the pass and an F with an AssertionError for the failure; run that live so students see both outcomes.
-->

---

## Floats and assertEqual

- `100 * 1.10` is not exactly `110` in floating point
- Decimals: `assertAlmostEqual()` ✅
- Decimals: `assertEqual()` ❌

<!--
Floating-point arithmetic has tiny representation errors, so exact equality is a trap for money-like decimals. Use assertAlmostEqual, which compares after rounding to seven places.
-->

---

|assertTrue(x)|bool(x) is True|
|assertIsNone(x)|x is None|
|assertIn(a, b)|a in b|
|assertGreater(a, b)|a > b|
