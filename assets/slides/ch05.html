Everything we've written so far has been counting, or watching for a sentinel. A for loop is built for a different, extremely common job: walk through every item in a container, one at a time, with no manual bookkeeping.

Compare this to a while loop, where you own every piece of the bookkeeping — the starting value, the update, the condition. A for loop takes all three of those off your hands the moment you're walking a container instead of counting toward a number.

No counter, no condition to write yourself — the for loop just knows to stop once the list runs out. This is the pattern you'll reach for anytime "do this once per item" is the actual job.

A string is a sequence type, the same family as a list, so a for loop walks it character by character with no extra syntax needed. If you can loop over a list, you can loop over a string.

Looping over a dictionary gives you keys, never values, in insertion order. Writing "for value in channels" would still be handing you 'MTV' and 'CNN' — the variable name doesn't change what Python actually gives you. You look the value up yourself with the key, exactly like this.

This is the revenue-tracking cousin of the sentinel-driven average we built with a while loop back in section 5.3 — same running-total idea, except now the container itself tells us when to stop, so there's no sentinel and no guard needed against dividing by zero.

Sometimes the cleanest way to write a loop is to give yourself an escape hatch, rather than stuffing every possible exit condition into the loop's own expression.

Break doesn't wait for the condition to become False on its own — it cuts the loop off mid-stride, the instant you tell it to. Let's see it searching a nested loop for an exact answer.

Notice there are two break statements — one to escape the inner loop, and a second, separate one to escape the outer loop right after. Break only ever exits the loop directly wrapping it, which is exactly why a nested search needs one break per level.

Continue doesn't leave the loop the way break does — it just abandons the rest of this one pass and moves straight to the next. Watch what that does to a divisibility check.

Every number that fails the divisible-by-3 check gets continued right past — the print line never runs for those values. You could rewrite this with an if wrapping the rest of the body instead, and functionally it'd be identical; continue just reads as "nope, next one" and stays out of the way once there's more than one line left to skip.

This is a style note as much as a technical one. Both of these are powerful, and both are easy for someone else — or future you — to miss while scanning code quickly. Reach for them when they make the logic clearer, not as a reflex.

Loop else answers exactly one question: did this loop get interrupted by a break? Not whether the condition ever came back False — those sound similar but they are not the same thing, and mixing them up is the most common misread of this construct.
