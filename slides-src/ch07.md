# 7.1 Recursive functions

<!--
We start with the simplest possible recursive function — one that counts
down and stops — purely to watch the mechanics: what a call to itself
actually does to memory, and why it eventually has to stop.
-->

---

## A function that calls itself

**recursive function:**
A function that calls itself, either directly or by calling another function that eventually calls it back.

```python
# Lets count down to a launch
def count_down(count):
    if count == 0:
        print('Go!')
    else:
        print(count)
        count_down(count - 1)
count_down(2)
```

Output: `2` then `1` then `Go!`

<!--
A while loop would do this job in fewer lines — the point here isn't
efficiency, it's watching what happens underneath. count_down(2) prints 2
and calls count_down(1), which prints 1 and calls count_down(0), which
prints Go! and stops. Three separate calls, and each one gets its own
private count variable sitting in its own namespace — the same way any two
ordinary function calls never share variables, even when those two calls
happen to be the same function calling itself. Ask the room: at the exact
moment count_down(0) is running, does the count equal to 1 from the call
above it still exist somewhere? It does — it's just waiting, paused, for
that inner call to finish.
-->

---

## Every recursive function needs a way out

Find the branch that stops the recursion — here, `count == 0`.

Miss that branch, or write it so the count moves *away* from it instead of *toward* it, and the function calls itself until Python gives up.

<!--
This is the single most important habit to build right now, before we've
written anything more complicated than a countdown: locate the stopping
condition first, every time, before you worry about anything else the
function does. We'll formalize this as the base case in section 7.4, but
the instinct to hunt for "what makes this stop" starts today. Next we look
at a recursive algorithm that actually earns its keep in real code —
binary search.
-->

---

# 7.2–7.3 Recursive search, and debugging it

<!--
Binary search is the first recursive algorithm in this chapter you would
genuinely reach for in production code. We'll build it, then look at the
one debugging trick that makes any recursive function's behavior visible
instead of a black box.
-->

---

## Guess by halving the range, not scanning

Guessing a number 0–100 one at a time averages 50 tries. Guess the *midpoint* of what's left every time — 50, then 25 or 75, then half of that — and you land it in about 7 tries no matter what.

That's binary search: guess the middle, throw away the half that can't hold the answer, repeat.

<!--
This only works because the data is sorted or ordered in some way — you
can't throw away half the search space unless you know which half the
answer has to be in. That guarantee is what makes each guess worth roughly
double the last one. Let's apply that exact halving idea to something more
useful than a guessing game — finding an item in an already-sorted list.
-->

---

## Binary search on a sorted list

```python
def find(lst, item, low, high):
    mid = (high + low) // 2
    if item == lst[mid]:  return mid   # Base: found
    if low == high:       return -1    # Base: not found
    if item < lst[mid]:
        return find(lst, item, low, mid)
    return find(lst, item, mid + 1, high)
```

<!--
Notice this one needs two base cases instead of one — found the item, or
ran out of list to search — because both of those are legitimate ways for
the search to end. Recursive functions can have as many base cases as the
problem genuinely needs; count_down only needed one because it only had one
way to stop. In practice you would reach for Python's own `in` operator
or list.index() before hand-rolling this — it's here because the shape maps
so cleanly onto recursion, not because it's the production-ready tool.
-->

---

## Watching it happen: indented debug output

```python
def find(lst, item, low, high, indent):
    print(f'{indent} range {low}-{high}')
    mid = (high + low) // 2
    # ...same base/recursive cases, but every
    # recursive call passes indent + '   '
```

Each call's `indent` is three spaces deeper than its caller's — the printed output staircases down with every level of recursion.

<!--
This is the one debugging technique worth building into muscle memory for
recursive code specifically: an ordinary print statement inside a
recursive function gets you output from every call tangled together at the
same indentation, which is nearly useless. Pass an extra bookkeeping
parameter — indent — along with the rest of the arguments, and grow it by a
few spaces on every recursive call. Walk the room through a live trace on
the board right now: call find on a five-item list, and watch the range
narrow by one level of indentation each time, until the base case fires at
the deepest, most-indented line and the whole thing unwinds back out,
returning through every one of those pending calls in reverse order. That
unwinding is exactly what section 7.4 is about to name formally.
-->

# 7.4 Creating a recursive function

<!--
Now we name the two pieces you've already been looking at in count_down
and find, and turn "watch me write one" into a repeatable recipe you can
apply to a function you've never seen before.
-->

---

## Two cases, every time

|Case|What it means|Does|
|-|-|-|
|Base case|The stopping condition|Returns a value directly|
|Recursive case|Everything else|Calls itself on a smaller version|

No reachable base case → infinite recursion → `RecursionError`.

<!--
Every recursive function you will ever write follows this exact shape —
one condition where it stops and answers directly, and one where it calls
itself again on a problem that's gotten smaller. We saw find need two base
cases; that's still this same table, just with two rows in the top slot
instead of one. The failure mode that caveat line names has two flavors:
forgetting the base case branch entirely, or writing one whose condition
the recursive calls never actually reach because the argument is moving
away from it instead of toward it. Either way, Python eventually kills the
program for you rather than let it spin forever.
-->

---

## Build the base case first, then add recursion

```python
def nfact(n):
    fact = 0
    if n == 0 or n == 1:      # Base case
        fact = 1
    else:                     # Recursive case
        fact = n * nfact(n - 1)
    return fact
```

Get the base case working and tested *before* you write the branch that calls the function again.

<!--
This is the practical recipe: write and test the stopping branch in
isolation first — call nfact(1), confirm it returns 1, and only then add
the else branch that multiplies n by a smaller call to itself. Factorial
isn't actually the best real-world case for recursion — a plain loop does
the same job without paying for a growing call stack — but it's simple
enough to show this two-step build process with nothing else competing for
your attention. Before reaching for recursion on a real problem, ask
whether it genuinely breaks into a smaller version of itself, and whether
recursion is actually clearer than a loop here — not just possible.
-->

---

## Splitting into an outer and inner function

A common pattern: an **outer** function callers actually use — `factorial(n)` — hands off to an **inner** helper, often prefixed `_`, that carries the extra bookkeeping the recursion needs.

`find(lst, item, low, high)` is really an inner helper — a caller shouldn't have to supply `low` and `high` by hand.

<!--
The indent parameter from the last section and the low/high range in
binary search are both exactly this problem — they're only meaningful
while the recursion is running, and forcing every caller to supply them by
hand makes the public interface confusing. An outer function validates
whatever the caller actually cares about — n isn't negative, say — then
calls the inner one, which is free to carry whatever bookkeeping the
recursion itself needs. We'll see this shape again in the next section.
-->

# 7.5 Recursive math functions

<!--
Some classic math sequences are defined in terms of their own earlier
values before you've written a line of code — which makes them recursion's
most natural home turf.
-->

---

## Fibonacci: each term from the two before it

```python
# Lets generate the next five Fibonacci terms
def fibonacci(v1, v2, run_cnt):
    print(f'{v1} + {v2} = {v1 + v2}')
    if run_cnt > 1:                       # Recursive case
        fibonacci(v2, v1 + v2, run_cnt - 1)

fibonacci(0, 1, 5)
```

Output: `0 + 1 = 1`, `1 + 1 = 2`, `1 + 2 = 3`, …

<!--
0, 1, 1, 2, 3, 5, 8 — each number the sum of the two before it — is a
recursive definition in plain English before it's a line of code. This
function shifts the running pair forward by one step and counts down
run_cnt, the exact same "smaller version of the same problem" shape as
count_down, just carrying two values forward instead of one.
-->

---

## GCD, and recursion's depth limit

```python
def gcd(n1, n2):
    if n1 == n2:             # Base case
        return n1
    elif n1 < n2:
        return gcd(n1, n2 - n1)   # Recursive case
    else:
        return gcd(n1 - n2, n2)   # Recursive case
```

`gcd(12, 8)` → `4`. Push any recursion ~1000 calls deep and Python raises `RecursionError` — every pending call sits in memory until it returns.

<!--
Euclid's algorithm, circa 300 BC — repeatedly subtract the smaller number
from the larger until they're equal, and that equal number is the greatest
common divisor. The depth-limit line matters more than it looks: unlike a
while loop, which just runs forever until you kill it, runaway recursion
runs out of stack space and Python raises RecursionError for you
automatically — usually a useful early warning that a base case isn't
actually being reached. sys.setrecursionlimit() can raise that ceiling, but
treat it as a last resort, not a fix.
-->

# 7.6 Recursive exploration of all possibilities

<!--
This is where recursion stops being a neat trick for math sequences and
starts earning its keep for real — generating every possible arrangement
of something, which loops alone get awkward doing fast.
-->

---

## Every ordering of a set of choices

```python
def scramble(remaining, chosen):
    if len(remaining) == 0:    # Base case
        print(chosen)
    for i in range(len(remaining)):
        rest = remaining[:i] + remaining[i+1:]
        scramble(rest, chosen + remaining[i])
scramble('cat', '')
```

Output: `cat`, `cta`, `act`, `atc`, `tca`, `tac`

<!--
remaining holds what hasn't been picked yet, chosen holds what has. Every
recursive call moves one item across from one to the other, and the base
case fires the instant nothing is left to move. This same shape generates
every ordering of anything — meeting agendas, delivery routes, shift
assignments — not just letters in a word.
-->

---

## Backtracking: pick, recurse, then undo the pick

**backtracking:**
Move an item into a partial solution, recurse on what's left, then undo the move before trying the next option.

```python
def shopping_bag(bag, items):
    if len(bag) == 3:                # Base case: bag full
        print(bag)
    else:
        for i, item in enumerate(items):
            bag.append(item); items.pop(i)
            shopping_bag(bag, items)
            items.insert(i, item); bag.pop()  # Undo
```

Same undo-then-try-the-next-branch shape powers route planning and discount-code search.

<!--
The undo step after the recursive call is what makes this work — putting
the item back into items and popping it out of bag means the exact same
lists get reused for every other branch of the exploration, instead of
needing a fresh copy at every level. This is why recursion earns its keep
here in a way nested for loops can't match: three loops handle exactly
three picks, four loops handle exactly four — but this function calls
itself once per remaining choice regardless of whether that's 3 items or
30, with no change to the code at all. That flexibility is the real payoff
of exploring possibilities recursively rather than by hand-nesting loops.
-->
