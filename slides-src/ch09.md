# 9.1 Lists

<!--
One habit matters more than any other as your programs grow: knowing
when you're modifying a list in place versus just handing out a second
name for the same object. Get this wrong and you'll ship a bug that only
shows up when two parts of your program share data they shouldn't.
-->

---

## One list, two names

```python
# Lets hand a roster off to another department
my_teams = ['Lakers', 'Dodgers']
your_teams = my_teams
my_teams[0] = 'Rams'
print(your_teams)
```

Output: `['Rams', 'Dodgers']`

<!--
your_teams never asked to change, and yet it did. That's because
your_teams = my_teams didn't copy any data -- it just handed your_teams a
reference to the exact same list object sitting in memory. Ask the room:
if my_teams were a list of sales_targets handed to two different
regions, what happens when one region edits their number? The other
region's copy silently changes too, because there was only ever one list.
We'll fix that with a real copy shortly. First, a related trap worth
separating out on its own.
-->

---

## Reassigning a name vs. modifying the list

- `fav_color = colors[2]` binds `fav_color` to whatever value lived there
- Reassigning `fav_color` afterward never touches `colors`
- Only indexed assignment -- `colors[1] = 'yellow'` -- reaches the shared list
- Same is true of any list method called on `colors` itself

<!--
This is the flip side of the aliasing problem. Pulling a value out of a
list with indexing gives you a plain copy of that one value -- reassign
the variable you stored it in, and the original list never notices.
What does reach into the list is indexed assignment, or a method call
like append or sort, because those operate on the list object directly
rather than on a name pointing at it. Keep that distinction in your head
-- it's the difference between "I changed a variable" and "I changed the
data everyone else is looking at." Next, the rest of the method toolbox
beyond what chapter 3 already gave you.
-->

---

# 9.2 List methods

<!--
Chapter 3 already covered append, pop, and remove. We're not going to
walk every remaining method one at a time -- the notes carry the full
table for reference -- instead let's look at the ones most likely to
trip you up.
-->

---

## The rest of the toolbox

| Method | Description |
|-|-|
| `extend(x)` | Add every item in `x` to the end |
| `insert(i, x)` | Insert `x` before position `i` |
| `sort()` / `reverse()` | Rearrange in place |
| `index(x)` / `count(x)` | Locate or tally `x` |

All but `index()`/`count()` modify the list in place.

<!--
extend and insert add elements; sort and reverse rearrange what's
already there; index and count just report back a value without
touching the list at all. The one that catches almost everybody at least
once is extend versus append, so let's look at exactly why.
-->

---

## append() vs. extend() -- the one everyone mixes up

```python
# Lets add a whole batch of new hires to the roster, not one blob
roster = ['Ana', 'Ben']
roster.extend(['Cy', 'Dee'])
print(roster)
```

Output: `['Ana', 'Ben', 'Cy', 'Dee']`

<!--
Watch what happens if you swap extend for append here instead: roster
dot append of that same list would add the whole list as one new
element, giving you ['Ana', 'Ben', ['Cy', 'Dee']] -- a list nested inside
your roster, which is almost never what you wanted. extend unpacks its
argument and adds each item individually. Same word, "add," very
different result. Next, the patterns you'll reach for constantly once
you start looping over a list.
-->

---

# 9.3 Iterating over a list

<!--
You already know the for-loop shape from chapter 5. This section is
about the patterns that come up constantly once you're actually walking
real data: tracking something as you go, using the shortcuts Python
gives you for free, and getting the index alongside the value when you
need both.
-->

---

## Tracking a value while you loop

```python
# Lets find the largest even bonus in this payout batch
bonuses = [150, 225, 480, 96]
max_even = None
for b in bonuses:
    if b % 2 == 0 and (max_even is None or b > max_even):
        max_even = b
print(max_even)
```

Output: `480`

<!--
You can't just call max() here, because there's a condition to check
first -- only even bonuses count. That's the general shape of "walk
every element, remember something as you go." Notice the seed value is
None, not zero. Ask the room why that matters: if every bonus in the
batch happened to be negative, zero would look like a real answer even
though it was never actually in the list. None can't be confused with a
value that was genuinely seen. This exact pattern -- so common Python
built shortcuts for the easy cases -- is what we look at next.
-->

---

## Built-in shortcuts skip the loop entirely

| Function | Description |
|-|-|
| `sum(list)` | Total of all elements |
| `max(list)` / `min(list)` | Largest / smallest |
| `any(list)` / `all(list)` | True if any / every element is truthy |

`sum([-3, 5, 25])` -> `27`

<!--
When the thing you're tracking doesn't need a condition -- a plain total,
or the largest or smallest value outright -- don't write the loop
yourself. sum, max, min, any, and all cover the common cases in one
call. The bonus example a moment ago needed a hand-rolled loop only
because of that even-number condition; without it, max(bonuses) alone
would have done the job. Last pattern for this section: what to do when
you need the position of each element, not just its value.
-->

---

## Getting the index too

```python
# Lets number each item for a printed menu
items = ['Burger', 'Fries', 'Shake']
for index, item in enumerate(items):
    print(f'{index + 1}: {item}')
```

Output: `1: Burger`, `2: Fries`, `3: Shake`

<!--
A plain for loop only ever hands you the value, never its position. The
naive fix is a separate counter variable you increment by hand every
pass -- don't do that. enumerate wraps the list and hands you both the
index and the value together, the same tool you met back in chapter 5.
That covers the core loop patterns; now let's look at what happens when
a list holds other lists.
-->

---

<!-- _class: lead -->

# 9.5 List nesting

<!--
A list can hold any object type as an element, including another list.
Stacked up, that's how you represent a table or a spreadsheet without
pulling in any extra library -- and it's exactly the shape a lot of
business data already comes in.
-->

---

## A list of lists is a table

```python
# Lets store quarterly sales, one row per region
sales = [[120, 150, 90], [80, 95, 110]]
print(sales[0])
print(sales[0][2])
```

Output: `[120, 150, 90]` then `90`

<!--
The first bracket gets you an entire row -- the nested list. The second
bracket reaches inside that row for one actual number. Read it as
[row][column], always in that order, the same convention a spreadsheet
uses. That indexing habit is the whole trick; the only thing left is
touching every cell instead of just one.
-->

---

## Walking every cell with a nested loop

```python
# Lets print every region's quarterly numbers
sales = [[120, 150, 90], [80, 95, 110]]
for row in sales:
    for cell in row:
        print(cell, end=' ')
    print()
```

Output: `120 150 90` then `80 95 110`

<!--
The outer loop walks the rows; the inner loop walks each row's columns.
Nesting depth isn't capped -- a three-level structure is legal Python --
but two dimensions is where nearly all business data actually lives,
because that's the shape a spreadsheet or a database table already
takes. Next, a closer look at slicing, and the one slice that matters
more for lists than it did for strings.
-->

---

<!-- _class: lead -->

# 9.6–9.7 Slicing, copying, and loops that modify a list

<!--
Slicing a list works exactly like slicing a string -- same bounds, same
stride, same exclusive end index. What's different is what a slice with
no bounds at all buys you here, and what happens when a loop tries to
change the list it's walking. Both of today's bugs trace back to the
same root cause: not understanding what you're actually holding a
reference to.
-->

---

## Slicing works the same as strings

| Operation | Example | Result |
|-|-|-|
| `list[start:end]` | `[5,10,20][0:2]` | `[5, 10]` |
| `list[start:end:stride]` | `[5,10,20,40][0:4:2]` | `[5, 20]` |
| `list[:]` | `[5,10,20][:]` | `[5, 10, 20]` |

End index exclusive, same rules as string slicing.

<!--
If you've internalized string slicing from last chapter, this table is a
formality -- omitted bounds mean start or end, negative indices count
backward, a stride skips elements. The row that matters most today is
the last one: a slice with no start and no end at all. With a string
that just gives you an identical copy of an immutable value. With a
list, it does something genuinely useful.
-->

---

## The `[:]` copy -- a real second list

```python
# Lets give each region its own copy of the target list
sales_targets = [100, 150, 200]
region_b = sales_targets[:]
region_b[0] = 120
print(sales_targets)
```

Output: `[100, 150, 200]` -- unchanged

<!--
Recall the aliasing problem from 9.1 -- your_teams = my_teams shared one
object between two names. sales_targets[:] doesn't do that. Because a
list is mutable, slicing the whole thing builds a brand-new list object,
a genuine second copy, instead of another name pointing at the original.
That's your insurance policy any time you're handing the same starting
data off to two parts of a program that might each edit their own copy.
Now the other bug this pairing is named for: what happens when a loop
tries to change values in the list it's iterating over.
-->

---

## Changing values: the loop variable is a copy

```python
# WRONG: this never touches the real list
discounts = [5, 10, -5, -4]
for d in discounts:
    if d < 0:
        d = 0
print(discounts)
```

Output: `[5, 10, -5, -4]` -- unchanged ❌

<!--
for d in discounts hands you a fresh copy of each value every pass, not
a live connection back into the list. Reassigning d only moves that
local copy; the list itself never hears about it. This is the single
most common "my code ran with no error but did nothing" bug students
hit with lists. The fix is one small change -- index into the list
directly instead of reassigning the loop variable.
-->

---

## Fix: assign through the index

```python
# Lets zero out negative discounts for real this time
discounts = [5, 10, -5, -4]
for pos in range(len(discounts)):
    if discounts[pos] < 0:
        discounts[pos] = 0
print(discounts)
```

Output: `[5, 10, 0, 0]` ✅

<!--
Looping over range(len(discounts)) instead of the list itself hands you
positions, and discounts[pos] = 0 reaches straight into the real object
-- no throwaway copy involved. The notes cover a related trap: removing
elements while looping, which shifts everything after the removed item
and causes the loop to silently skip a value. The fix there is the same
family of idea -- loop over discounts[:], a snapshot copy, so deleting
from the real list never disturbs your position. Next, a much shorter
way to write the common case of building a new list from an old one.
-->

---

# 9.8 List comprehensions

<!--
Applying the same operation to every element and collecting the results
into a new list is common enough that Python gives it its own compact
syntax. It won't replace every for loop you write, but for this one
shape, it's shorter and it runs faster.
-->

---

## Build a new list in one line

```python
# Lets add a 5% raise to every salary
salaries = [50000, 62000, 48000]
raised = [round(s * 1.05) for s in salaries]
print(raised)
```

Output: `[52500, 65100, 50400]`

<!--
Read it left to right: expression first, then the loop that drives it,
all inside brackets. The brackets are your reminder this builds a
brand-new list -- it never touches salaries itself. Compare that to a
three-line for loop with an append call doing the identical job; the
comprehension is one line and the interpreter runs it more efficiently.
Comprehensions can also filter, which is where they earn their keep.
-->

---

## Add a condition to filter as you build

```python
# Lets keep only employees earning over 50k
salaries = [50000, 62000, 48000, 71000]
high_earners = [s for s in salaries if s > 50000]
print(high_earners)
```

Output: `[62000, 71000]`

<!--
Tack an if onto the end and the condition is checked once per element,
before that element is even considered for the result -- only the ones
that pass make it into the new list at all. This combination, transform
plus filter in one line, is the shape you'll write constantly once it's
in your hands. Next, two remaining tools that round out the list
toolkit: sorting on your own terms, and reading input from outside the
program entirely.
-->

---

# 9.9–9.10 Sorting lists and reading command-line arguments

<!--
Two last additions to the list toolkit before we move to dictionaries.
Sorting comes with two decisions every time -- do you want the original
list preserved, and what actually counts as "smaller"? And separately,
a program doesn't have to wait for input() -- values can arrive on the
command line the moment it launches.
-->

---

## sort() rearranges; sorted() leaves the original alone

```python
# Lets rank sales without losing the original order
sales = [4200, 3100, 5600, 2800]
ranked = sorted(sales, reverse=True)
print(sales)
print(ranked)
```

Output: `[4200, 3100, 5600, 2800]` then `[5600, 4200, 3100, 2800]`

<!--
sales.sort() would rearrange the existing list in place and hand back
None -- fine if you never need the original order again, a real problem
if you do. sorted() instead returns a brand-new sorted list and leaves
sales exactly as it was. reverse=True flips either one from
lowest-to-highest to highest-to-lowest. Preserving the original is
usually the safer default when you're not sure yet which one a report
needs. Sorting numbers is straightforward; sorting text takes one more
tool.
-->

---

## key= changes what counts as smallest

```python
# Lets sort a roster ignoring case
reps = ['Serena Williams', 'rafael Nadal', 'john McEnroe']
print(sorted(reps, key=str.lower))
```

Output: `['john McEnroe', 'rafael Nadal', 'Serena Williams']`

<!--
Sorted normally, every lowercase name lands after every uppercase one,
because a lowercase letter has a larger encoded value than any capital.
key=str.lower fixes that by comparing the lowercased version of each
name for ordering purposes only -- the names themselves never actually
change. key isn't limited to string methods either; it accepts any
function, which is how you'd sort a two-dimensional table by each row's
total. Now let's shift entirely -- a program getting its data before it
even starts running, off the command line.
-->

---

## Reading values off the command line

```python
import sys
# Lets greet whoever ran the script
name = sys.argv[1]
age = int(sys.argv[2])
print(f'Hello {name}, age {age}.')
```

Run as `python myprog.py Tricia 12` -> `Hello Tricia, age 12.`

<!--
sys.argv is a list, supplied by the standard library's sys module,
holding every piece of the command line as a string -- argv[0] is
always the script's own name, argv[1] the first real argument, and so
on. That int() wrapped around age isn't optional: every argument arrives
as a string, and skipping the conversion either errors on any math you
try or silently does string concatenation instead of addition. One more
habit before this becomes something you'd actually ship.
-->

---

## Check the count before you trust it

```python
import sys
if len(sys.argv) != 3:
    print('Usage: python myprog.py name age')
    sys.exit(1)
```

<!--
Index past the end of sys.argv and you get an IndexError and a stack
trace instead of a usable program -- not exactly professional if someone
else is running your script. Checking len(sys.argv) up front and
printing a usage message instead is a small habit that turns a crash
into a clear instruction. One note from the field: an argument with a
space in it, like a full name, needs quotes on the command line, or the
shell splits it into two arguments and throws off every index after it.
That closes out lists entirely. Let's pivot to dictionaries.
-->

# 9.12 Dictionaries

<!--
Chapter 3 gave you dictionary basics -- braces, key-value pairs, adding
and deleting entries. Here's a bit more on how they get built, and a
guarantee worth knowing: as of Python 3.7, dictionaries keep the order
you inserted items in. That's part of the language spec now, not an
implementation quirk you're lucky to get -- you can rely on it in a
report.
-->

---

## Building a dict beyond `{}`

```python
# Lets build the same contact list two different ways
contacts_a = dict(Bobby='805-555-2232', Johnny='951-555-0055')
contacts_b = {'Bobby': '805-555-2232', 'Johnny': '951-555-0055'}
print(contacts_a == contacts_b)
```

Output: `True`

<!--
Braces are the usual move, but dict() takes keyword arguments and
produces the identical dictionary -- it just reads a little differently
on the page. The keyword-argument form only works when your keys are
valid Python names, no spaces, can't start with a number, which is
exactly why it looks different from the brace syntax. Dictionary values
aren't limited to simple types either, which is where this gets useful.
-->

---

## A value can be any type, including another container

```python
# Lets store each student's list of grades
student_grades = {}
student_grades['Jason'] = ['B+', 'A-']
print(student_grades['Jason'])
```

Output: `['B+', 'A-']`

<!--
Nothing stops a dictionary value from being a list, or even another
dictionary -- we'll build on that in a few minutes with a full nested
record. For now, the takeaway is that a dict value is exactly as
flexible as any other Python variable. Here's the quick reference for
the core operations you'll use every day.
-->

---

## The common operations

| Operation | Description |
|-|-|
| `my_dict[key]` | Get the value for `key` |
| `my_dict[key] = value` | Add or overwrite an entry |
| `del my_dict[key]` | Remove the entry for `key` |
| `key in my_dict` | Check whether `key` exists |

<!--
This table is the workhorse of everyday dictionary use, and it should
already feel familiar from chapter 3. What's new is the method set
built on top of it -- merging two dictionaries, clearing one out, and
reading a key that might not even exist without crashing. That's next.
-->

---

# 9.13–9.14 Dictionary methods and iteration

<!--
Beyond indexing and del, the dict type ships its own methods for
merging, clearing, and safe reads, plus the tools for actually looping
through one properly. These two sections are really one skill --
working through a dictionary's contents -- so we'll take them together.
-->

---

## Methods for merging, clearing, and reading safely

| Method | Description |
|-|-|
| `clear()` | Remove everything |
| `get(key, default)` | Read, or return `default` if missing |
| `update(other)` | Merge another dict in |
| `pop(key, default)` | Remove and return a value |

All but `get()` modify the dictionary in place.

<!--
update is how you'd merge a new batch of survey responses into an
existing tally -- shared keys get overwritten by whatever's in the
argument. pop removes and hands back a value in one step. get is the odd
one out, and the one worth a slide of its own, because it's what saves
you from the single most common dictionary crash.
-->

---

## get() never crashes on a missing key

```python
# Lets look up a price without risking a KeyError
prices = dict(bananas=1.59, fries=2.39)
print(prices.get('burger', 0))
print(prices.get('fries', 0))
```

Output: `0` then `2.39`

<!--
Indexing a dict with a key that doesn't exist -- prices['burger'] --
raises a KeyError and kills the program. get() never does; it just
hands back whatever default you specify, here a plain 0. Anywhere you're
reading a dictionary built from user input or an external file, where
you can't guarantee every key you'll ask for actually exists, get() is
the safer default. Now, looping through a dictionary properly.
-->

---

## A plain loop hands you the keys

```python
# Lets list every product we track
calories = dict(Coke=90, Coke_zero=0, Pepsi=94)
for soda in calories:
    print(soda)
```

Output: `Coke`, `Coke_zero`, `Pepsi`

<!--
A bare for loop over a dictionary only ever gives you the keys, in
insertion order, since that's guaranteed now. That's fine when the keys
are all you need -- but most of the time you want the value that goes
with each one too, which is where items() comes in.
-->

---

## items() hands you the key and the value together

```python
# Lets print each product with its calorie count
calories = dict(Coke=90, Coke_zero=0, Pepsi=94)
for soda, cal in calories.items():
    print(f'{soda}: {cal}')
```

Output: `Coke: 90`, `Coke_zero: 0`, `Pepsi: 94`

<!--
items() yields each key-value pair as a tuple, and unpacking it directly
into soda and cal in the for statement gets you both in a single loop --
the same trick enumerate used for index and value back in 9.3. keys()
and values() exist too for when you only need one side; the notes cover
all three. That wraps up working through a dictionary. Last stop:
dictionaries holding other dictionaries, which is how real business
records actually take shape.
-->

---

# 9.15 Dictionary nesting

<!--
Same idea as list nesting from 9.5, but for dictionaries -- a value can
be another dictionary. This is one of the most useful shapes you'll
build in business data work, because it mirrors how a real record
looks: a name maps to a record, and the record itself has several
fields.
-->

---

## A dictionary value can be another dictionary

```python
# Lets store each student's record as a nested dict
students = {}
students['Jose'] = {'Grade': 'A+', 'StudentID': 22321}
print(students['Jose']['Grade'])
```

Output: `A+`

<!--
Each set of brackets steps down one level. students['Jose'] gets you the
inner dictionary; adding ['Grade'] reaches into that inner dictionary
for the actual value. You could store the same data as a list at some
fixed position instead, but then you'd have to remember that position 0
always means grade -- a dictionary key like 'Grade' documents itself.
Let's build a slightly fuller record to see why that matters in
practice.
-->

---

## A gradebook, the way real records look

```python
grades = {'Ricky Bobby': {'Homeworks': [50, 52, 78],
                           'Midterm': 40, 'Final': 65}}
student = grades['Ricky Bobby']
total = sum(student['Homeworks']) + student['Midterm'] + student['Final']
print(f'Total points: {total}')
```

Output: `Total points: 235`

<!--
This is the shape an API response or a database row actually comes back
in -- a name mapping to a record, and the record itself mixing a list
value with plain numeric ones. Nesting depth isn't capped -- a fourth or
fifth level is legal Python -- but each extra level is another set of
brackets a reader has to track, and two or three levels is the practical
ceiling before a different structure starts making more sense. That
covers both containers, past the basics.
-->
