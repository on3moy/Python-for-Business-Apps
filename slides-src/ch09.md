# 9.1–9.2 Lists and their methods

<!--
One habit matters more than any other as your programs grow: knowing
when you're modifying a list in place versus just handing out a second
name for the same object. Get this wrong and you'll ship a bug that only
shows up when two parts of your program share data they shouldn't.

Then the rest of the method toolbox. Chapter 3 already covered append,
pop, and remove, so we'll spend our time on the ones most likely to trip
you up rather than reading the full table -- that lives in the notes.
-->

---

## One list, two names

```python
# Lets hand a roster off to another department
my_teams = ['Lakers', 'Dodgers']
your_teams = my_teams
my_teams[0] = 'Rams'
print(your_teams)
```

Output: `['Rams', 'Dodgers']`

<!--
your_teams never asked to change, and yet it did. That's because
your_teams = my_teams didn't copy any data -- it just handed your_teams a
reference to the exact same list object sitting in memory.

Ask the room: if my_teams were a list of sales_targets handed to two
different regions, what happens when one region edits their number? The
other region's copy silently changes too, because there was only ever one
list. Let them sit with that for a second before you move on -- this is
the trap the whole first half of the chapter is built around.

We'll fix it with a real copy shortly. First, a related trap worth
separating out on its own.
-->

---

## Reassigning a name vs. modifying the list

- `fav_color = colors[2]` binds `fav_color` to whatever value lived there
- Reassigning `fav_color` afterward never touches `colors`
- Only indexed assignment -- `colors[1] = 'yellow'` -- reaches the shared list
- Same is true of any list method called on `colors` itself

<!--
This is the flip side of the aliasing problem. Pulling a value out of a
list with indexing gives you a plain copy of that one value -- reassign
the variable you stored it in, and the original list never notices.

What does reach into the list is indexed assignment, or a method call
like append or sort, because those operate on the list object directly
rather than on a name pointing at it.

Keep that distinction in your head -- it's the difference between "I
changed a variable" and "I changed the data everyone else is looking at."
If they remember one sentence from this section, that is the one.

Next, the rest of the method toolbox beyond what chapter 3 gave you.
-->

---

## The rest of the toolbox

| Method | Description |
|-|-|
| `extend(x)` | Add every item in `x` to the end |
| `insert(i, x)` | Insert `x` before position `i` |
| `sort()` / `reverse()` | Rearrange in place |
| `index(x)` / `count(x)` | Locate or tally `x` |

All but `index()`/`count()` modify the list in place.

<!--
Do not read this table aloud row by row. Group it instead: extend and
insert add elements, sort and reverse rearrange what's already there, and
index and count just report back a value without touching the list at
all.

That last grouping is the one that matters, and it is the caption line --
almost everything here mutates in place, which means it changes the data
every other name pointing at that list can see. Connect it straight back
to the aliasing slide.

The one that catches almost everybody at least once is extend versus
append, so let's look at exactly why.
-->

---

## `append()` vs. `extend()` — the one everyone mixes up

```python
# Lets add a whole batch of new hires to the roster, not one blob
roster = ['Ana', 'Ben']
roster.extend(['Cy', 'Dee'])
print(roster)
```

Output: `['Ana', 'Ben', 'Cy', 'Dee']`

<!--
Ask them to predict the output of the append version before you reveal
anything. It is a genuinely good five-second exercise and the wrong
answer is instructive.

roster.append of that same list would add the whole list as one new
element, giving you ['Ana', 'Ben', ['Cy', 'Dee']] -- a list nested inside
your roster, which is almost never what you wanted. extend unpacks its
argument and adds each item individually.

Same word in English, "add." Very different result. Worth demoing both
live in the notebook and printing len(roster) after each -- 4 versus 3
makes the difference concrete in a way the brackets alone don't.

Next, the patterns you'll reach for constantly once you start looping
over a list.
-->

# 9.3–9.5 Looping and nesting

<!--
You already know the for-loop shape from chapter 5. This section is about
the patterns that come up constantly once you're actually walking real
data: tracking something as you go, and the shortcuts Python gives you
for free.

Then nesting -- a list can hold any object type as an element, including
another list. Stacked up, that's how you represent a table or a
spreadsheet without pulling in any extra library, and it's exactly the
shape a lot of business data already comes in.
-->

---

## Tracking a value while you loop

```python
# Lets find the largest even bonus in this payout batch
bonuses = [150, 225, 480, 96]
max_even = None
for b in bonuses:
    if b % 2 == 0 and (max_even is None or b > max_even):
        max_even = b
print(max_even)
```

<!--
You can't just call max() here, because there's a condition to check
first -- only even bonuses count. That's the general shape of "walk every
element, remember something as you go."

Notice the seed value is None, not zero. Ask the room why that matters:
if every bonus in the batch happened to be negative, zero would look like
a real answer even though it was never actually in the list. None can't
be confused with a value that was genuinely seen. That is a real bug
students ship, not a style preference.

One related tool to mention but not slide: if you need each element's
position as well as its value, enumerate() -- which you met in chapter
5.12 -- is still the right answer here. Don't hand-roll a counter
variable you increment yourself.

This pattern is so common that Python built shortcuts for the easy cases,
which is what we look at next.
-->

---

## Built-in shortcuts skip the loop entirely

| Function | Description |
|-|-|
| `sum(list)` | Total of all elements |
| `max(list)` / `min(list)` | Largest / smallest |
| `any(list)` / `all(list)` | True if any / every element is truthy |

`sum([-3, 5, 25])` → `27`

<!--
When the thing you're tracking doesn't need a condition -- a plain total,
or the largest or smallest value outright -- don't write the loop
yourself.

Point back at the previous slide explicitly: the bonus example needed a
hand-rolled loop only because of that even-number condition. Without it,
max(bonuses) alone would have done the whole job in one call. The lesson
is to check whether a built-in already covers your case before you write
five lines.

any and all are the two they won't have met before. any is True if at
least one element is truthy, all is True only if every one is -- both are
worth one sentence and a pointer to the notes.

Now let's look at what happens when a list holds other lists.
-->

---

## A list of lists is a table

```python
# Lets store quarterly sales, one row per region
sales = [[120, 150, 90], [80, 95, 110]]
print(sales[0])
print(sales[0][2])
```

Output: `[120, 150, 90]` then `90`

<!--
The first bracket gets you an entire row -- the nested list. The second
bracket reaches inside that row for one actual number.

Read it as [row][column], always in that order, the same convention a
spreadsheet uses. Say that phrase out loud twice; the bracket order is
the only thing that trips people here, and having the words "row,
column" attached to it fixes it.

Draw the two-by-three grid on the board and point at the cell that
sales[0][2] lands on. Thirty seconds of drawing saves five minutes of
confusion later.

That indexing habit is the whole trick; the only thing left is touching
every cell instead of just one.
-->

---

## Walking every cell with a nested loop

```python
# Lets print every region's quarterly numbers
sales = [[120, 150, 90], [80, 95, 110]]
for row in sales:
    for cell in row:
        print(cell, end=' ')
    print()
```

Output: `120 150 90` then `80 95 110`

<!--
The outer loop walks the rows; the inner loop walks each row's columns.
Trace one full pass out loud -- outer picks row one, inner prints three
numbers, the bare print() ends the line, then outer picks row two.

That lone print() after the inner loop is the detail worth pausing on. It
is indented with the outer loop, not the inner one, and that is what puts
each region on its own line. Move it one level in and the whole table
collapses onto a single line -- worth demoing live because it is a
one-character fix for a confusing-looking bug.

Nesting depth isn't capped -- a three-level structure is legal Python --
but two dimensions is where nearly all business data actually lives,
because that's the shape a spreadsheet or a database table already takes.
-->

# 9.6–9.8 Copying, modifying, and comprehensions

<!--
Slicing a list works exactly like slicing a string -- same bounds, same
stride, same exclusive end index -- so we are not going to re-teach that
table. It's in the notes if anyone wants it.

What's different is what a slice with no bounds at all buys you here, and
what happens when a loop tries to change the list it's walking. Both of
today's bugs trace back to the same root cause: not understanding what
you're actually holding a reference to. Then comprehensions, which are
the compact way to write the most common list-building loop there is.
-->

---

## The `[:]` copy — a real second list

```python
# Lets give each region its own copy of the target list
sales_targets = [100, 150, 200]
region_b = sales_targets[:]
region_b[0] = 120
print(sales_targets)
```

Output: `[100, 150, 200]` — unchanged

<!--
Call all the way back to the aliasing problem from the first section --
your_teams = my_teams shared one object between two names, and editing
one edited both. Put both slides side by side mentally for them.

sales_targets[:] doesn't do that. Because a list is mutable, slicing the
whole thing builds a brand-new list object, a genuine second copy,
instead of another name pointing at the original. The empty slice is
saying "give me everything, as a new list."

That's your insurance policy any time you're handing the same starting
data off to two parts of a program that might each edit their own copy.

Worth one sentence: this is a shallow copy. If the list contains other
lists, those inner lists are still shared. The notes cover it; most
business code never hits it.

Now the other bug this section is named for.
-->

---

## Changing values: assign through the index

```python
# Lets zero out negative discounts -- for real this time
discounts = [5, 10, -5, -4]
for pos in range(len(discounts)):
    if discounts[pos] < 0:
        discounts[pos] = 0
print(discounts)
```

Output: `[5, 10, 0, 0]` ✅

<!--
Show the broken version first, live, before you advance to this slide.
Write `for d in discounts:` with `d = 0` inside, run it, and let them see
the list come back completely unchanged with no error at all.

That is the single most common "my code ran fine but did nothing" bug
students hit with lists. `for d in discounts` hands you a fresh copy of
each value every pass, not a live connection back into the list.
Reassigning d only moves that local copy; the list never hears about it.

The fix on this slide is one small change: loop over range(len(...)) so
you're holding positions, and discounts[pos] = 0 reaches straight into
the real object -- no throwaway copy involved.

Related trap in the notes, worth naming out loud: removing elements while
looping shifts everything after the removed item and makes the loop
silently skip a value. Same family of fix -- iterate over discounts[:], a
snapshot copy, so deleting from the real list never disturbs your
position.
-->

---

## Build a new list in one line

```python
# Lets add a 5% raise to every salary
salaries = [50000, 62000, 48000]
raised = [round(s * 1.05) for s in salaries]
print(raised)
```

Output: `[52500, 65100, 50400]`

<!--
Read it left to right: expression first, then the loop that drives it,
all inside brackets. Say it as a sentence -- "round s times 1.05, for
each s in salaries" -- because that word order is exactly the syntax.

The brackets are your reminder this builds a brand-new list; it never
touches salaries itself. Compare it out loud to the three-line for loop
with an append call doing the identical job. Same result, one line, and
the interpreter runs it more efficiently.

Do write the long version on the board next to it once. Students who
learn comprehensions without ever seeing the loop they replace tend to
use them where a plain loop would read better.

Comprehensions can also filter, which is where they earn their keep.
-->

---

## Add a condition to filter as you build

```python
# Lets keep only employees earning over 50k
salaries = [50000, 62000, 48000, 71000]
high_earners = [s for s in salaries if s > 50000]
print(high_earners)
```

Output: `[62000, 71000]`

<!--
Tack an if onto the end and the condition is checked once per element,
before that element is even considered for the result -- only the ones
that pass make it into the new list at all.

Point out that 50000 is absent from the output. The condition is strictly
greater-than, and someone always asks. Better to answer it before they
do.

This combination -- transform plus filter in one line -- is the shape
you'll write constantly once it's in your hands. It is also the single
most common thing you will see in real pandas-adjacent Python, so it is
worth being fluent in.

Next, two remaining tools that round out the list toolkit.
-->

# 9.9–9.10 Sorting and command-line arguments

<!--
Two last additions to the list toolkit before we move to dictionaries.

Sorting comes with two decisions every time: do you want the original
list preserved, and what actually counts as "smaller"? And separately, a
program doesn't have to wait for input() -- values can arrive on the
command line the moment it launches.
-->

---

## `sort()` rearranges; `sorted()` leaves the original alone

```python
# Lets rank sales without losing the original order
sales = [4200, 3100, 5600, 2800]
ranked = sorted(sales, reverse=True)
print(sales)
print(ranked)
```

Output: `[4200, 3100, 5600, 2800]` then `[5600, 4200, 3100, 2800]`

<!--
sales.sort() would rearrange the existing list in place and hand back
None -- fine if you never need the original order again, a real problem
if you do.

That None is worth calling out as a live demo: `ranked = sales.sort()`
looks completely reasonable and leaves ranked holding None. It is the
same missing-return shape they met in chapter 6, and it will bite at
least one person on the homework.

sorted() instead returns a brand-new sorted list and leaves sales exactly
as it was. reverse=True flips either one from lowest-to-highest to
highest-to-lowest.

Preserving the original is usually the safer default when you're not sure
yet which one a report needs. Sorting numbers is straightforward; sorting
text takes one more tool.
-->

---

## `key=` changes what counts as smallest

```python
# Lets sort a roster ignoring case
reps = ['Serena Williams', 'rafael Nadal', 'john McEnroe']
print(sorted(reps, key=str.lower))
```

Output: `['john McEnroe', 'rafael Nadal', 'Serena Williams']`

<!--
Sorted normally, every lowercase name lands after every uppercase one,
because a lowercase letter has a larger encoded value than any capital.
That's the same ASCII ordering rule from chapter 8 -- worth a one-line
callback, they have seen 'Banana' < 'apple' already.

key=str.lower fixes it by comparing the lowercased version of each name
for ordering purposes only. The names themselves never actually change,
which is the part people misread -- the output still has the original
capitalization.

Notice there are no parentheses after str.lower. You're handing sorted()
the function itself, not calling it -- exactly the "functions are
objects" idea from chapter 6.8. That callback is worth making explicitly;
it's the first time it pays off.

key accepts any function, which is how you'd sort a two-dimensional table
by each row's total.
-->

---

## Reading values off the command line

```python
import sys
# Lets greet whoever ran the script, safely
if len(sys.argv) != 3:
    sys.exit('Usage: python myprog.py name age')
name, age = sys.argv[1], int(sys.argv[2])
print(f'Hello {name}, age {age}.')
```

Run as `python myprog.py Tricia 12` → `Hello Tricia, age 12.`

<!--
sys.argv is a list holding every piece of the command line as a string.
argv[0] is always the script's own name, argv[1] the first real argument,
and so on -- so the count check is 3, not 2, and that off-by-one is worth
pointing at directly.

Two habits are baked into this one slide. First, that int() around age
isn't optional: every argument arrives as a string, and skipping the
conversion either errors on any math you try or silently concatenates
instead of adding.

Second, check the length before you index. Reaching past the end of
sys.argv gets you an IndexError and a stack trace instead of a usable
program -- not exactly professional if someone else is running your
script. A usage message turns a crash into an instruction.

From the field: an argument with a space in it, like a full name, needs
quotes on the command line, or the shell splits it into two arguments and
throws off every index after it.

That closes out lists entirely. Let's pivot to dictionaries.
-->

# 9.12–9.13 Dictionaries

<!--
Chapter 3 gave you dictionary basics -- braces, key-value pairs, adding
and deleting entries. Here's a bit more on how they get built, what can
go in them, and how to read one without crashing.

One guarantee worth stating up front: as of Python 3.7, dictionaries keep
the order you inserted items in. That's part of the language spec now,
not an implementation quirk you're lucky to get -- you can rely on it in
a report.
-->

---

## Building a dict beyond `{}`

```python
# Lets build the same contact list two different ways
contacts_a = dict(Bobby='805-555-2232', Johnny='951-555-0055')
contacts_b = {'Bobby': '805-555-2232', 'Johnny': '951-555-0055'}
print(contacts_a == contacts_b)
```

Output: `True`

<!--
Braces are the usual move, but dict() takes keyword arguments and
produces the identical dictionary -- it just reads a little differently
on the page.

Connect it to chapter 6: those really are keyword arguments, the same
mechanism from 6.13. Which immediately explains the limitation -- the
keyword form only works when your keys are valid Python names. No spaces,
can't start with a number. A key like 'Q3 Revenue' has to use braces.

That's why you see both forms in real code, and why the brace form is the
safer default for data that came from outside your program.
-->

---

## A value can be any type, including another container

```python
# Lets store each student's list of grades
student_grades = {}
student_grades['Jason'] = ['B+', 'A-']
print(student_grades['Jason'])
```

Output: `['B+', 'A-']`

<!--
Nothing stops a dictionary value from being a list, or even another
dictionary -- we'll build on that at the end of the hour with a full
nested record.

The rule to state: keys are restricted, values are not. A key has to be
immutable -- a string, a number, a tuple -- which is why you can't use a
list as a key. A value is exactly as flexible as any other Python
variable.

That asymmetry is worth one sentence because the error you get from
trying to use a list as a key ("unhashable type") is genuinely cryptic
the first time.
-->

---

## `get()` never crashes on a missing key

```python
# Lets look up a price without risking a KeyError
prices = dict(bananas=1.59, fries=2.39)
print(prices.get('burger', 0))
print(prices.get('fries', 0))
```

Output: `0` then `2.39`

<!--
First, spend a minute on the everyday operations without a slide, because
chapter 3 already taught them: my_dict[key] reads, my_dict[key] = value
both adds and silently overwrites, del removes, and `key in my_dict`
checks KEYS, never values -- that last one catches people who expect `in`
to search values the way it does on a list.

The method set on top of that is in the notes: clear() empties it,
update(other) merges another dictionary in with shared keys overwritten,
pop(key) removes and returns in one step. Name them, don't slide them.

One method does earn its own slide, and this is it.

Indexing a dict with a key that doesn't exist -- prices['burger'] --
raises a KeyError and kills the program. Demo that first so the contrast
lands; the traceback is the whole motivation for this slide.

get() never does that. It hands back whatever default you specify, here a
plain 0. Leave the default off entirely and you get None instead, which
is worth knowing but is usually less useful than a real zero.

Anywhere you're reading a dictionary built from user input or an external
file -- anywhere you can't guarantee every key you ask for exists --
get() is the safer default.

The judgment call to voice: a KeyError is loud and immediate, which is
sometimes exactly what you want. get() is for when a missing key is a
normal, expected situation, not a bug.

Now, looping through a dictionary properly.
-->

# 9.14–9.15 Looping and nesting dictionaries

<!--
Two things left. How to actually walk a dictionary's contents, and then
dictionaries holding other dictionaries -- which is how real business

---

## Looping gives you keys; `items()` gives you both

```python
# Lets print each product with its calorie count
calories = dict(Coke=90, Coke_zero=0, Pepsi=94)
for soda, cal in calories.items():
    print(f'{soda}: {cal}')
```

Output: `Coke: 90`, `Coke_zero: 0`, `Pepsi: 94`

<!--
Start with the bare version live: `for soda in calories:` prints only the
keys -- Coke, Coke_zero, Pepsi -- in insertion order, since that's
guaranteed now. That surprises people who expect the values, so show it
before you show this slide's version.

That's fine when the keys are all you need. Most of the time you want the
value that goes with each one too, and that's items().

items() yields each key-value pair as a tuple, and unpacking it directly
into soda and cal in the for statement gets you both in a single loop --
the same unpacking trick enumerate used for index and value back in
chapter 5, and the same one multiple return values used in chapter 6.15.
Third time they've seen it; name that.

keys() and values() exist too for when you only need one side. The notes
cover all three.

Last stop: dictionaries holding other dictionaries.
-->

---

## A dictionary value can be another dictionary

```python
# Lets store each student's record as a nested dict
students = {}
students['Jose'] = {'Grade': 'A+', 'StudentID': 22321}
print(students['Jose']['Grade'])
```

Output: `A+`

<!--
Same idea as list nesting earlier, but for dictionaries. Each set of
brackets steps down exactly one level: students['Jose'] gets you the
inner dictionary, and adding ['Grade'] reaches into that inner dictionary
for the actual value.

Demo the half-step -- print students['Jose'] on its own first, so they
see the whole inner dictionary come back before you index into it. Two
lines of bracket-chaining is much less mysterious once you've seen the
intermediate value.

The argument for dictionaries over lists here: you could store the same
record as a list and remember that position 0 always means grade. A key
named 'Grade' documents itself, and nobody has to remember anything.

Let's build a fuller record to see why that matters in practice.
-->

---

## A gradebook, the way real records look

```python
grades = {'Ricky Bobby': {'Homeworks': [50, 52, 78],
                           'Midterm': 40, 'Final': 65}}
student = grades['Ricky Bobby']
total = sum(student['Homeworks']) + student['Midterm'] + student['Final']
print(f'Total points: {total}')
```

Output: `Total points: 235`

<!--
This is the shape an API response or a database row actually comes back
in -- a name mapping to a record, and the record itself mixing a list
value with plain numeric ones.

The line worth pointing at is `student = grades['Ricky Bobby']`. Pulling
the inner dictionary into its own named variable first is what keeps the
total line readable. The alternative is four separate
grades['Ricky Bobby'][...] chains on one line, which nobody can read. That
is a genuine style lesson, not just a convenience.

Note the sum() call handling the list value while the other two are read
directly. Different value types in one record, each handled the way its
own type needs -- that's the whole point of the structure.

Nesting depth isn't capped, but each extra level is another set of
brackets a reader has to track. Two or three levels is the practical
ceiling before a different structure starts making more sense.
-->
