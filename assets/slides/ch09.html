Two last additions to the list toolkit before we move to dictionaries. Sorting comes with two decisions every time: do you want the original list preserved, and what actually counts as "smaller"? And separately, a program doesn't have to wait for input() -- values can arrive on the command line the moment it launches.

sales.sort() would rearrange the existing list in place and hand back None -- fine if you never need the original order again, a real problem if you do. That None is worth calling out as a live demo: `ranked = sales.sort()` looks completely reasonable and leaves ranked holding None. It is the same missing-return shape they met in chapter 6, and it will bite at least one person on the homework. sorted() instead returns a brand-new sorted list and leaves sales exactly as it was. reverse=True flips either one from lowest-to-highest to highest-to-lowest. Preserving the original is usually the safer default when you're not sure yet which one a report needs. Sorting numbers is straightforward; sorting text takes one more tool.

Sorted normally, every lowercase name lands after every uppercase one, because a lowercase letter has a larger encoded value than any capital. That's the same ASCII ordering rule from chapter 8 -- worth a one-line callback, they have seen 'Banana' < 'apple' already. key=str.lower fixes it by comparing the lowercased version of each name for ordering purposes only. The names themselves never actually change, which is the part people misread -- the output still has the original capitalization. Notice there are no parentheses after str.lower. You're handing sorted() the function itself, not calling it -- exactly the "functions are objects" idea from chapter 6.8. That callback is worth making explicitly; it's the first time it pays off. key accepts any function, which is how you'd sort a two-dimensional table by each row's total.

sys.argv is a list holding every piece of the command line as a string. argv[0] is always the script's own name, argv[1] the first real argument, and so on -- so the count check is 3, not 2, and that off-by-one is worth pointing at directly. Two habits are baked into this one slide. First, that int() around age isn't optional: every argument arrives as a string, and skipping the conversion either errors on any math you try or silently concatenates instead of adding. Second, check the length before you index. Reaching past the end of sys.argv gets you an IndexError and a stack trace instead of a usable program -- not exactly professional if someone else is running your script. A usage message turns a crash into an instruction. From the field: an argument with a space in it, like a full name, needs quotes on the command line, or the shell splits it into two arguments and throws off every index after it. Chapter 3 gave you dictionary basics -- braces, key-value pairs, adding and deleting entries. Here's a bit more on how they get built, what can go in them, and how to read one without crashing. One guarantee worth stating up front: as of Python 3.7, dictionaries keep the order you inserted items in. That's part of the language spec now, not an implementation quirk you're lucky to get -- you can rely on it in a report.

Braces are the usual move, but dict() takes keyword arguments and produces the identical dictionary -- it just reads a little differently on the page. Connect it to chapter 6: those really are keyword arguments, the same mechanism from 6.13. Which immediately explains the limitation -- the keyword form only works when your keys are valid Python names. No spaces, can't start with a number. A key like 'Q3 Revenue' has to use braces. That's why you see both forms in real code, and why the brace form is the safer default for data that came from outside your program.

Nothing stops a dictionary value from being a list, or even another dictionary -- we'll build on that at the end of the hour with a full nested record. The rule to state: keys are restricted, values are not. A key has to be immutable -- a string, a number, a tuple -- which is why you can't use a list as a key. A value is exactly as flexible as any other Python variable. That asymmetry is worth one sentence because the error you get from trying to use a list as a key ("unhashable type") is genuinely cryptic the first time.

First, spend a minute on the everyday operations without a slide, because chapter 3 already taught them: my_dict[key] reads, my_dict[key] = value both adds and silently overwrites, del removes, and `key in my_dict` checks KEYS, never values -- that last one catches people who expect `in` to search values the way it does on a list. The method set on top of that is in the notes: clear() empties it, update(other) merges another dictionary in with shared keys overwritten, pop(key) removes and returns in one step. Name them, don't slide them. One method does earn its own slide, and this is it. Indexing a dict with a key that doesn't exist -- prices['burger'] -- raises a KeyError and kills the program. Demo that first so the contrast lands; the traceback is the whole motivation for this slide. get() never does that. It hands back whatever default you specify, here a plain 0. Leave the default off entirely and you get None instead, which is worth knowing but is usually less useful than a real zero. Anywhere you're reading a dictionary built from user input or an external file -- anywhere you can't guarantee every key you ask for exists -- get() is the safer default. The judgment call to voice: a KeyError is loud and immediate, which is sometimes exactly what you want. get() is for when a missing key is a normal, expected situation, not a bug.
