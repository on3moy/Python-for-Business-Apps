# 10.8 Class customization

Print an instance without doing anything extra and you get something like `<__main__.Toy instance at 0xb74cb98c>` — not exactly useful. This is where the special method names from [instance methods](10.3-instance-methods.md) start earning their keep — Python calls them automatically for common operations like printing and comparing.  

## \_\_str\_\_ for printing

```
class Toy:
    def __init__(self, name, price, min_age):
        self.name = name
        self.price = price
        self.min_age = min_age

    def __str__(self):
        return f'{self.name} costs only ${self.price:.2f}. Not for children under {self.min_age}!'

truck = Toy('Monster Truck XX', 14.99, 5)
print(truck)
```

Output:
`Monster Truck XX costs only $14.99. Not for children under 5!`

The instant `print(truck)` runs, Python calls `truck.__str__()` for you and prints whatever string comes back. You never call `__str__()` yourself.  

## Operator overloading

**operator overloading:**
Redefining what a built-in operator like `<`, `==`, or `+` does when used with instances of your class.  

```
class Time:
    def __init__(self, hours, minutes):
        self.hours = hours
        self.minutes = minutes

    def __str__(self):
        return f'{self.hours}:{self.minutes:02d}'

    def __lt__(self, other):
        if self.hours < other.hours:
            return True
        elif self.hours == other.hours:
            return self.minutes < other.minutes
        return False

times = [Time(10, 40), Time(12, 15), Time(9, 15)]

min_time = times[0]
for t in times:
    if t < min_time:
        min_time = t

print(f'Earliest time is {min_time}')
```

Output:
`Earliest time is 9:15`

The comparison `t < min_time` silently calls `t.__lt__(min_time)` — `self` is the left operand, `other` is the right one. Return `True` or `False` and the operator just works, the same way it would for two numbers.  

|Rich comparison method|Overloaded operator|
|-|-|
|`__lt__(self, other)`|less than (`<`)|
|`__le__(self, other)`|less than or equal to (`<=`)|
|`__gt__(self, other)`|greater than (`>`)|
|`__ge__(self, other)`|greater than or equal to (`>=`)|
|`__eq__(self, other)`|equal to (`==`)|
|`__ne__(self, other)`|not equal to (`!=`)|

??? question "Why would I ever want to overload an operator instead of writing a compare_to() method?"

    Because `t < min_time` reads better than `t.compare_to(min_time) < 0`, and it lets your objects drop straight into things that already expect `<` to work — `sorted()`, `min()`, `max()`. Once `__lt__` is defined, a whole ecosystem of built-in tools starts working on your class for free.  

!!! warning "Python can't stop you from misusing this"

    Nothing forces `__lt__` to actually implement "less than" — you could make it do anything, including something totally unrelated to comparison. Good practice is to only overload an operator when the resulting behavior would be obvious and unsurprising to someone reading `a < b` in your code. If it wouldn't be obvious, write a named method instead.
