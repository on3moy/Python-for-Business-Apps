# 2.1–2.2 Variables and identifiers

<!--
We open with the single most common line of code you will write all
semester: an assignment statement. Everything from here forward assumes you
are comfortable naming a value and retrieving it later.

Then we formalize exactly what counts as a legal name — the term of art is
"identifier" — and look at the names Python has already claimed for itself.
-->

---

## Naming a value

**Assignment statement:**
Evaluate the right-hand side, then bind the name on the left to that result.

```python
x = 13
JohnDoe = 55
```

Always name, then `=`, then the value.

<!--
A variable is nothing more than a label we attach to a value so we can refer
back to it. The equal sign here is not mathematical equality — it is an
instruction, and saying that out loud matters: evaluate the right side
first, then bind the name on the left to the result.

The pattern is rigid and worth stating plainly: name, equal sign, value.
Both examples follow it — a lowercase name and a capitalized one, both
perfectly legal.

Ask the room what they would name a variable holding an employee's salary.
Get two or three answers on the board — it sets up the naming conventions
slide nicely, and it gets people talking in the first five minutes.
-->

---

## Common mistakes

`5 = x` ❌ — the target must be a name, not a value
`x => 5` ❌ — Python has exactly one assignment operator, `=`
`1x = 5` ❌ — names can't start with a digit

<!--
Three failures, each worth naming individually.

Five equals x fails because the direction is backwards — the target of an
assignment must always be the name, not the value. The arrow fails because
Python has exactly one assignment operator, the equal sign, full stop. And
a name starting with a digit fails because of the identifier rule.

Say that rule now, since it explains the third one: an identifier is a
sequence of letters, underscores, and digits, and it must start with a
letter or an underscore. That is the entire rule.

One more thing worth a beat while we're here — Python is case sensitive.
Cat and cat are two entirely distinct names, not a typo Python quietly
corrects for you. Students coming from Excel or SQL, where case is often
forgiving, get caught by this.

Committing these to memory now saves you a dozen confusing error messages
later.
-->

---

## Naming styles

- `lower_case_with_underscores` — our default
- `UPPER_CASE` — constants
- `CapitalizedWords` — classes later in the semester
- `mixedCase` ⚠️ avoid unless already common in the script
- `Capitalized_Words_With_Underscores` ❌ ugly, don't

<!--
This is a preview of PEP 8, the community style guide for Python, and we
will return to it repeatedly as the semester goes on, so there is no need
to dwell here today.

The one habit worth building immediately is lower_case_with_underscores for
ordinary variables. It is what the rest of the Python ecosystem expects,
and consistent style is what makes code reviewable by someone other than
you six months from now.

Frame it as a professional courtesy rather than a rule: nobody will fail
you for mixedCase, but every Python developer who reads your code will
notice.
-->

---

## Don't overwrite Python's own words

```python
print = 13
sum = 13 + 23
```

Both ❌ — you just broke `print()` and `sum()` for the rest of your session.

<!--
This one is a live demo, not a lecture. Actually run print = 13 in a
notebook, then try to call print() afterward and watch it fail, because
print is no longer a function — it is now the integer 13. Then restart the
kernel to fix it.

It is a small, memorable scare early in the semester, and it makes the
abstract warning concrete: reserved names are not decoration, they are
load-bearing.

Then give them the self-service tool rather than a list to memorize. In a
notebook, `import keyword; keyword.kwlist` prints every reserved word, and
`dir(builtins)` prints every built-in name on top of that — several hundred
between them. We haven't formally covered import yet; that's section 2.8,
so tell them to trust it for now.

The habit I actually want: rather than memorizing what Python has claimed,
learn how to ask Python to tell you. That habit generalizes to every
library they will ever use.
-->

# 2.3 Objects

<!--
We now step back from syntax and ask a more fundamental question: what
actually happens in memory when we write an assignment statement?

The answer is objects — and this is the model that makes chapters 3, 6 and
9 make sense, so it is worth slowing down even though nothing here is
immediately practical.
-->

---

## Every value is an object

```python
x = 4
```

An object represents a value. The interpreter creates it, then binds the
name to it.

<!--
In Python, absolutely everything — integers, strings, functions, the lists
you will meet in chapter three — is represented internally as an object.

When this line executes, two things happen in sequence, and the order
matters: first the interpreter creates an object in memory to represent the
value 4, and only then does it bind the name x to that object. The name and
the value are two separate things, connected by this act of binding.

Here is the asymmetry to sit with: one object can answer to several names,
the way both "Bob" and "Robert" might refer to the same person. But each
individual name points to exactly one object at any given moment.

That single sentence is what makes the aliasing behavior in chapter 9 —
where two list names turn out to be the same list — completely predictable
instead of baffling. Plant it now and collect on it later.
-->

---

## Type is what decides what's legal

**Type:** the object's format — `int`, `str`, `float`

```python
print(type('13'))
print(type(13))
```

`'13'` and `13` look alike and are not remotely the same thing.

<!--
Every object carries three properties: a value, a type, and an identity.

Value is the intuitive one — it is simply the data the object holds, like
'Hi Im Baby' or 13. Name it and move on.

Type is the one that changes what your program can do. It is the object's
format — integer, string, float — and it determines which operations are
even legal. Thirteen in quotes and thirteen without look nearly identical
on the page and behave completely differently: one is text, one is a
number, and Python will not silently treat them the same way in arithmetic
or in comparisons.

Run both type() calls live. Then run '13' + 13 and let the TypeError land.
That error message is one they will see many times this semester, and
meeting it on purpose now is much better than meeting it by accident at
11pm.

type() is built in — no import needed, unlike the modules in 2.8.
-->

---

## Identity — the third property

```python
x = '🦖'
print(id(x))
```

A unique id assigned by the interpreter. Not permanent — garbage collection
can reassign a freed id later.

<!--
Identity is a unique number the interpreter assigns to each object, and you
retrieve it with the built-in id function — the third built-in we've met
now, alongside print and type.

Run it live against x, then bind a second name to the same object and show
that both report the identical id. That is the "one object, two names" idea
from two slides ago, made visible.

Unlike value and type, identity is not something to lean on. Python
automatically frees an object's memory once nothing refers to it — that's
garbage collection — and a later object may be handed that very same
number. Don't rely on identity surviving across a program run.

It is useful for exactly one thing: confirming whether two names point at
the same object right now. Which, again, is the chapter 9 setup.
-->

# 2.4–2.5 Numbers and arithmetic

<!--
With objects established as the underlying model, let's get concrete and
look at the numeric types we will use constantly — then the arithmetic that
ties them together.

The good news for the room: this half is arithmetic they already know. The
only genuinely new thing is which symbol Python uses.
-->

---

## Floats and integers

A **float literal** always shows its fractional part: `1.0`, `0.0`, `99.0`.

```python
float('13.5')
int('13')
```

Both convert if they can — neither can convert `'Hi'`.

<!--
A float is Python's type for real numbers, and the name comes from the
decimal point being free to "float" anywhere among the digits.

Notice the convention: even a whole-number float still displays its
fractional part, so 99.0 rather than bare 99. That trailing .0 is how you
tell at a glance you're looking at a float rather than an integer, and it
will matter in about four slides when division surprises them.

float() and int() attempt a conversion and raise an error rather than
silently guessing. Run float('Hi') live and let the traceback make the
point — this is the same conversion they'll wrap around input() all
semester.

Two things worth mentioning without slides. Scientific notation: 0.003 and
3.0e-3 are the same float, with a negative exponent shifting the decimal
left and a positive one shifting it right. And floats do have a ceiling —
around 1.0e308, past which you get an overflow error. In business code you
will essentially never hit it, but it's worth knowing the ceiling exists
rather than assuming Python's numbers are infinite.
-->

---

## Cleaning up the display

```python
print(f'{13.12345:.2f}')
```

Output: `13.12`

Nobody wants to read 13 decimal places in a report.

<!--
This f-string syntax is a preview of formatted strings, which we formalize
in chapter three. For now just recognize the pattern: colon, then a format
spec, here .2f meaning fixed-point with two decimal places.

They will use this on literally every dollar figure they print for the rest
of the course, so it is worth showing early even though the full treatment
comes later.

A warning for anyone with Excel muscle memory, and this one is worth
demoing because the failure is silent: commas are never allowed inside a
Python number literal. Writing 13,000 does not give you thirteen thousand.
It gives you a tuple — a completely different data structure — and no error
at all. That is a genuinely confusing bug the first time you hit it.
-->

---

## Arithmetic operators

| Operator | Meaning |
|-|-|
| `+` `-` | add, subtract (and unary negation) |
| `*` | multiply |
| `/` | divide |
| `**` | exponent |

<!--
This table covers the operators you already know from arithmetic. The
double asterisk for exponentiation is likely the only unfamiliar symbol,
since most calculators use a caret instead — and a caret in Python does
something else entirely, so that substitution fails silently rather than
erroring. Worth a warning.

The definition to state while this is up: an expression is any combination
of variables, literals, operators and parentheses that Python can reduce to
a single value — 2 * (x + 1) is an expression. That's the whole definition,
and it doesn't need its own slide.

Then run a few live and have the class call out the answer before you
execute: 1 + 0, 2 ** 4, (1 + 3) * (2 + 2). Flag that 5 // 2 and 4 % 2 are
coming in a few minutes and let them sit with a little curiosity rather
than explaining them here.
-->

---

## Order of operations

Same PEMDAS you already know:

1. `( )` parentheses
2. `**` exponent
3. unary `-`
4. `*` `/` `%` left to right
5. `+` `-` left to right

<!--
This is the same precedence hierarchy they learned as PEMDAS in algebra,
extended with two Python-specific wrinkles: unary negation sits just below
exponentiation, and modulo shares precedence with multiplication and
division.

One footnote worth saying but not sliding: exponentiation alone evaluates
right to left, so 2 ** 3 ** 2 is 2 ** 9, not 8 ** 2. Nobody should write
that without parentheses anyway, which is the actual lesson.

Ask the room to predict, out loud, what 2 + 3 * 4 evaluates to before you
run it. Most will get fourteen immediately — which is exactly the point.
This is arithmetic they already understand intuitively; Python is just
formalizing rules they use every day without naming them.

The professional habit to plant: when precedence is even slightly
ambiguous, add the parentheses. They cost nothing and they remove all doubt
for the next human reading it.
-->

# 2.6–2.7 Real expressions and division

<!--
Let's see arithmetic inside an actual, if small, program — and pick up the
shorthand for updating a variable in place.

Then division, which deserves its own close look, because Python gives you
three distinct flavors of it and choosing the right one matters.
-->

---

## A realistic expression

```python
down_payment = int(input('Enter down payment: '))
payment_per_month = int(input('Enter monthly payment: '))
num_months = int(input('Enter number of months: '))

total_cost = down_payment + (payment_per_month * num_months)
print(f'Total cost: ${total_cost:.2f}')
```

<!--
This is a small car-lease calculator, and it is worth running live with real
numbers — the class always has opinions about car payments, and that
engagement is useful this early in the semester.

Point at the three int() wrappers. input() always hands back a string, every
time, no exceptions. Leave the conversion off and the multiplication either
errors or silently repeats the string, which is a genuinely baffling result
to debug.

Then notice the parentheses around the multiplication are not strictly
required — multiplication already happens before addition. They are there
for the human reader. That is the habit from the previous slide, applied.

This program is input, process, output from chapter one, in five lines.
Name that structure out loud; it's the shape of nearly everything they'll
write this semester.
-->

---

## Compound operators

| Compound | Expands to |
|-|-|
| `age += 1` | `age = age + 1` |
| `age -= 1` | `age = age - 1` |
| `age *= 2` | `age = age * 2` |
| `age /= 2` | `age = age / 2` |
| `age %= 2` | `age = age % 2` |

<!--
Every one of these is pure shorthand. Nothing new is happening
semantically, only syntactically — each compound form expands to the exact
same statement typed out longhand.

Notice the pattern repeats identically across every arithmetic operator:
the operator, then equals, expanding to the variable reassigned to itself
combined with the right-hand operand. Once one of these clicks, all five
click. Say that — it saves people from trying to memorize five things.

My recommendation to the room: write the expanded version, age equals age
plus one, until the pattern is second nature, and only then switch to the
compact form.

You will live in compound operators once we hit loops in chapter five,
incrementing a counter on every pass. It is worth building the comfort now
while the stakes are low and there's no loop logic competing for your
attention.
-->

---

## `/` always hands back a float

Input: `4 / 2`
Output: `2.0`

Regular division returns a **float**, even when it divides evenly.

<!--
This is the detail that trips people up most often, and it is worth a full
stop.

Ordinary division with a single forward slash always returns a float, even
when the two operands divide perfectly evenly. Four divided by two is not
the integer two — it is 2.0. Run it live; the trailing .0 is the tell they
learned to spot a few slides ago.

Why it matters: if your downstream code expects a whole number — an index
into a list, a count of items, anything you'd feed to range() — regular
division alone will not give you that. Which is exactly why the next two
operators exist.

Ask the room what they'd expect 4 / 2 to print before you run it. Almost
everyone says 2. That small surprise is what makes the rule stick.
-->

---

## `//` and `%` — the quotient and the leftover

```python
# Lets split 5 invoices across 3 people
print(5 // 3)     # 1 each
print(5 % 3)      # 2 left over
```

Floor division truncates toward negative infinity — it does not round.

<!--
These two are a pair, and teaching them together is what makes them stick:
floor division hands you how many times it goes in, modulo hands you
exactly what floor division threw away.

Five divided by three is about 1.667. Floor division gives 1 — and say
"truncates," not "rounds," because with negative operands it moves toward
negative infinity rather than toward the nearest whole number. That's the
caveat line on the slide and it's worth one sentence, no more.

Modulo gives back the 2 that got discarded.

The business framings that land: modulo is how you test whether a number is
even, n % 2 == 0, which they will use constantly. And the invoice split in
the comment is the real-world shape — distributing a stack of work evenly
across a team and figuring out how many are left for whoever picks up the
slack.

Demo both against a negative number if anyone asks. Otherwise don't open
that door.
-->

# 2.8–2.10 Modules and the standard library

<!--
We now zoom out from single expressions to how code gets organized into
files — the difference between a script and a notebook, what a module
actually is, and how to reach into one.

Then we put it to use with two modules from Python's standard library that
you will reach for constantly.
-->

---

## `.py` or `.ipynb`?

- **`.py`** — plain script, run top to bottom by a person or a scheduler
- **`.ipynb`** — notebook, run cell by cell, better for exploring

Same language underneath. Two very different jobs.

<!--
Both are ways to save Python code, and the choice isn't about which is
"better" in the abstract — it depends entirely on the use case.

A .py file is a plain script, executed top to bottom from the command line,
from a scheduler, or from the play button in VS Code. A .ipynb notebook
breaks code into individually runnable cells, which makes it excellent for
exploration, iteration and visualization, but it is not designed to be
triggered by a server on a schedule.

Ask the room: if your company runs a nightly job on a server, which do you
reach for? The answer is .py — schedulers execute scripts, not notebooks.

Then the flip side: if you're doing exploratory analysis on Databricks or
Azure Notebooks, platforms many of you will meet in industry, you'll live
in .ipynb most of the day.

We use notebooks in this class because we're learning, not because
notebooks are the professional default.
-->

---

## A module is just a `.py` file you reuse

```python
import MyFirstFunction

MyFirstFunction.bmi_calculator()
```

Dot notation reaches into whatever the module defines.

<!--
A module is nothing exotic — it is simply a .py file whose functions or
variables you want to use somewhere else. No special extension, no
declaration required. The moment another script imports it, that ordinary
.py file is functioning as a module.

The import statement pulls that file's contents into your current script,
and dot notation is how you reach inside to grab a specific thing — here
bmi_calculator, defined inside MyFirstFunction.py.

Connect it back: this is the exact same mechanism they already used when I
mentioned `import keyword` a few sections ago. Now they know what was
actually happening.

The mental model worth stating: dot notation means "inside." math.sqrt is
the sqrt that lives inside math. They'll see that pattern in every library
for the rest of their careers.

One wrinkle comes next, and it surprises everyone.
-->

---

## `__name__ == '__main__'`

```python
# Is this the main file we are running, or is it an import?
if __name__ == '__main__':
    main()
```

Importing a module runs the whole file — unless you guard it like this.

<!--
Here is the detail that surprises almost everyone the first time: importing
a module does not just expose its functions. It runs the entire file from
top to bottom, immediately, print statements and all.

The guard is how you prevent that. __name__ equals '__main__' is true only
when the file is being run directly, and it is something else entirely when
the file is being imported.

This is worth a live demo and it only takes a minute. Write two tiny
scripts, import one from the other without the guard, and watch it dump
output the importer never asked for. Then add the guard and show the
difference.

Tell them plainly: they will see this line in almost every professional
Python file they ever open. Recognizing it is more important right now than
writing it.
-->

---

## Using what someone else already wrote

```python
import math
import random

print(math.sqrt(144))          # 12.0
print(random.randint(1, 6))    # a die roll
```

`sqrt()`, like `print()`, is a **function** — a named, reusable block someone
else already wrote and tested.

<!--
Two modules, one pattern: import, then dot notation. That's the whole
skill.

Note math.sqrt(144) returns 12.0, a float, not 12 — square root, like
division, hands back floats even when the answer is a whole number. Callback
to the division slide.

From math, the ones worth naming: ceil and floor to round up or down,
factorial, and math.pi. Do not read a table — instead give them dir(math),
which lists everything the module provides. The professionals they'll
compete with aren't the ones who memorized function names; they're the ones
who know how to ask the tool what it can do.

From random, two things. First, it isn't truly random — it's pseudo-random,
generated from a seed. Fix the seed and you get the identical sequence every
run, which is how you make a demo or a test reproducible.

Second, the boundary difference, because it's a classic off-by-one:
randint(12, 20) includes 20, randrange(12, 20) stops at 19. Ask which one
they'd use for a six-sided die — randint(1, 6), because a die needs that
inclusive upper bound.
-->

# 2.11 Representing text

<!--
We close the chapter with the escape sequences that let us embed special
characters inside ordinary strings — and the switch that turns them back
off again.
-->

---

## Escape sequences

| Sequence | Meaning |
|-|-|
| `\n` | newline |
| `\t` | tab |
| `\\` | a literal backslash |
| `\'` | a literal single quote |

The backslash means "don't read the next character literally."

<!--
An escape sequence is a two-character combination, always starting with a
backslash, that Python reads as an instruction rather than as literal text.
This is the formal version of the newline we glanced at back in chapter
one.

Backslash-n inserts a line break, backslash-t a tab. If you need an actual
backslash or quote character inside a string, you escape it too, so Python
knows you mean the character itself rather than the start of another
sequence. These four cover the overwhelming majority of what you'll write
this semester.

Demo it: print a single string containing \n and watch it render as two
lines. The \n never appears in the output — Python consumed it as an
instruction.

If there's time and interest, this is also the moment for chr() and ord().
Every character corresponds to a number, a Unicode code point; chr turns a
number into a character and ord does the reverse. A loop over range(32,
127) printing chr(num) scrolls the whole printable ASCII range past them,
which is genuinely fun to watch. Optional — the notes cover it.
-->

---

## Raw strings turn escapes off

```python
my_string = 'This is a \n normal string'
my_raw_string = r'This is a \n raw string'
```

The `r` prefix tells Python to ignore every escape sequence in the string.

<!--
Prefixing a string literal with r turns off escape interpretation entirely
— every backslash becomes a literal backslash.

Print both and put them side by side. One breaks across two lines, the
other shows a literal backslash-n. Same characters typed, completely
different result.

The reason this matters to them specifically: Windows file paths. Writing
r'C:\Users\name' saves you from doubling every single backslash by hand,
and without the r prefix a path containing \t or \n silently turns into a
tab or a newline in the middle of your filename. That is a real bug that
looks like the file simply doesn't exist.

Keep this one in your back pocket. You will reach for it the first time you
hard-code a Windows path and Python mangles it.
-->
