# 4.1 If-else branches

---

## Everything so far ran top to bottom

Every line. Every time. No choices.

That stops here.

**branch:**
A sequence of statements only executed under a certain condition.

<!--
Ask the room: what's the last piece of software you used that made a decision
about you? Credit limit, insurance quote, shipping cost. All branching.
-->

---

## You already know this pattern

Anyone who has worked a hostess stand:

- Party of 1 → seat at the counter
- Party of 2 → small table
- Anything else → large table

That is an if-elseif-else.

---

## The shape of it

```python
# Lets give a discount to our long time customers
years_active = 7

if years_active > 5:
    discount = 0.10
```

Two things to notice: the **colon**, and the **indent**.

Python uses whitespace to decide what belongs to the branch.

---

## if-else — one or the other

```python
# Lets set an insurance rate
driver_age = 22

if driver_age < 25:
    insure_price = 4800
else:
    insure_price = 2200
```

One of those runs. Never both, never neither.

---

## More than two? Chain with elif

```python
# Lets figure out an anniversary gift
if num_years == 1:
    print('Newlyweds')
elif num_years == 25:
    print('Silver')
else:
    print('Congrats')
```

The **first** True wins. The rest are skipped.

<!--
Emphasise "first wins" — this is the single most important mechanic in the
chapter and everything about ranges depends on it.
-->

---

# 4.2 Detecting equal values

---

## Compares with `==`

`if num_years == 50:` ✅

Asks a question — is this true or false?

<!--
Double equals is a comparison, not an assignment. Python evaluates the
question on the right of if and hands back a boolean, true or false,
without changing num_years at all.
-->

---

## Assigns with `=`

`if num_years = 50:` ❌ syntax error

You will do this. Everyone does. Now you know what the error means.

<!--
A single equals sign inside an if statement is a syntax error, because
Python knows an assignment cannot double as a condition to test. This is
the single most common typo in the entire chapter — everyone hits it at
least once, so when the traceback shows up, you will already know exactly
what happened and how to fix it.
-->

---

## Equality and inequality

| Operator | Meaning | x is 3 |
|-|-|-|
| `==` | equal to | `x == 3` → True |
| `!=` | not equal to | `x != 4` → True |

<!--
These two operators are the workhorses of every condition you will write —
double equals asks whether two values match, and bang-equals asks whether
they don't. Both hand back one of exactly two possible answers, which is
worth naming precisely on its own, so let's do that next.
-->

---

## Boolean

**Boolean:**
A type with exactly two values — True or False.

<!--
Every comparison you write — every == and != from the table we just saw,
and every < and > we're about to meet — evaluates down to a Boolean.
There is no third option, no maybe, no null in between. That binary
outcome is exactly what an if statement is built to consume.
-->

---

## Even or odd

```python
# Lets check if a number is even
user_num = 22
div_remainder = user_num % 2

if div_remainder == 0:
    print(f'{user_num} is even.')
else:
    print(f'{user_num} is odd.')
```

Output: `22 is even.`

---

## Routing an invoice

```python
# Lets decide what happens to this invoice
status = 'overdue'
if status == 'paid':
    print('File it.')
elif status == 'pending':
    print('Wait.')
elif status == 'overdue':
    print('Send a reminder.')
```

Output: `Send a reminder.`

# 4.3 Detecting ranges

---

## Real data comes in ranges

Salary bands. Age brackets. Tax tiers. Shipping weights.

Almost nothing in business is a single equality check.

---

## The sequential trick

```python
# Lets sort a player into an age group
if age < 6:
    print('No teams')
elif age < 8:
    print('U8')
elif age < 10:
    print('U10')
```

`age < 10` really means **8 or 9** — because `age < 8` was already False.

<!--
Walk age = 9 through it out loud, branch by branch. This clicks or it doesn't,
and it's worth the two minutes.
-->

---

## You only write the top of each range

The bottom is implied by every branch above it.

Which also means **order matters enormously**.

Flip two branches and you get wrong numbers with no error at all.

---

# 4.4 Relational operators

---

## The four

Four relational operators cover every range comparison you'll write.

<!--
We've already met equality and inequality — now the four operators that
let us ask "how does this value compare," not just "does it match." These
are what make range checks like the age brackets and salary bands we just
worked through possible in the first place.
-->

---

## Relational operators

| Operator | Meaning | x is 3 |
|-|-|-|
| `<` | less than | `x < 4` → True |
| `>` | greater than | `x > 2` → True |
| `<=` | less than or equal | `x <= 3` → True |
| `>=` | greater than or equal | `x >= 4` → False |

<!--
Four operators, and you already know all of them from grade-school
arithmetic — Python just requires you to type them out as two-character
symbols rather than the single glyphs you may be used to on a whiteboard.
-->

---

## The `=` always goes second

`<=` ✅ · `=<` ❌

<!--
One syntax rule worth locking in now: when an operator pairs with equals,
the equals sign always comes second. Writing =< instead of <= is a syntax
error, and it's an easy one to make on muscle memory from other languages.
-->

---

## Pricing by band

```python
# Lets price car insurance by age
if user_age < 16:
    insurance_price = 0
elif user_age < 25:
    insurance_price = 4800
else:
    insurance_price = 2100
```

Age 27 → `$2100`

---

## Chaining

```python
# Lets check a value sits inside a range
if 10 < x < 15:
    print('In range')
```

Reads like maths, works like maths.

Evaluated left to right — and `a` is never compared to `c`.

# 4.5 Logical operators

---

## When one condition isn't enough

Business rules rarely hinge on just one test — think "premium and loyal."

<!--
Everything we've built so far tests one condition at a time. Real business
rules are almost never that simple — eligibility for a discount might
depend on tenure and balance together, or on one of two qualifying
criteria. Logical operators are how we combine conditions into a single
question.
-->

---

## Logical operators

| Operator | True when |
|-|-|
| `a and b` | **both** are True |
| `a or b` | **at least one** is True |
| `not a` | the operand is False |

<!--
and demands both sides be True, or is satisfied by either side alone, and
not simply flips a single condition. Three operators, and they cover
every way you'll ever need to combine conditions.
-->

---

## No symbols to memorize

Python spells them out. No `&&`, `||`, `!`.

<!--
Python writes these out as plain English words rather than the symbols
you may have seen in other languages — no double ampersands or pipes to
remember, just and, or, and not, read the way you'd say them out loud.
-->

---

## Building a range with and

```python
# Lets check the value lands between 10 and 15
if (x > 10) and (x < 15):
    print('In range')
```

`x > 10` covers 11 and up.
`x < 15` covers 14 and down.

Ask for both, get the overlap.

---

## Cable channels

```python
# Lets classify the channel
if (user_channel >= 2) and (user_channel <= 499):
    channel_type = 'standard'
elif (user_channel >= 1002) and (user_channel <= 1499):
    channel_type = 'hd'
else:
    channel_type = 'error'
```

---

## Implicit range

Plain `elif` chain.

For ranges that increase with no gaps.

<!--
An implicit range leans on the fact that elif only runs if every branch
above it failed — so each condition only needs to state its lower bound,
and the previous branch's failure quietly supplies the upper bound. This
reads cleanly when your ranges are continuous with no gaps between them.
-->

---

## Explicit range

Uses `and`.

For gaps, or a real upper bound.

Both correct. Pick the one that reads better.

<!--
An explicit range spells out both bounds with and, which is the right
choice the moment your ranges have a gap between them or you genuinely
need to test an upper bound rather than relying on elif's fall-through
behavior. Neither style is more correct than the other — pick whichever
reads more clearly for the range you are describing.
-->

---

# 4.6 Ranges with gaps

---

## Not every range is a staircase

Movie tickets: children 12 and under, seniors 65 and up.

Everyone from 13 to 64 is **the gap**.

---

## Let else swallow the gap

```python
# Lets price a movie ticket
if user_age <= 12:
    movie_ticket_price = 11
elif user_age >= 65:
    movie_ticket_price = 12
else:
    movie_ticket_price = 14
```

You never had to name the middle group.

---

## When the gap is in the middle

```python
# Lets validate an office number
if (office_num >= 100 and office_num <= 150) or \
   (office_num >= 200 and office_num <= 250):
    valid = True
else:
    valid = False
```

Offices 100–150 and 200–250 exist. Nothing between.

---

## Watch the boundaries

Is 12 a child? Is 65 a senior?

`<=` and `>=` say yes. `<` and `>` say no.

**Off-by-one at a boundary is the most common bug in pricing logic** — and nobody notices until a customer complains.

<!--
Worth pausing here. This is the bug they will actually ship.
-->

# 4.7 Multiple features

---

## Separate ifs

```python
if balance > 1000:
    print('Premium')
if years > 5:
    print('Loyal')
```

**Both** can run.

<!--
Two standalone if statements are evaluated independently — Python checks
the first, then, regardless of the outcome, checks the second on its own
terms. A customer who is both high-balance and long-tenured prints both
labels. Nothing about the first condition constrains the second.
-->

---

## if / elif

```python
if balance > 1000:
    print('Premium')
elif years > 5:
    print('Loyal')
```

**One** runs.

<!--
Chain the same two conditions with elif instead, and the second branch
only gets evaluated if the first one failed — so at most one label ever
prints, even for that same high-balance, long-tenured customer. Same
conditions, same order, structurally different outcome. This is exactly
the trap the slide title warned about.
-->

---

## Which do you want?

- Separate `if` → *tag everything that applies*
- `if` / `elif` → *pick exactly one*

Same-looking code. Completely different month-end report.

---

## Nested if-else

```python
# Lets calculate the sales bonus
if sales_type == 2:
    if sales_bonus < 5:
        sales_bonus = 10
    else:
        sales_bonus = sales_bonus + 2
else:
    sales_bonus = sales_bonus + 1
```

The inner `if` is only reached when the outer one is True.

Two levels is fine. Four means you want logical operators instead.

# 4.8 Comparing data types

---

## Different types, different rules

| Type | Compared how |
|-|-|
| Numbers | Arithmetically |
| Strings | Character by character |
| Lists, tuples | Element by element |
| Dictionaries | Only `==` / `!=` |

---

## Strings are case sensitive

```python
# Lets compare two days
my_str = 'Tuesday'

print(my_str == 'Tuesday')
print(my_str == 'tuesday')
```

Output: `True` then `False`

That `T` vs `t` has ruined more afternoons than I can count.

---

## Never compare floats with ==

```python
print(0.1 + 0.2 == 0.3)
```

Output: `False`

Yes, really. Floating-point is stored imprecisely.

Compare with `<` or `>`, or check the difference is small enough to ignore.

<!--
Run this live. The gasp is the point — it makes the lesson stick.
-->

---

## Operators that do not exist

| You meant | Write | Not |
|-|-|-|
| greater or equal | `>=` | `=>` ❌ |
| not equal | `!=` | `<>` ❌ |

---

# 4.9 Membership and identity

---

## in / not in

```python
# Lets see if a name is on the roster
roster = ['Alves', 'Messi', 'Fabregas']

if name in roster:
    print(f'Found {name}.')
```

Enormously useful once your data comes from a spreadsheet or an API.

---

## It works on strings too

```python
# Lets inspect an HTTP request
request_str = 'GET index.html HTTP/1.1'

if '/1.1' in request_str:
    print('HTTP protocol 1.1')
```

A string is a sequence of characters, so `in` finds substrings.

---

## Dictionaries: keys, not values

```python
my_dict = {'A': 1, 'B': 2, 'C': 3}

print('B' in my_dict)
print(3 in my_dict)
```

Output: `True` then `False`

`3` is a **value**, not a key. This trips people up constantly.

---

## is / is not — mostly don't

`is` asks "are these the same object?"

`==` asks "do these have the same value?"

You almost always want `==`.

Python quietly reuses objects for small numbers, so `x is 3` can be True while `y is 1000` is False. Don't build logic on that.

# 4.10 Order of evaluation

---

## The pecking order

1. `( )` parentheses
2. `* / % + -` arithmetic
3. `< <= > >= == != in` comparison
4. `not`
5. `and`
6. `or`

**Arithmetic before comparison, comparison before logic.**

---

## Working one through

```python
# Lets evaluate this step by step
x = 7
y = 6
z = 3

print(y * z < x + 1 or z == 3)
```

`18 < 8` → False · `z == 3` → True · `False or True` → **True**

---

## Where it goes wrong

`not` binds tighter than you'd guess reading it out loud in English.

<!--
The pecking order we just walked through has one trap worth naming on its
own: not binds more tightly than most people expect, since English reads
"not" as applying to the whole clause that follows. Python does not agree,
and the mismatch produces two classic misreadings.
-->

---

## The classic misreadings

| You meant | Python does |
|-|-|
| `(not a) == b` | `not (a == b)` |
| `(not x) + y < 5` | `not ((x + y) < 5)` |

<!--
Neither of these raises an error, which is exactly what makes the bug
dangerous — the code runs, it just runs against a different condition
than the one you had in your head.
-->

---

## The fix is cheap

None of these are errors. They just quietly give a different answer.

**Use parentheses even when you don't need them.**

<!--
Wrap the piece you mean not to apply broadly in its own parentheses,
every single time, even when precedence would technically get it right
without them. A reader — including you, in six months — should never
have to reconstruct the pecking order in their head to know what a
condition means.
-->

# 4.11 Code blocks and indentation

---

## Indentation is syntax, not style

**code block:**
A series of statements grouped together, defined by indentation level.

- Outermost block: no indent
- New block follows a colon
- Must be indented **more** than the one before

Four spaces. Always four spaces.

---

## Nesting

```python
# Lets classify a car
if antique:
    if model in ['Ford', 'Chevrolet', 'Dodge']:
        print('Domestic antique.')
```

Each indent step tells Python "this belongs to the thing above me".

---

## Never mix tabs and spaces

Your editor may draw a tab as four spaces.

Python does not care what it *looks* like — a tab is a tab.

Mixing them raises `IndentationError`, and the code looks perfectly aligned on screen the whole time.

**Set your editor to insert spaces. Once. Today.**

# 4.12 Conditional expressions

---

## The long way

```python
if order_total > 50:
    shipping = 0
else:
    shipping = 7
```

<!--
Four lines to assign a single variable one of two values. Nothing wrong
with this — it's perfectly readable — but watch what happens when we
collapse it down to a single expression.
-->

---

## The short way

```python
shipping = 0 if order_total > 50 else 7
```

Same logic, one line.

<!--
This is a conditional expression — everything the four-line version did,
compressed onto one line with no loss of behavior. It reads almost like
English if you say it out loud: shipping is 0 if order_total is over 50,
else it's 7. Let's look at the general shape underneath that sentence.
-->

---

## The shape

```python
expr_when_true if condition else expr_when_false
```

The **condition in the middle is evaluated first**.

Three operands — sometimes called a *ternary* operation.

---

## Use it sparingly

Good for a simple assignment.

Bad the moment the branches do more than produce a value, or the condition gets long.

Plenty of Python developers dislike these, and the complaint is fair — the middle operand runs first, which is not how we read English.
