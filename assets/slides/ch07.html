Every function you have written up to now calls other functions — count_down calls print, a helper calls another helper. Today we look at what happens when a function calls itself. It sounds like a paradox the first time you hear it, and it genuinely trips people up the first few times they trace through one by hand, so we are going to slow down and watch the call stack build up and unwind, one call at a time. By the end of the hour you will have a reliable two-step recipe for writing one of these from scratch.

We start with the simplest possible recursive function — one that counts down and stops — purely to watch the mechanics: what a call to itself actually does to memory, and why it eventually has to stop.

A while loop would do this job in fewer lines — the point here isn't efficiency, it's watching what happens underneath. count_down(2) prints 2 and calls count_down(1), which prints 1 and calls count_down(0), which prints Go! and stops. Three separate calls, and each one gets its own private count variable sitting in its own namespace — the same way any two ordinary function calls never share variables, even when those two calls happen to be the same function calling itself. Ask the room: at the exact moment count_down(0) is running, does the count equal to 1 from the call above it still exist somewhere? It does — it's just waiting, paused, for that inner call to finish.

This is the single most important habit to build right now, before we've written anything more complicated than a countdown: locate the stopping condition first, every time, before you worry about anything else the function does. We'll formalize this as the base case in section 7.4, but the instinct to hunt for "what makes this stop" starts today. The depth-limit line matters more than it looks: unlike a while loop, which just runs forever until you kill it, runaway recursion runs out of stack space and Python raises RecursionError for you automatically — usually a useful early warning that a base case isn't actually being reached. sys.setrecursionlimit() can raise that ceiling, but treat it as a last resort, not a fix.
