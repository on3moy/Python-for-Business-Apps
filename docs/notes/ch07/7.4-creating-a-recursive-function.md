# 7.4 Creating a recursive function  

Writing a recursive function from scratch goes easier if you build it in two deliberate steps instead of trying to write the whole thing at once.  

**base case:**  
The condition under which a recursive function returns a value directly, without calling itself again.  

**recursive case:**  
The condition under which the function calls itself, usually on a smaller or simpler version of the original problem.  

## Step 1: Write the base case first

Get the "stop" condition working and tested before you touch the recursive part at all.  

```
def nfact(n):
    fact = 0
    if n == 1 or n == 0:   # Base case
        fact = 1
    # Fixme: Finish
    return fact
```

## Step 2: Add the recursive case

Only once the base case is solid do you add the branch that calls the function again.  

```
def nfact(n):
    fact = 0
    if n == 1 or n == 0:   # Base case
        fact = 1
    else:                  # Recursive case
        fact = n * nfact(n - 1)
    return fact
```

Output:  
```
Enter N: 6
N! is: 720
```

!!! note "Factorial isn't actually a great recursion example"  

    A loop version — `for i in range(n, 0, -1): result *= i` — is just as clear and doesn't pay the cost of a growing call stack. Factorial earns its spot here purely because it's simple enough to demonstrate the base-case/recursive-case pattern without other complexity getting in the way. Python programmers generally reach for [loops](../ch05/5.1-loops-general.md) over recursion more often than programmers in other languages do; recursion tends to actually pay off on tree-shaped data of unpredictable depth, not flat sequences.  

Before reaching for recursion at all, ask two questions: does the problem actually break down into a smaller version of itself, and is a recursive solution genuinely *clearer* than a loop — not just possible. Binary search passes both tests. Factorial passes the first and fails the second.  

!!! warning "Two ways recursion goes infinite"  

    - Forgetting a base case entirely.  
    - Writing a base case that the recursive calls never actually reach (e.g. the argument moves away from it instead of toward it).  

    Either mistake causes infinite recursion, and Python eventually kills the program with a `RecursionError` rather than let it run forever.  

## Outer/inner function pairs

A common pattern splits a recursive function into two: an **outer** function callers actually use (`factorial(n)`), and an **inner** helper prefixed with an underscore (`_factorial(n)`) that does the real recursive work. The outer function validates input — checking `n` isn't negative, say — then hands off to the inner one, which can carry extra bookkeeping parameters the caller never needs to see.  

??? question "Why bother splitting into two functions instead of one?"  

    Because the inner function's parameters are often only meaningful *during* the recursion — like `low` and `high` in a binary search, or an `indent` string for debug output. Forcing a caller to supply those every time makes the function's public interface confusing. The outer function keeps the call site simple; the inner one keeps the recursion honest.
