# 2.1 Variables and Assignments

<!--
We open with the single most common line of code you will write all
semester: an assignment statement. Everything from here forward assumes you
are comfortable naming a value and retrieving it later.
-->

---

## Variable

Named item, such as x, y, john, lamp.

**Assignment statement:**
We assign variables with `=`.

```python
x = 13
JohnDoe = 55
```

<!--
A variable is nothing more than a label we attach to a value so we can refer
back to it. The equal sign here is not mathematical equality — it is an
instruction: evaluate the right-hand side, then bind the name on the left to
that result. Before we move to the rules, ask the room what they would name
a variable holding, say, an employee's salary. Get two or three answers on
the board — it sets up the naming conventions slide nicely.
-->

---

## The rules

`x = 13` ✅
`JohnDoe = 55` ✅

Variable always starts on the left, then `=`, then the value.

<!--
The pattern is rigid and worth stating plainly: name, then equal sign, then
the value being assigned. Both of these examples follow it — a lowercase
name and a capitalized one, both legal. Hold that pattern in mind, because
the next slide is entirely devoted to the ways students break it.
-->

---

## Common mistakes

`5 = x` ❌ — the target must be a name, not a value
`x => 5` ❌ — Python has exactly one assignment operator, `=`
`1x = 5` ❌ — names can't start with a digit

<!--
Three failures, and each is worth naming individually. Five equals x fails
because the direction is backwards — the target of an assignment must
always be the name, not the value. The arrow syntax fails because Python
has exactly one assignment operator, the equal sign, full stop. And a
variable starting with a digit fails because Python's rules for legal
names — which we formalize in the next section — require a letter or
underscore first. Committing these to memory now saves you from a dozen
confusing error messages later.
-->

---

## Naming styles

- `lower_case_with_underscores` — our default
- `UPPER_CASE` — constants
- `CapitalizedWords` — classes later in the semester
- `mixedCase` ⚠️ avoid unless already common in the script
- `Capitalized_Words_With_Underscores` ❌ ugly, don't

<!--
This is a preview of PEP 8, the community style guide for Python, and we
will return to it repeatedly as the semester goes on, so there is no need
to dwell here today. The one habit worth building immediately is
lower_case_with_underscores for ordinary variables — it is what the rest of
the Python ecosystem expects, and consistent style is what makes code
reviewable by someone other than you six months from now.
-->

---

# 2.2 Identifiers

<!--
Now that we can assign variables, let's formalize exactly what counts as a
legal name in Python — the term of art here is "identifier."
-->

---

## Identifier

A sequence of letters, underscores, and digits. Must start with a letter or
underscore.

Python is **case sensitive** — `Cat` and `cat` are different names.

<!--
That is the entire rule: letters, digits, and underscores, and the first
character cannot be a digit. Notice this formalizes the constraint we saw a
moment ago with 1x = 5. And case sensitivity is worth a beat — coming from
Excel or SQL, where case is often forgiving, students are sometimes
surprised that Cat and cat are two entirely distinct names to the
interpreter, not a typo Python quietly corrects for them.
-->

---

## Reserved words

Python reserves words to do its own work. Don't overwrite them.

```python
print = 13
sum = 13 + 23
```

Both ❌ — you just broke `print()` and `sum()` for the rest of your session.

<!--
Live demo: actually run print = 13 in a notebook, then try to call print()
afterward and watch it fail, because print is no longer a function — it is
now the integer 13. Then restart the kernel to fix it. This is a small,
memorable scare early in the semester, and it makes the abstract warning
concrete: reserved names are not decoration, they are load-bearing.
-->

---

## Finding the full list

```python
import keyword
import builtins

keyword_list = keyword.kwlist
builtin_list = dir(builtins)
reserved_words = keyword_list + builtin_list
print(f'Number of words to avoid: {len(reserved_words)}')
```

<!--
We have not covered import yet formally — that is section 2.8 — so tell the
room to trust this snippet for now and file it away as a self-service tool
rather than something to memorize. The larger point is a habit we want to
instill early: rather than memorizing every reserved word Python ships
with, learn how to ask Python to tell you.
-->

---

# 2.3 Objects

<!--
We now step back from syntax and ask a more fundamental question: what
actually happens in memory when we write an assignment statement? The
answer is objects.
-->

---

## Every value is an object

An object represents a value, created automatically by the interpreter.

```python
x = 4
```

That line creates an object to represent `4`, and binds the name `x` to it.

<!--
In Python, absolutely everything — integers, strings, functions, lists you
will meet in chapter three — is represented internally as an object. When
this line executes, two things happen in sequence: first the interpreter
creates an object in memory to represent the value 4, and only then does it
bind the name x to that object. The name and the value are two separate
things, connected by this act of binding.
-->

---

## Name binding

An object can have more than one name bound to it. Every name is bound to
exactly one object.

```python
x = '🦖'

# Lets show the value
print(x)

# Lets show the type
print(type(x))
```

<!--
Notice that print and type are both built in — neither required an import,
which is worth flagging since section 2.8 introduces functions that do.
Run this live: print shows the value, type shows what kind of object it
is. The asymmetry I want you to sit with is this — one object can answer
to several names, the way both "Bob" and "Robert" might refer to the same
person — but each individual name points to exactly one object at any
given moment. In a few slides we will meet a third built-in, id, that lets
us confirm that directly.
-->

---

## Value

**Value:** what it holds — `'Hi Im Baby'`, `13`, `'13'`

<!--
Every object carries three properties, and value is the most intuitive of
the three: it is simply the data the object holds. Notice these three
examples on the slide — a string, an integer, and a string that merely
looks like a number — because that last pair is exactly what sets up the
next slide's point about type.
-->

---

## Type

**Type:** its format — int, string, etc.

`'13'` and `13` share a value loosely, but not a type.

<!--
Type is the object's format — whether the interpreter treats it as an
integer, a string, a float, and so on. It is worth pointing out that '13'
in quotes and 13 without quotes look similar but carry different types —
one is text, one is a number — and Python will not silently treat them the
same way in arithmetic or comparisons. Type is what determines which
operations are even legal on a given object.
-->

---

## Identity

**Identity:** a unique id, assigned by the interpreter

```python
x = '🦖'
print(id(x))
```

Not permanent — garbage collection can reassign a freed id later.

<!--
Identity is a unique number the interpreter assigns to an object, and you
retrieve it with the built-in id function — the third built-in we've now
met, alongside print and type. Run this live against the same x from a
few slides back. Unlike value and type, identity is not something to lean
on for the long haul — Python automatically frees an object's memory once
nothing in the program still refers to it, through garbage collection, and
a later object may be handed that very same identity number. Don't rely on
identity surviving across a program run; it is useful mainly for
confirming whether two names point at the same object right now.
-->

---

# 2.4 Numeric Types

<!--
With objects established as the underlying model, let's get concrete and
look at the numeric types we will use constantly: floats and integers.
-->

---

## Floating-point numbers

A real number like `13.01`, `-55.23`, `0.00001`.

A **float literal** always shows the fractional part, even if it's `0`:
`1.0`, `0.0`, `99.0`.

```python
float('13.5')
int('13')
```

Both convert if they can — neither can convert `'Hi'`.

<!--
A float is Python's data type for real numbers, and the name comes from the
decimal point being free to "float" anywhere in the digits. Notice the
convention: even a whole-number float still displays its fractional part,
so 99.0 rather than bare 99 — that trailing .0 is how you can tell at a
glance you are looking at a float rather than an integer. The float and int
functions attempt a conversion and will raise an error rather than silently
guess if the string cannot be interpreted as a number — try float('Hi') live
and let the traceback make the point.
-->

---

## Scientific notation

`0.003` is the same as `3.0e-3`

- Negative exponent moves the decimal left ⬅️
- Positive exponent moves the decimal right ➡️

<!--
Scientific notation is simply another way to write the same float, using an
e to indicate how many places, and in which direction, to shift the decimal
point. A negative exponent shifts left, toward zero; a positive exponent
shifts right, toward larger magnitude. You will see this format any time
Python needs to display a very small or very large number compactly, so it
is worth being able to read it fluently rather than treating it as noise.
-->

---

## Overflow

Floats have a limit to how long a decimal can get.

**Overflow error:**
A value too large to be stored in the memory the interpreter allocated.

32-bit Python tops out around `1.0e308`. Yes, that's 307 zeros.

<!--
Even floats have a ceiling. On a 32-bit installation of Python, the largest
representable float sits around 1.0 times ten to the 308th power — a one
followed by roughly three hundred and seven zeros — and asking for anything
beyond that raises an overflow error, because the interpreter simply has
nowhere left to store the additional precision. In business contexts this
almost never comes up, but it is worth knowing the ceiling exists rather
than assuming Python's numbers are infinite.
-->

---

## Formatting floats

```python
print(f'{13.12345: .2f}')
```

Output: `13.12`

Nobody wants to read 13 decimal places in a report. Clean it up.

<!--
This f-string syntax is a preview of formatted strings, which we will
formalize in chapter three — for now, just recognize the pattern: colon,
then a format spec, here .2f meaning fixed-point with two decimal places.
A quick warning for anyone coming from Excel muscle memory: commas are
never allowed inside a Python number literal. Writing 13,000 does not give
you thirteen thousand — it gives you a different data structure entirely,
and that is a bug that can be very confusing to track down the first time
you hit it.
-->

---

# 2.5 Arithmetic Expressions

<!--
We now have values and types. Let's combine them — Python can do everything
a calculator can, and the rules for combining operations follow a familiar
order of operations.
-->

---

## Expression

A combination of variables, literals, operators, and parentheses that
evaluates to a value — like `2 * (x + 1)`.

<!--
An expression is any combination of these pieces — variables, literal
values, operators, parentheses — that Python can reduce down to a single
value. That's the whole definition; the next slide is simply the
inventory of operators you have to work with.
-->

---

## Arithmetic operators

| Operator | Meaning |
|-|-|
| `+` `-` | add, subtract (and unary negation) |
| `*` | multiply |
| `/` | divide |
| `**` | exponent |

<!--
This table covers the operators you already know from arithmetic; the
double asterisk for exponentiation is likely the only unfamiliar symbol
here, since most calculators use a caret instead. Every one of these
combines with the values and variables from the previous slide to build
an expression.
-->

---

## Order of operations

Same PEMDAS you already know:

1. `( )` parentheses
2. `**` exponent
3. unary `-`
4. `*` `/` `%` left to right
5. `+` `-` left to right

`**` alone evaluates right to left.

<!--
This is the same precedence hierarchy you learned as PEMDAS in algebra
class, extended with two Python-specific wrinkles: unary negation sits
just below exponentiation, and modulo shares precedence with multiplication
and division. Ask the room to predict, out loud, what 2 plus 3 times 4
evaluates to before you run it. Most will get fourteen right away — which
is exactly the point. This is arithmetic they already understand; Python
is just formalizing rules they use intuitively every day.
-->

---

## Try it

```python
1 + 0
1 * 0
0 / 1
5 // 2
2 ** 4
4 % 2
(1 + 3) * (2 + 2)
```

<!--
Run these one line at a time in a live cell and have the class call out the
expected result before you execute each one. Floor division and modulo get
their own dedicated section coming up next, so resist the urge to fully
explain them here — just flag that 5 // 2 and 4 % 2 are coming, and let the
room sit with a little curiosity.
-->

# 2.6 Python Expressions

<!--
Let's see arithmetic expressions inside an actual, if small, program — and
pick up a shorthand for updating a variable in place.
-->

---

## A realistic expression

```python
down_payment = int(input('Enter down payment: '))
payment_per_month = int(input('Enter monthly payment: '))
num_months = int(input('Enter number of months: '))

total_cost = down_payment + (payment_per_month * num_months)
print(f'Total cost: ${total_cost:.2f}')
```

<!--
This is a small car-lease calculator, and it is worth running live with
real numbers — the class always has opinions about car payments, and that
engagement is useful. Notice the parentheses around the multiplication are
not strictly required by precedence, since multiplication already happens
before addition, but they make the intent unmistakable to a human reader,
which is a habit worth encouraging even when the interpreter does not
demand it.
-->

---

## Compound operators

Shorthand for "update this variable using itself."

<!--
Every one of these is pure shorthand — nothing new is happening
semantically, only syntactically. Each compound operator expands to the
exact same statement typed out longhand. Let's look at the full set, then
talk about when it is actually worth reaching for the shorthand.
-->

---

## The shorthand table

| Compound | Expands to |
|-|-|
| `age += 1` | `age = age + 1` |
| `age -= 1` | `age = age - 1` |
| `age *= 1` | `age = age * 1` |
| `age /= 1` | `age = age / 1` |
| `age %= 1` | `age = age % 1` |

<!--
Notice the pattern repeats identically across every arithmetic operator —
the compound form on the left is always the operator, followed by equals,
and it always expands to the variable reassigned to itself combined with
the right-hand operand. Once one of these clicks, all five click.
-->

---

## Write it out first

Write the expanded form until it clicks, then switch to shorthand.

You'll live in compound operators once we hit loops.

<!--
I recommend writing the expanded version — age equals age plus one — until
the pattern is second nature, and only then switching to the compact form.
You will see compound operators constantly once we get to loops later in
the course, incrementing a counter on every pass, so it is worth building
the comfort now while the stakes are low and there's no loop logic
competing for your attention.
-->

# 2.7 Division & Modulo

<!--
Division deserves its own close look, because Python actually gives you
three distinct flavors of it, and choosing the right one matters.
-->

---

## Three kinds of division

Input: `4 / 2`
Output: `2.0`

Regular division always returns a **float**, even with no remainder.

<!--
This is the detail that trips people up most often: ordinary division with
a single forward slash always returns a float, even when the two operands
divide evenly. Four divided by two is not the integer two, it is 2.0. If
your downstream code expects a whole number — say, an index or a count —
regular division alone will not give you that, which is exactly why the
next two operators exist.
-->

---

## Floor division `//`

Rounds down to the smallest whole number.

Input: `5 // 3`
Output: `1`

<!--
Floor division, the double slash, discards everything after the decimal
point and gives you back an integer. Five divided by three is
approximately 1.667, and floor division truncates that down to 1 — not
rounds, truncates, so it always moves toward negative infinity rather than
to the nearest whole number. Keep that in mind once we get to negative
operands, because floor division does not behave like ordinary rounding
there. What happened to the leftover 0.667? That is exactly what our next
operator hands back to you.
-->

---

## Modulo `%`

The remainder left over after division.

Input: `5 % 3`
Output: `2`

<!--
Modulo hands you exactly what floor division threw away, expressed as the
remainder — 2 in this case, since three goes into five once with two left
over. In business terms, modulo is how you test whether a number is even,
using n modulo 2 equals 0, or how you split a batch of items into
equal-sized groups with some leftover remainder — think distributing a
stack of invoices evenly across a team of five and figuring out how many
are left over for whoever picks up the slack.
-->

# 2.8 Module Basics

<!--
We now zoom out from single expressions to how code gets organized into
files — the difference between a script and a notebook, and what a module
actually is.
-->

---

## .py files

- Plain script file
- Run via CLI: `python file.py`
- Or the play button in VS Code

<!--
Both .py and .ipynb are ways to save Python code, and the choice is not
about which is "better" in the abstract — it depends on the use case. A .py
file is a plain script, executed top to bottom from the command line, a
scheduler, or the play button in VS Code. Ask the room: if your company
runs a nightly job on a server, which format do you reach for? The answer
is .py — schedulers execute scripts, not notebooks.
-->

---

## .ipynb files

- Jupyter notebook, cell by cell
- Better for exploring and visualizing
- Common at Databricks / Azure Notebooks

<!--
A .ipynb notebook breaks code into individually runnable cells, which makes
it excellent for exploration, iteration, and visualization, but it is not
designed to be triggered by a server on a schedule the way a .py script is.
If you are doing exploratory analysis on Databricks or Azure Notebooks —
platforms many of you will meet in industry — you will live in .ipynb most
of the day. Same language underneath, two very different jobs.
-->

---

## Module

**Module:** a file containing Python code other files can reuse.

Any `.py` file qualifies — nothing special required.

<!--
A module is nothing exotic — it is simply a .py file whose functions or
variables you want to reuse somewhere else. There is no special file
extension or declaration required; the moment another script imports it,
that ordinary .py file is functioning as a module. So the question becomes,
how does another script actually reach in and use it? That's import.
-->

---

## Import

**Import:** how you make a module available in your script.

```python
import MyFirstFunction

MyFirstFunction.bmi_calculator()
```

Dot notation reaches into whatever the module defines.

<!--
The import statement pulls that file's contents into your current script,
and dot notation is then how you reach inside it to grab a specific
function — here bmi_calculator, defined inside MyFirstFunction.py. This is
the exact same mechanism you already used two sections ago to pull in the
keyword and builtins modules; now you know what was actually happening
under the hood. One wrinkle is coming next: importing does more than just
expose functions — it runs the whole file.
-->

---

## `__name__ == '__main__'`

```python
# Is this the main file we are running or is it an import?
if __name__ == '__main__':
    # If this is the main file, run the meat and potatoes
    main()
else:
    # If it's imported, only run this
    some_other_function()
```

Importing a module runs the whole file — unless you guard it like this.

<!--
Here is a detail that surprises almost everyone the first time they hit it:
importing a module does not just expose its functions — it runs the entire
file from top to bottom, immediately, print statements and all. The
__name__ guard is how you prevent that: __name__ equals '__main__' is only
true when the file is being run directly, not when it is being imported.
This is worth a live demo — write two small scripts, import one from the
other without the guard, and watch it dump output the importer never asked
for. Then add the guard and show the difference.
-->

# 2.9 Math Module

<!--
Now that we understand imports, let's put one to use — Python's built-in
math module, which gives us the operations a basic calculator lacks.
-->

---

## import math

```python
import math

num = 144
sqrt_num = math.sqrt(num)
print(sqrt_num)
```

Output: `12.0`

`sqrt()`, like `print()`, is a **function** — a named, reusable block of
statements.

<!--
Once imported, dot notation gives us access to everything the math module
defines. sqrt is a function in exactly the same sense that print is a
function — a named, reusable block of statements someone else already
wrote and tested, which we now get to call rather than reimplement. Notice
the output is 12.0, a float, not 12 — square root, like division, tends to
hand back floats even when the mathematical answer happens to be a whole
number.
-->

---

## A few you'll actually use

| Function | Does |
|-|-|
| `math.sqrt(x)` | square root |
| `math.ceil(x)` / `math.floor(x)` | round up / down |
| `math.factorial(x)` | x! |
| `math.pi` | 3.14159... |

<!--
This is a small, curated slice of a much longer library — do not try to
memorize the whole thing. The real skill I want you to walk away with is

# 2.10 Random Numbers

<!--
Next, a module you will reach for constantly for testing, simulation, and
sampling: random.
-->

---

## import random

```python
import random

# Lets generate a random floating point number
print(random.random())
```

Not actually random — **pseudo-random**, generated from a seed.

Same seed, same sequence, every time. Useful for reproducible demos.

<!--
The values this module produces are not truly random in the physical
sense — they are pseudo-random, generated by a deterministic formula that
starts from a starting value called a seed. Left alone, Python seeds
itself from the current time, so each run looks different. But if you fix
the seed explicitly, you get the exact same sequence of "random" numbers
every single time, which is enormously useful when you want a demo or a
test to be reproducible rather than different every time you run it.
-->

---

## Ranges you control

```python
random.randrange(3)          # 0, 1, or 2
random.randint(12, 20)       # 12 through 20, inclusive
random.randrange(12, 20)     # 12 through 19
```

<!--
Notice the boundary difference between these two, because it is a common
source of off-by-one bugs: randint is inclusive on both ends, so
randint(12, 20) can return 20, while randrange excludes the upper bound, so
randrange(12, 20) tops out at 19. Ask the room which one they would reach
for to simulate a six-sided die — randint(1, 6), since a die roll needs
that inclusive upper bound — versus picking a random index into a list,
where randrange is usually the more natural fit.
-->

# 2.11 Representing Text

<!--
We close the chapter with how Python represents individual characters
under the hood, and the escape sequences that let us embed special
characters inside ordinary strings.
-->

---

## chr() and ord()

```python
for num in range(32, 127):
    char_converted = chr(num)
    print(f'{num}: {char_converted}')
```

`chr()` turns a number into a character. `ord()` does the reverse.

<!--
Under the hood, every character your keyboard can produce corresponds to a
number — a Unicode code point. chr takes that number and gives you back
the character; ord does the reverse, taking a character and giving you its
number. This loop walks through the printable ASCII range and shows the
mapping directly — run it live and let the class watch the alphabet and
punctuation scroll by as plain integers underneath.
-->

---

## Escape sequences

The backslash tells Python "don't read the next character literally."

<!--
An escape sequence is a two-character combination, always starting with a
backslash, that Python interprets as an instruction rather than literal
text. This is the formal version of the newline character we glanced at
back in chapter one — let's see the full set, then a live example.
-->

---

## The common ones

| Sequence | Meaning |
|-|-|
| `\n` | newline |
| `\t` | tab |
| `\\` | a literal backslash |
| `\'` | a literal single quote |

<!--
\n inserts a line break, \t inserts a tab, and if you actually need a
literal backslash or quote character inside a string, you escape it too,
so Python knows you mean the character itself rather than the start of
another sequence. These four cover the overwhelming majority of what
you'll write this semester.
-->

---

## Escapes in action

```python
print('Hello, this is the first line\nThis is the second line')
```

<!--
Run this live and watch a single string literal render as two lines of
output. The \n never appears in the printed result — Python consumes it
as an instruction, not as text. This is worth contrasting with what
happens when you don't want that behavior, which is exactly the problem
raw strings solve, coming up next.
-->

---

## Raw strings

```python
my_string = 'This is a \n \'normal\' string\n'
my_raw_string = r'This is a \n \'raw\' string'
```

The `r` prefix tells Python to ignore every escape sequence in the string.

<!--
Prefixing a string literal with r turns off escape-sequence interpretation
entirely — every backslash is treated as a literal backslash. This is
especially useful for file paths on Windows, where r'C:\Users\name' saves
you from having to double every single backslash by hand. Keep this one in
your back pocket; you will reach for it the first time you try to hard-code
a Windows file path and Python mangles it.
-->
