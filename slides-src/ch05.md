# 5.1–5.3 While loops

<!--
We start with the vocabulary, then the while loop — Python's literal
translation of "keep going while this is true."

The one habit to plant early is the infinite-loop trap. It shows up in the
abstract in 5.1 and in very concrete form two slides later, and it is the
bug that eats the most student time this semester.
-->

---

## Everything so far ran once

**loop:**
A construct that repeats a block of statements — the loop body — for as long
as some condition is true.

Each pass through the body is one **iteration**.

<!--
Think about closing out a cash register at the end of a shift. You do not
write one line per transaction — you check whether there is another receipt,
process it, and check again. That check, process, check again rhythm is
exactly what a loop is.

Ask the room: what's a task you do at work that's really just the same three
steps repeated until something runs out? Inventory counts, invoice batches,
email lists. Everyone has one.

The one warning to plant now, before we write any real syntax: a loop's
condition has to depend on something that actually moves. If nothing in the
body updates that value, the condition never flips and the loop runs
forever. File that away — you'll want it in about three minutes.
-->

---

## The `while` loop

```python
# Lets watch a value grow past a limit
value = 1

while value < 6:
    print(value)
    value = value * 2

print('Done')
```

Output: `1` `2` `4` `Done`

<!--
A while loop runs its body repeatedly as long as the condition is True, then
moves on. Two details matter more than the syntax.

First, the condition is checked BEFORE the body ever runs — which means a
while loop can execute zero times if the condition starts out False. Worth
demoing: set value = 10 and watch nothing print at all.

Second, walk this out loud: value gets checked, printed, doubled, checked
again. The moment value becomes 8, the condition 8 < 6 is False and the loop
ends — so 8 never prints. That "the check happens before the print" detail is
exactly what trips people up the first few times.

Ask them to predict the last number printed before you run it. Plenty will
say 8.
-->

---

## Sentinel values

```python
# Lets keep asking until the password matches
password = 'star'
user_input = input('Enter the password: ')

while user_input != password:
    print('Wrong password. Try again.')
    user_input = input('Enter the password: ')
```

<!--
A sentinel value exists purely to signal "stop" — it is not real data, just
an agreed-upon flag. Here it's the string 'star': the loop runs exactly as
long as the user has not typed it.

The structural detail worth pointing at, because students get it wrong
constantly: the input line appears TWICE. Once before the loop, to give the
condition something to check on the very first pass, and once inside the
body, to give it a fresh value every pass after that. Delete either one and
the loop breaks in a different way.

Same shape works with numbers — sum values until the user enters 0, then
report the average. One trap in that version worth naming out loud: if the
very first input is the sentinel, your count is still zero when you divide,
and you get a ZeroDivisionError. Any sentinel-driven average needs a
"nothing was entered" guard. That bug ships constantly.
-->

---

## The classic forgotten-update bug

```python
# Lets watch a loop that never ends
score = 1

while score > 0:
    score = score * 2
    print(score)
```

`score` only ever gets bigger. `score > 0` never flips.

<!--
This is the 5.1 warning showing up for real. Score only grows, so the
condition is never going to become False — this program runs until you kill
it. Show them Ctrl+C or the stop button in the notebook now, before they
need it at 11pm.

Not every infinite loop is a bug, by the way. A `while True` that checks for
input every frame in a game is doing exactly its job. It's the accidental
ones that hurt.

The habit worth building while stakes are low: guard your condition with <
or >, never with ==. An off-by-one increment can sail right past an exact
target — stepping by 2 from 1 skips 8 entirely — and leave you stuck
forever. It can never sail past "greater than."

The notes have three more while-loop workouts: peeling digits apart with %
and //, Euclid's GCD algorithm, and a sentinel-driven average. Point at them
rather than walking them.
-->

# 5.4–5.5 Counting and `for` loops

<!--
Counting iterations is such a common job that it gets its own section. Then
the for loop, which is built for a different and extremely common job: walk
every item in a container with no manual bookkeeping at all.
-->

---

## Counting with a while loop

```python
# Lets count from 1 to 5
loop_variable = 1

while loop_variable <= 5:
    print(loop_variable)
    loop_variable = loop_variable + 1
```

Output: `1 2 3 4 5`

<!--
Three pieces of bookkeeping, and the student owns all three: the starting
value, the condition, and the update. Point at each one as you name it —
that ownership is exactly what the for loop is about to take away.

loop_variable starts at 1 and climbs by 1 every pass. The instant it hits 6
the condition is False and the loop stops, which is why the count ends at 5.

And yes — leave off that last line and you get the exact same infinite loop
from the previous slide, just wearing a counting costume. Say that
explicitly; it is the same bug in a friendlier outfit.

Nothing says a counting loop goes up by one. Decrement instead, or step by
any amount — `variation -= 5` counts down by fives. Compound operators from
chapter 2 do the work; the shape of the loop never changes.
-->

---

## The `for` loop takes the bookkeeping away

```python
# Lets greet everyone on the list
for name in ['Kai', 'Sam', 'Alex']:
    print(f'Hi {name}!')

print('Done')
```

No counter to write. No condition to get wrong. Stops when the container runs out.

<!--
A for loop iterates over each element in a container, assigning a variable to
the current element on every pass, until every element has been visited.

Put it directly against the previous slide: the while version made you own
the starting value, the update, and the condition. The for loop takes all
three off your hands the moment you're walking a container rather than
counting toward a number. That is the entire trade.

This is the pattern you reach for any time "do this once per item" is the
actual job — and that is most of the time in business code.

Two variations worth naming without slides. A string is a sequence too, so
`for char in 'Yes'` walks it character by character with no extra syntax.
And `reversed(names)` walks a container backward without touching the
original — handy when most-recent-first matters.
-->

---

## A running total

```python
# Lets average a list of daily revenues
daily_revenues = [2350.25, 1800.50, 1795.00, 2050.25]

total = 0
for day in daily_revenues:
    total += day

average = total / len(daily_revenues)
```

<!--
This is the accumulator pattern, and it is the single most common thing you
will do inside a for loop all semester: start a variable at zero outside the
loop, add to it on every pass, use it after the loop ends.

Point at where `total = 0` sits. Outside the loop. Move it inside and the
total resets every pass, leaving you with just the last value — a classic
bug and worth demoing live because the output looks almost plausible.

Connect it back: this is the revenue cousin of the sentinel-driven average
from the while section. Except now the container itself tells us when to
stop, so there's no sentinel, and len() gives us the count for free — which
means no ZeroDivisionError guard needed either.

That's a real argument for for loops over while loops, not just a
convenience.
-->

---

## Dictionaries hand you keys

```python
# Lets loop over a dictionary
channels = {'MTV': 35, 'CNN': 28}

for name in channels:
    print(f'{name} is on channel {channels[name]}')
```

Output: `MTV is on channel 35` `CNN is on channel 28`

<!--
Looping over a dictionary gives you KEYS, never values, in insertion order.
Make them predict the output before you run it; a good number will expect
the numbers.

The detail that catches people: writing `for value in channels` would still
hand you 'MTV' and 'CNN'. The variable name doesn't change what Python gives
you — it is just a label you chose. Rename it to something honest.

You look the value up yourself with the key, exactly as this slide does.

Flag the forward reference: in chapter 9 we'll meet .items(), which hands
you the key and the value together and makes this pattern much cleaner. For
now, know that a bare loop over a dictionary means keys.
-->

# 5.6 Counting using `range()`

<!--
A for loop needs a container to walk. But what if there isn't one — you just
want to run something exactly ten times? That is precisely the job range was
built for.
-->

---

## What each call produces

| Call | Sequence generated |
|-|-|
| `range(5)` | `0 1 2 3 4` |
| `range(3, 7)` | `3 4 5 6` |
| `range(0, 10, 2)` | `0 2 4 6 8` |
| `range(5, 0, -1)` | `5 4 3 2 1` |

<!--
range() generates a sequence of integers — starting at a value that IS
included, ending BEFORE a value that is not, stepping by an amount you
choose. Up to three arguments: start, stop, step.

The first row is by far the most common thing you'll type. Every other row is
a variation to recognize on sight rather than memorize.

Row four is worth a beat: a negative step counts down, but notice start and
stop had to flip their relationship too. Get that backwards and you get an
empty sequence and no error at all — the loop simply never runs, which is a
genuinely confusing silent failure.

One under-the-hood note, one sentence: range is lazy. It doesn't build a
list in memory, it hands out integers as the loop asks. That's why printing
a range shows you `range(0, 5)` rather than the numbers — wrap it in list()
if you actually want to see them.
-->

---

## Run something exactly N times

```python
# Lets run something exactly 5 times
for i in range(5):
    print(i)
```

Output: `0 1 2 3 4`

<!--
Start at zero, stop before five. This single-argument call is the one you
will type constantly — any time you need "do this N times" and don't care
about the actual numbers.

Notice i starts at 0, not 1. That is deliberate and it lines up with list
indexing, which they'll meet properly in chapter 9. If you genuinely need 1
through 5, that's range(1, 6) — and the awkwardness of that 6 is exactly the
subject of the next slide.

Good place to pause and let them write one. Have them print their own name
three times. It takes thirty seconds and it's the first loop most of them
will have written unaided.
-->

---

## `range(X, Y)` never includes Y

`range(0, 5)` stops **before** 5 — you get `0 1 2 3 4`, never `5`.

**This trips up anyone coming from spreadsheet thinking**, where `A1:A5`
includes both ends.

<!--
Python ranges only ever include the start, never the stop. It feels
arbitrary until it bites you once, and then you never forget.

The spreadsheet comparison on the slide is the one that lands with this
room specifically. In Excel, A1:A5 is five cells including both ends. In
Python, range(1, 5) is four numbers and stops at 4. Their intuition is
actively working against them here.

The reason it's designed this way, worth one sentence: range(len(items))
gives you exactly the valid index positions of a container, with no
off-by-one arithmetic. Once they're indexing lists in chapter 9 this
convention starts feeling like a gift rather than a trap.

Until then: when you write a range, say the last number it produces out loud.
Stop minus one. Every time.
-->

# 5.7–5.9 Choosing, nesting, and building up

<!--
Three short sections that go together: which loop to reach for, what happens
when you put one inside another, and the working habit that keeps a nested
program from becoming unfixable.
-->

---

## Which loop do you actually reach for?

- `for` — the iteration count is knowable up front, or you're walking every
  element of a container
- `while` — the number of iterations genuinely is not knowable ahead of time

<!--
Show the same job written both ways first. `i = 0; while i < 100: ...; i +=
1` versus `for i in range(100):`. Identical result, and the for loop is the
one to write — there's no update line to accidentally forget, because range
advances the position for you.

Then the rule on the slide. The tell to watch for: if you find yourself
hand-rolling a counter with += 1 inside a while loop, and you knew the
iteration count the whole time, you wanted a for loop.

The honest version of the while case is user input and sentinels — you have
no idea how many times someone will type the wrong password.

These are guidelines, not laws, but they'll be right the overwhelming
majority of the time.
-->

---

## Nested loops multiply, don't add

```python
# Lets pair every row against every column
for i in range(5):
    for j in range(3):
        print(f'{i},{j}')
```

Outer 5 times, inner 3 times → the inner body runs **15** times. Not 8.

<!--
Ask the room to predict the total before you run it. Someone will say 8.
That wrong answer is the whole lesson.

The inner loop restarts FULLY on every single outer iteration. i stays fixed
while j runs 0, 1, 2 underneath it, then i advances and j starts over from
zero. That is what makes it multiplication.

A nested loop is the natural move any time you need every COMBINATION of two
things — one item from group A against every item in group B. Every
two-letter domain name is 26 times 26, which is 676 combinations from six
lines of code.

Say the performance warning once, because they'll hit it eventually: nesting
multiplies the work. Two loops over a thousand items each is a million
iterations. That's fine on a laptop and a real problem on a big dataset.
-->

---

## Building a grid

```python
# Lets print a rectangle of asterisks
for row in range(2):
    for col in range(3):
        print('*', end=' ')
    print()
```

Output: two rows of `* * *`

<!--
This is the shape nested loops were made for: anything with rows and columns.
A rectangle of asterisks, seat labels in a theater, a table of numbers, a
calendar.

The outer loop picks the row; the inner loop fills that entire row before the
outer one moves on.

The line to point at is the bare `print()` at the bottom. It's indented with
the OUTER loop, not the inner one, which is what ends each row. Move it one
level in and everything collapses onto a single line. Demo that — it's a
one-character change with a dramatic result, and it's the clearest
demonstration of why indentation is syntax in Python.

`end=' '` is what keeps the asterisks on one line in the first place;
without it, print starts a new line every time.
-->

---

## Don't write the whole thing at once

**incremental programming:**
Building a program from a small working version, growing it piece by piece,
testing after every addition.

A 40-line program with five bugs is five bugs tangled together.

<!--
This is a habit-forming slide placed here on purpose, because nested loops
are exactly where people start trying to write the whole program in one
sitting.

Debugging one broken line in a five-line program is quick. Debugging one
broken line buried in forty lines you have never actually run is a different
kind of pain — the kind that eats an entire evening.

Walk the phone-decoder example from the notes verbally, three versions.
Version 1 does nothing clever: just prove the loop visits every character.
Version 2 echoes digits through and marks everything else with a placeholder
'?' plus a FIXME comment. Version 3 fills in one letter range at a time,
testing each before adding the next.

The rule that makes it real: a finished program has zero FIXMEs left. If you
find one after you thought you were done, that's the process telling you
exactly where to look.

Tell them to build their homework this way. The ones who do, finish.
-->

# 5.10–5.11 `break`, `continue`, and loop `else`

<!--
Sometimes the cleanest loop has an escape hatch, rather than stuffing every
possible exit condition into the loop's own expression.

Then the else clause nobody expects, which exists precisely to answer "did
this loop get interrupted?"
-->

---

## `break` exits immediately

```python
# Lets find a meal that spends the money exactly
for num_tacos in range(6):
    for num_empanadas in range(7):
        if (num_empanadas * 3) + (num_tacos * 4) == 20:
            break
    ...
```

`break` only ever exits the loop **directly** wrapping it.

<!--
break doesn't wait for the condition to become False on its own — it cuts the
loop off mid-stride the instant you tell it to.

The caption is the part worth real time, because it surprises everyone: this
break escapes the INNER loop only. The outer loop happily continues to the
next value of num_tacos. A nested search needs one break per level, plus a
flag or a check to trigger the outer one.

Draw that on the board — two boxes, break punching through the inner box and
stopping at the wall of the outer one.

That awkwardness is real, and it is one honest argument for wrapping a
nested search in a function and using `return` instead, which ends everything
at once. That's chapter 6 — plant it, don't teach it.
-->

---

## `continue` skips the rest of this pass

```python
# Lets only print multiples of 3
for num in range(20):
    if num % 3 != 0:
        continue
    print(num)
```

Output: `0 3 6 9 12 15 18`

<!--
continue doesn't leave the loop the way break does — it abandons the rest of
this one pass and jumps straight to the next iteration. Every number failing
the divisible-by-three check gets skipped before print ever runs.

Be honest about the alternative: you could wrap the print in an `if num % 3
== 0` instead, and it would be functionally identical. continue reads as
"nope, next one" and stays out of the way when there are several lines left
to skip — that's its real argument, not brevity.

Then the style warning, which matters more than either keyword. break and
continue change control flow with no obvious visual marker, and a teammate
skimming your code can walk right past one. Use them when the intent is
genuinely clearer, not just because they're shorter to type.
-->

---

## The `else` nobody expects

```python
for name in names:
    if found(name):
        break
else:
    print('Searched everything, no match.')
```

Runs only if the loop finished **without** `break` firing.

<!--
This surprises almost everybody, and the misread is always the same: loop
else has nothing to do with an if-branch failing. It answers exactly one
question — did this loop get interrupted by a break?

Contrast it with code placed right after the loop, which runs EVERY time,
break or no break. Loop else only fires on the clean, uninterrupted finish.

Which gives you the one use case worth remembering, and it's on the slide:
search a list, break the instant you find a match, and put "not found" in the
else — because that's the only branch that runs when the search genuinely
came up empty.

Without loop else you'd need a found = False flag, set it True before
breaking, and check it afterward. Show that version on the board so they can
see what the else replaces. Otherwise this looks like trivia rather than a
tool.
-->

# 5.12–5.13 `enumerate()` and putting it together

<!--
One more tool — getting the position alongside the value — and then a
capstone that uses every loop idea in the chapter at once.
-->

---

## `enumerate()` gives you index and value

```python
# Lets get index and value together
origins = [4, 8, 10]

for index, value in enumerate(origins):
    print(f'Element {index}: {value}')
```

Output: `Element 0: 4` `Element 1: 8` `Element 2: 10`

<!--
A plain for loop hands you the value and never the position. Plenty of real
tasks need both — printing a numbered list, or flagging "row 3 was the
problem."

Show the two clunky alternatives on the board first, because the contrast is
what sells this. One: `for index in range(len(origins))` and look the value
up yourself every pass — works, but it's more machinery than the job needs.
Two: loop over values and call .index(value) to find the position — which
BREAKS the moment a value repeats, because .index() always returns the first
match. That's a genuine bug, not just inelegance.

enumerate wraps the container and yields an index, value pair each iteration,
with no bookkeeping and no duplicate problem.

The mechanism underneath is unpacking: `x, y = (7, 3)` assigns both at once,
and `index, value` on the left of the for statement is the same thing. Name
them whatever fits — row and price, position and beverage. Order is what
matters, not the name.
-->

---

## Capstone: tallying dice rolls

```python
# Lets roll 1000 times and count each sum
counts = {}
for total in range(2, 13):
    counts[total] = 0
for roll in range(1000):
    counts[random.randint(1, 6) + random.randint(1, 6)] += 1
```

<!--
The task: roll two dice repeatedly and print a text histogram of how often
each sum came up. Built incrementally, exactly the way 5.9 said to.

Step one, not on the slide, is proving a single roll works — two randints and
a sum, printed. Nothing counted yet. Do that live before showing this.

This slide is step two: a dictionary keyed by every possible sum, initialized
to zero, then incremented once per roll. That's the counting pattern from
5.4, tallying into a dictionary instead of a single variable.

Point at why the first loop exists at all — every key has to exist before you
can += into it, or you get a KeyError on the first roll. That's a real bug
they will hit, and chapter 9's .get() is the eventual fix.

Step three wraps this in a while loop asking "how many more rolls?" — a for
loop nested inside a while loop, each doing the job it's suited for from 5.7.
-->

---

## Every tool from this chapter, together

```python
# Lets draw the histogram from the tally
for total, count in counts.items():
    print(f'{total}s: {"*" * count}')
```

A `for` inside a `while`. A dictionary instead of a dozen variables. String
multiplication for the bars.

<!--
One asterisk per occurrence, printed once per key, using the same
index-and-value unpacking idea as enumerate — applied to a dictionary's
items() this time.

Run it. The histogram peaks at 7 every single time, and that's worth thirty
seconds: seven has six ways to roll it, two and twelve have exactly one each.
The shape of the output is a real statistical fact falling out of the code,
and students find that genuinely satisfying.

Then the actual point of a capstone, and say it plainly: nothing here is new.
Every piece was covered earlier in this chapter. Fluency isn't learning more
syntax — it's getting comfortable reaching for the right combination of what
you already have.

If the room is fried, stop here rather than pushing into questions.
-->
