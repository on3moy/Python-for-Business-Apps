# 4.1–4.2 Branching and equality

<!--
We start with the mechanics of a branch, then the operator that asks the
question in the first place.

The single most important mechanic in the whole chapter shows up in this
block — "the first True wins" — and everything about ranges later depends
on it. Do not rush it.
-->

---

## Everything so far ran top to bottom

Every line. Every time. No choices.

**branch:**
A sequence of statements only executed under a certain condition.

<!--
That is the whole conceptual leap of this chapter, and it is worth one
slow sentence: up to now the interpreter has had no discretion. From here
on it does.

The analogy that lands with this room, because half of them have worked
one: a hostess stand. Party of one goes to the counter, party of two gets
a small table, anything else gets a large table. That is an
if-elif-else, and they have been executing it manually for years.

Push them for their own examples before moving on. Shipping thresholds,
late fees, overtime rules -- every business policy is a branch somebody
wrote down. The syntax is new; the thinking is not.
-->

---

## The shape of it

```python
# Lets give a discount to our long time customers
years_active = 7

if years_active > 5:
    discount = 0.10
```

Two things to notice: the **colon**, and the **indent**.

<!--
Point at the colon and the indent physically. Those two characters are the
entire syntax of a block in Python, and they will reappear in every loop,
every function, and every class for the rest of the semester.

Python uses whitespace to decide what belongs to the branch. No braces, no
end keyword -- the indentation IS the grouping. That is unusual among
programming languages and it is the thing most likely to bite them in
week one.

Run it with years_active = 7 and then with 3. With 3, nothing happens at
all -- no output, no error, discount never gets created. Ask what happens
if you then try to print(discount). That NameError is a useful thing to
meet on purpose.
-->

---

## `if` / `elif` / `else` — the first True wins

```python
# Lets decide what happens to this invoice
if status == 'paid':
    print('File it.')
elif status == 'pending':
    print('Wait.')
else:
    print('Send a reminder.')
```

Exactly one branch runs. Never both, never neither.

<!--
This is the mechanic to over-emphasize. Say it three times if you have to:
Python checks the conditions in order, top to bottom, takes the FIRST one
that is True, runs that block, and skips every remaining branch without
even evaluating it.

The else is the catch-all -- it runs only when every condition above it
failed, which guarantees that exactly one branch always runs.

Walk status = 'overdue' through it out loud, branch by branch, so they see
the two failed tests before the else fires.

Everything about ranges in the next section depends on this "first wins"
behavior. If someone is fuzzy on it now, they will be lost in ten minutes.
Take questions here rather than later.
-->

---

## `==` compares. `=` assigns.

`if num_years == 50:` ✅ — asks a question, gets back True or False

`if num_years = 50:` ❌ — SyntaxError

<!--
Double equals is a comparison, not an assignment. Python evaluates the
question and hands back a Boolean -- a type with exactly two possible
values, True or False, with no third option and no maybe. Every comparison
in this chapter evaluates down to one of those two, which is exactly what
an if statement is built to consume.

A single equals inside an if is a syntax error, because Python knows an
assignment cannot double as a condition. This is the single most common
typo in the entire chapter. Everyone hits it at least once -- so when the
traceback shows up tonight, they will already know what it means.

Also name the partner operator here: != asks whether two values do NOT
match. Same idea, opposite answer.

Good live example if there's time: the even/odd check. user_num % 2 == 0
combines chapter 2's modulo with this chapter's comparison, and it is the
single most common use of modulo they will ever write.
-->

# 4.3–4.4 Ranges and relational operators

<!--
Almost nothing in business is a single equality check. Salary bands, age
brackets, tax tiers, shipping weights -- real data comes in ranges.

This block is where "first True wins" starts paying off, and where the
operators that make ranges possible get formalized.
-->

---

## The sequential trick

```python
# Lets sort a player into an age group
if age < 6:
    print('No teams')
elif age < 8:
    print('U8')
elif age < 10:
    print('U10')
```

`age < 10` really means **8 or 9** — because `age < 8` was already False.

<!--
This clicks or it doesn't, and it is worth the full two minutes. Walk age =
9 through it out loud, branch by branch: is 9 less than 6? No. Less than 8?
No. Less than 10? Yes -- U10.

Then ask the room where the lower bound of that last branch came from,
because nobody typed an 8 into it. The answer is that the branch above it
already failed, and that failure IS the lower bound.

That is the whole trick, and it only works because of the "first True wins"
rule from the previous section. Make the connection explicit.

Same pattern with money instead of ages if the room wants a business
framing: insurance priced by age band is the classic, under 16 free, under
25 expensive, else standard.
-->

---

## You only write the top of each range

The bottom is implied by every branch above it.

Which means **order matters enormously** — flip two branches and you get
wrong numbers with no error at all.

<!--
This is the consequence slide, and the second sentence is the one that
matters.

Demo the failure live, because it is silent and that is what makes it
dangerous. Take the age brackets and move the `age < 10` branch to the
top. Now every single player lands in U10 -- a nine-year-old, a
seven-year-old, a three-year-old. No error, no warning, no traceback. Just
a completely wrong roster.

This is the shape of the bug they will actually ship: code that runs
perfectly and produces wrong numbers. Nobody notices until a customer
complains or a report doesn't reconcile.

The habit: when you write a sequential range chain, order it from the
narrowest condition outward, and test a value from every single band
before you trust it.
-->

---

## Relational operators

| Operator | Meaning | x is 3 |
|-|-|-|
| `<` | less than | `x < 4` → True |
| `>` | greater than | `x > 2` → True |
| `<=` | less than or equal | `x <= 3` → True |
| `>=` | greater than or equal | `x >= 4` → False |

`<=` ✅ · `=<` ❌ — the `=` always goes second.

<!--
Four operators, and they already know every one of them from grade-school
arithmetic. Python just requires two-character symbols rather than the
single glyphs from a whiteboard.

Do not read the table row by row. Spend the time on the caveat line
instead: when an operator pairs with equals, the equals sign always comes
second. Writing =< is a syntax error, and it is an easy one to make on
muscle memory from other languages or from writing it by hand.

The pair worth dwelling on is < versus <=, because that single character is
the difference between including a boundary value and excluding it. We come
back to exactly that in a few slides when we price movie tickets, and it is
where the real bugs live.
-->

---

## Chaining reads like maths

```python
# Lets check a value sits inside a range
if 10 < x < 15:
    print('In range')
```

Evaluated left to right — and `10` is never compared to `15`.

<!--
Python lets you chain comparisons the way you would write them on paper,
and it means exactly what it looks like: x is greater than 10 and less than
15.

This is genuinely unusual -- most languages do not allow it, and in many of
them writing 10 < x < 15 silently produces nonsense. In Python it does the
right thing, so use it.

The caption is the fine print: it is evaluated as two separate comparisons
joined together, so the two endpoints are never compared to each other.
That matters only in strange cases, but it is worth saying once.

The alternative spelling with `and` is coming up in the next section, and
both are correct. Chaining reads better for a simple between-two-values
test; `and` reads better the moment the two conditions aren't about the
same variable.
-->

# 4.5–4.6 Combining conditions, and gaps

<!--
Everything so far tests one condition at a time. Real business rules are
almost never that simple -- eligibility might depend on tenure AND balance,
or on either of two qualifying criteria.

Then the case the sequential trick can't handle: ranges with holes in them.
-->

---

## Logical operators

| Operator | True when |
|-|-|
| `a and b` | **both** are True |
| `a or b` | **at least one** is True |
| `not a` | the operand is False |

Python spells them out — no `&&`, `||`, `!`.

<!--
and demands both sides be True. or is satisfied by either side alone. not
simply flips a single condition. Three operators, and they cover every way
you will ever need to combine conditions.

The caption is a genuine kindness of the language worth pointing out:
Python uses plain English words rather than the symbol soup other languages
use. Anyone who has seen && or || in JavaScript or Excel formulas can
forget them here.

The one to watch is `or`, because English is ambiguous about it. "Coffee or
tea" in conversation means one or the other, not both. Python's `or` means
at least one, and it is perfectly happy when both are True. That mismatch
between English and code causes real bugs.
-->

---

## Building a range with `and`

```python
# Lets classify the cable channel
if (user_channel >= 2) and (user_channel <= 499):
    channel_type = 'standard'
elif (user_channel >= 1002) and (user_channel <= 1499):
    channel_type = 'hd'
else:
    channel_type = 'error'
```

<!--
Each branch now states both of its bounds explicitly, joined with and. Ask
for both, get the overlap.

Contrast the two styles out loud, because both are correct and they should
be able to choose deliberately:

An IMPLICIT range is the plain elif chain from the last section -- each
condition states only its lower bound and lets the branch above it supply
the upper one. It reads beautifully when your ranges are continuous with no
gaps.

An EXPLICIT range, like this slide, spells out both bounds with and. It is
the right choice the moment your ranges have gaps between them, which is
exactly the case here -- channels 500 through 1001 simply do not exist.

Neither is more correct. Pick the one that reads better for the range you
are describing.

Note the parentheses aren't strictly required -- comparison binds tighter
than and -- but they cost nothing and remove all doubt.
-->

---

## Let `else` swallow the gap

```python
# Lets price a movie ticket
if user_age <= 12:
    movie_ticket_price = 11
elif user_age >= 65:
    movie_ticket_price = 12
else:
    movie_ticket_price = 14
```

You never had to name the middle group.

<!--
Not every range is a staircase. Movie tickets: children 12 and under,
seniors 65 and up. Everyone from 13 to 64 is the gap -- and the gap is the
biggest group of customers.

The elegant part is that you never describe that group at all. Two named
bands, and else catches literally everyone else. Ask the room how they'd
write the middle branch explicitly -- age >= 13 and age <= 64 -- and then
point out that it is redundant and gives you two more numbers to get wrong.

When the gap is in the MIDDLE of what you're validating rather than at the
edges, you need or instead. Office numbers 100-150 and 200-250 exist with
nothing between: one condition per valid block, joined with or. That's in
the notes; mention it, don't slide it.
-->

---

## Watch the boundaries

Is 12 a child? Is 65 a senior?

`<=` and `>=` say yes. `<` and `>` say no.

**Off-by-one at a boundary is the most common bug in pricing logic.**

<!--
Pause here. This is the bug they will actually ship.

Take the movie ticket example and ask the room directly: does a child turning
13 today pay 11 dollars or 14? Now find the single character in the code
that decides it. One character, eleven dollars, every transaction, forever.

Nobody notices this class of bug from reading the code, because the code
looks completely reasonable either way. It surfaces when a customer
complains, or when someone reconciles a report three weeks later.

The habit worth building: for every boundary in your logic, write down the
exact value that sits on it and test that specific number. Not 10 and 20 --
test 12 and 13, test 64 and 65. The boundary is the only place the bug can
hide.
-->

# 4.7–4.8 Structure and data types

<!--
Two branching structures that look nearly identical and behave completely
differently -- then what happens when you compare things that aren't
numbers.
-->

---

## Separate `if`s tag everything that applies

```python
# Lets label a customer
if balance > 1000:
    print('Premium')
if years > 5:
    print('Loyal')
```

Change the second `if` to `elif` and only **one** label ever prints.

<!--
This is the most consequential slide in the section and it hinges on three
characters.

Two standalone ifs are evaluated independently. Python checks the first
and then, regardless of the outcome, checks the second on its own terms. A
customer who is both high-balance and long-tenured prints BOTH labels.

Chain the same two conditions with elif and the second branch is only
evaluated if the first failed -- so at most one label ever prints, for that
same customer. Same conditions, same order, structurally different result.

Write both on the board side by side and run them against balance = 5000,
years = 10. Two lines of output versus one.

The rule to state plainly:
- Separate ifs when you want to tag everything that applies.
- if/elif when you want to pick exactly one.

Same-looking code. Completely different month-end report. That is not an
exaggeration -- this exact confusion produces double-counted customers in
real reporting.
-->

---

## Nesting

```python
# Lets calculate the sales bonus
if sales_type == 2:
    if sales_bonus < 5:
        sales_bonus = 10
    else:
        sales_bonus = sales_bonus + 2
else:
    sales_bonus = sales_bonus + 1
```

Two levels is fine. Four means you want logical operators instead.

<!--
The inner if is only reached when the outer one is True -- so you are
asking a follow-up question that only makes sense once the first answer is
known. That's the legitimate use of nesting: a genuinely dependent
question.

Trace one value through both levels out loud, then trace a value that fails
the outer test and show that the entire inner block never runs.

The caption is the judgment call and it is worth saying with some force. If
you find yourself three or four levels deep, the code has stopped being
readable and the conditions almost certainly want to be combined with `and`
instead. Deeply nested branching is one of the clearest signals that logic
needs restructuring -- and you will see plenty of it in code you inherit.
-->

---

## Never compare floats with `==`

```python
print(0.1 + 0.2 == 0.3)
```

Output: `False`

Compare with `<` or `>`, or check the difference is small enough to ignore.

<!--
Run this live. The gasp is the point -- it is what makes the lesson stick,
and no amount of explaining beats watching it happen.

Then explain: floating-point numbers are stored as binary approximations,
and 0.1 has no exact binary representation any more than one-third has an
exact decimal one. The stored value is very slightly off, the errors
accumulate through the addition, and the result is not bit-for-bit
identical to 0.3.

This is not a Python quirk. It is how essentially every language on every
processor handles floats, and it matters enormously in financial code.

The practical fix is the caption: compare with < or >, or test whether the
difference is smaller than some tolerance you choose.

Two related type rules worth naming without slides. Strings compare
character by character and are case sensitive -- 'Tuesday' == 'tuesday' is
False, and that capital T has ruined more afternoons than I can count. And
operators that do not exist in Python: => and <> are both syntax errors.
The notes have the full comparison table by type.
-->

# 4.9–4.10 Membership and evaluation order

<!--
An operator that reads like English and does a genuinely useful job, then
the rules that decide what your condition actually means when you combine
several things.
-->

---

## `in` / `not in`

```python
# Lets see if a name is on the roster
roster = ['Alves', 'Messi', 'Fabregas']

if name in roster:
    print(f'Found {name}.')
```

Enormously useful once your data comes from a spreadsheet or an API.

<!--
This is one of Python's genuinely pleasant features -- the code reads like
the sentence you'd say out loud, and it replaces what would otherwise be a
loop comparing against every element by hand.

It works on strings too, which surprises people. A string is a sequence of
characters, so `'/1.1' in request_str` finds a substring inside a larger
string. That is how you'd check an HTTP request, a file extension, or a
product code prefix -- and it is exactly what they'll reach for after
chapter 8.

not in is the mirror image and reads just as cleanly: `if name not in
roster`.

Worth one sentence on `is` versus `==` while we're near the topic: `is`
asks "are these literally the same object," `==` asks "do these have the
same value." You almost always want ==. Python quietly reuses objects for
small integers, which means `is` can appear to work and then fail on a
bigger number. Don't build logic on it. The notes cover why.
-->

---

## Dictionaries: keys, not values

```python
my_dict = {'A': 1, 'B': 2, 'C': 3}

print('B' in my_dict)
print(3 in my_dict)
```

Output: `True` then `False`

<!--
This trips people up constantly, so make them predict both lines before you
run either.

'B' is a key, so the first check is True. 3 is a value, not a key, so the
second is False -- even though 3 is very visibly sitting right there in the
dictionary.

The reason is that `in` on a dictionary searches keys and only keys. That
is a deliberate design choice, not an oversight: looking up a key is
instant regardless of dictionary size, while searching values would mean
checking every entry.

If you genuinely need to search values, `3 in my_dict.values()` does it --
mention it, and flag that we'll cover values() properly in chapter 9.

The habit: whenever you write `in` against a dictionary, say "keys" out
loud in your head.
-->

---

## The pecking order

1. `( )` parentheses
2. `* / % + -` arithmetic
3. `< <= > >= == != in` comparison
4. `not` → `and` → `or`

**Use parentheses even when you don't need them.**

<!--
The summary line that covers ninety percent of cases: arithmetic happens
before comparison, and comparison happens before logic. That ordering is
what lets you write `y * z < x + 1` and have it mean what you'd expect --
both sides of the comparison get computed first.

Trace one live: with x=7, y=6, z=3, the expression `y * z < x + 1 or z == 3`
becomes 18 < 8, which is False, or z == 3, which is True -- so False or True,
which is True. Step through it on the board rather than asserting it.

Now the trap worth naming: `not` binds more tightly than almost anyone
expects, because English reads "not" as applying to the whole clause that
follows. Python disagrees. `not a == b` means `not (a == b)`, and
`not x + y < 5` means `not ((x + y) < 5)`.

Neither raises an error. That is precisely what makes it dangerous -- the
code runs, it just runs a different condition than the one in your head.

Which is why the caption is the actual lesson. Parentheses cost nothing. A
reader, including you in six months, should never have to reconstruct this
list in their head to know what a condition means.
-->

# 4.11–4.12 Indentation and one-line branches

<!--
We close with the whitespace rules that make Python Python, and a compact
form for the simplest possible branch.
-->

---

## Indentation is syntax, not style

**code block:**
A series of statements grouped together, defined by indentation level.

- A new block follows a colon
- It must be indented **more** than the one before

Four spaces. Always four spaces.

<!--
In most languages indentation is a courtesy to the reader. In Python it is
the grammar -- it is how the interpreter knows what belongs to what. Get it
wrong and the program either fails or, worse, runs with a line in the wrong
block.

Then the warning that saves a support email: never mix tabs and spaces.
Your editor may draw a tab as four spaces, but Python does not care what it
looks like -- a tab is a tab and a space is a space. Mixing them raises
IndentationError while the code looks perfectly aligned on screen the whole
time. That is a genuinely maddening bug because your eyes cannot see it.

Show them the VS Code setting live if there's time -- insert spaces, tab
size four. Once, today, and it never comes up again.

Nesting works the same way, one step per level: an if inside an if just
gets indented twice, and each step tells Python "this belongs to the thing
above me."
-->

---

## One line instead of four

```python
# The long way
if order_total > 50:
    shipping = 0
else:
    shipping = 7

# The same thing
shipping = 0 if order_total > 50 else 7
```

<!--
Four lines to assign a single variable one of two values. Nothing wrong
with that -- it is perfectly readable -- but it collapses.

Read the one-liner out loud as a sentence: shipping is 0 if order_total is
over 50, else it's 7. It reads almost like English, which is why people
like it.

The general shape, worth writing on the board:
    expr_when_true if condition else expr_when_false

Three operands, which is why it's sometimes called a ternary operation. And
the part that catches people: the condition in the MIDDLE is evaluated
first, which is not the order you read it in.

Use it sparingly. It is good for a simple assignment like this one and bad
the moment the branches do more than produce a value, or the condition gets
long. Plenty of Python developers dislike these and the complaint is fair.

If you can't read it aloud in one breath, write the four-line version.
-->
