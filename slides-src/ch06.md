# 6.1–6.2 Defining and calling

<!--
We start with vocabulary and the single most important distinction in the
chapter: print versus return. If they leave today with only that, the lecture
worked.

Expect 12-15 minutes on this block. It is the foundation and it is where the
confusion that shows up in week 10 actually starts.
-->

---

## Stop retyping the same calculation

Copy the same formula into three places, and you will eventually copy it wrong once.

**function:**
A named series of statements you invoke by name instead of retyping. `def` creates one.

<!--
Ask the room first: where have you already retyped the same few lines in a
homework? Somebody will mention a tax or commission calculation. Use their
example instead of mine if you get a good one.

The motivation is almost embarrassingly simple — naming a block of code means
you never retype it, and there is exactly one place to fix when it is wrong.

Do not define anything yet. Sell the problem before you sell the solution;
the syntax lands better when they already want it.
-->

---

## Writing it once, calling it twice

```python
# Lets convert Fahrenheit to Celsius, written once
def f2c(f):
    return (f - 32.0) * (5.0 / 9.0)

c1 = f2c(f1)
c2 = f2c(f2)
```

The calling code no longer cares *how* the conversion works — only that `f2c()` answers.

<!--
Walk the def line character by character: the keyword, the name, the
parentheses, the parameter inside them, the colon, the indent. They have seen
colon-and-indent twice already with if and for, so call that back explicitly.

Then the point that actually matters: look at what DISAPPEARED from the
bottom two lines. No formula, no 32, no 5/9. Just a name and a value.

Live demo cue: define it in the notebook, then call it with 212 and 32. Then
break it on purpose — delete the return — and ask what they expect to print.
That sets up the next slide.
-->

---

## The four moving parts

|Part|What it is|In `f2c`|
|-|-|-|
|Definition|`def` line + indented body|`def f2c(f):`|
|Call|Name + `()`|`f2c(98.6)`|
|Parameter|Named input in the definition|`f`|
|Argument|Value handed over at call time|`98.6`|

<!--
Four terms, one anatomy. Definition is written once and just sits there.
Call is what makes something happen, and you write it as many times as you
like.

Parameter versus argument gets used interchangeably in hallway conversation,
but be precise here because the exam is precise: parameter is the name in the
definition, argument is the value at the call site. My memory hook is that
both "parameter" and "placeholder" start with P.

Worth saying out loud: defining a function produces NO output. Students run
the cell, see nothing, and assume it failed.
-->

---

## `print` shows you. `return` hands it back.

```python
# Lets see why the difference matters
def shown(qty, price):
    print(qty * price)

total = shown(3, 12.50)   # total is None
```

A function with no `return` still hands something back: `None`.

<!--
This is the slide. If we are behind schedule, cut something else to protect
it.

The trap is that at the top of a notebook cell both versions LOOK identical —
Jupyter echoes a returned value, so print and return appear to do the same
thing. The difference only surfaces the moment you try to store or reuse the
answer.

print is for humans. return is for the rest of your program.

Demo cue: run both versions side by side in the notebook, then multiply each
result by 1.0725. One works, one raises TypeError on None. Let them see the
error — they will meet it again in 6.9 and on their own homework tonight.

Every return hands back exactly ONE object. A tuple is one object wearing a
trench coat; we come back to that in 6.15.
-->

# 6.3–6.4 Why bother

<!--
Short block, maybe 6 minutes. This is the "so what" section and it is mostly
talking, not code.
-->

---

## The same function, two different types

```python
# Lets hand the same function two kinds of input
def combine(x, y):
    return x + y

combine(2, 3)          # 5
combine('Q', '3')      # 'Q3'
```

Python never checks a parameter's type up front — that is what makes this work.

<!--
Two names for one idea. Dynamic typing is the mechanism: Python binds a type
to the value, not to the parameter, and checks nothing until the operation
actually runs. Polymorphism is the payoff: one function, many types.

Ask before revealing the second result: what does combine of quote-Q and
quote-3 give us? Half the room will say five. That misconception is worth
surfacing now.

The cost side is real too — nothing stops you passing a string where you
meant a number, and the error appears deep inside the function rather than at
the call. That is the tradeoff for the flexibility.

Close 6.4 verbally rather than with a slide — three reasons, ranked by when
they will feel each one. Reuse: write it once, call it anywhere, and that is
what bites them this semester. Readability: calc_commission(sales) says what
the line does, and that is what their teammate feels. Modularity: one person
writes it, everyone else calls it, and that is what their employer feels.

The framing that lands for the third one — on a real team nobody reads the
body of a function they did not write. They read the name, the parameters,
and the docstring, then they call it. That is the entire social contract of
working in a shared codebase.

If the room is quiet, ask what happens when the sales tax rate changes and
the rate is pasted into forty places.
-->

# 6.5–6.7 Writing them

<!--
Now we build functions rather than talk about them. This block is best done
live in the notebook with the slides as a backstop.
-->

---

## A call is just a value

```python
# Lets drop calls straight into a bigger expression
def cube(n):
    return n ** 3

volume = cube(3) + cube(4)
print(cube(cube(2)))
```

Wherever a value can go, a call that returns one can go too.

<!--
This unlocks a lot. A call evaluates to whatever it returns, which means it
behaves exactly like a variable in an expression — it can be added, compared,
indexed, passed to another function, or nested inside itself.

They have been doing this since week two without noticing: int(input()) is a
call feeding another call.

Trace the nested one on the board rather than just reading it. cube of 2 is
8, then cube of 8 is 512. Inside out, always.
-->

---

## Sketch the shape before it works

```python
# Lets stub it out so the program still runs
def forecast(sales):
    pass

def commission(sales):
    return 0.0
```

A stub is a promise: right name, right parameters, honest placeholder body.

<!--
This is a professional habit, not a beginner crutch, and it is worth saying
that explicitly.

You design the whole program as a set of named, empty functions, confirm the
shape makes sense, and then fill them in one at a time with everything else
still running. The alternative — writing one giant function top to bottom and
running it for the first time at the end — is how you get a hundred errors at
once with no idea which is the real one.

pass is the placeholder that keeps the def line valid. Returning a fake value
like 0.0 is often better, because the calling code can keep working.

Tell them to stub their homework before writing it. Some will; those are the
ones who finish.
-->

---

## Branches and loops, one level deeper

```python
# Lets pick a fee tier inside a function
def fee(price):
    if price < 100:
        return 5.00
    elif price < 500:
        return 12.00
    return 25.00
```

Nothing new here — the same rules, just indented inside a `def`.

<!--
Deliberately anticlimactic, and say so. Everything they learned about if and
for in the last two chapters works identically inside a function body. The
only change is one more level of indentation.

The one genuinely new idea is the early return: the first return that runs
ends the function immediately, so no else is needed after a return. Point at
the elif and ask why there is no final else. That is a real insight, not
syntax trivia.

If time allows, contrast with the version that assigns to a result variable
and returns once at the bottom. Both are fine; know both exist.
-->

# 6.8–6.9 Objects and mistakes

<!--
Ten minutes. The second half of this block is the one that saves them
debugging hours, so protect it.
-->

---

## The name without `()` is the function itself

```python
# Lets pass a function into another function
def apply_to_all(func, values):
    for v in values:
        print(func(v))

apply_to_all(commission, [1000, 2000])
```

`commission` is the object. `commission()` is the act of running it.

<!--
Parentheses are the verb. Without them you are naming a thing; with them you
are doing something.

Because a function is an ordinary object, it can be assigned to a second
name, stored in a list or dict, and passed as an argument — which is exactly
what this slide does. That last one is the foundation for sorted(key=...),
map, and every callback they will ever write in pandas.

Demo cue: print commission with no parens and show the function object with
its memory address. Then bind bonus = commission and call bonus(1000). The
room usually finds this genuinely surprising.

Do not say "higher-order function" unless someone asks. The idea lands; the
jargon does not.
-->

---

## The bug you will actually write

```python
# Lets forget the return and watch it fail later
def total(a, b):
    a + b

print(total(2, 3) * 2)
```

Output: `TypeError: unsupported operand type(s) for *: 'NoneType' and 'int'`

<!--
This is the single most common function bug, and the cruelty of it is that
the function is not where it fails. The def runs fine, the call runs fine,
and the error lands on a completely different line — wherever that None
finally gets used in arithmetic.

Teach the reading habit, not the fix: when you see NoneType in an error
message, stop looking at the line in the error and go find the function that
produced that value. Nine times out of ten it is missing a return.

Other classics worth naming out loud but not sliding: calling a function
before defining it, and calling with the wrong number of arguments. Both fail
loudly and immediately, which makes them far kinder than this one.

Ask the room to spot the missing word before you reveal the output.
-->

# 6.10–6.12 Scope and arguments

<!--
The conceptually hardest block in the chapter. Slow down. If you are running
short, cut the global keyword slide rather than rushing all three.
-->

---

## What happens inside, stays inside

```python
# Lets try to read a local variable from outside
def demo():
    subtotal = 99

demo()
print(subtotal)     # NameError
```

Each call gets a fresh, private namespace that is thrown away when it returns.

<!--
Frame it as a feature, not a restriction. Local scope is what lets you use
the name total in fifty different functions without any of them colliding.
Without it, every variable in a large program would have to be uniquely
named, which is unworkable.

A function CAN read a global variable — if the name is not found locally,
Python looks outward. That is why a top-level TAX_RATE is visible inside.

Demo cue: define the same variable name inside two different functions with
different values, print from each, and show they never interfere.

Vocabulary to say once and move on: namespace, local scope, global scope.
-->

---

## Assigning makes a new local

```python
# Lets accidentally shadow a global
rate = 0.05

def bump():
    rate = 0.10      # brand new local, global untouched

bump()
print(rate)          # still 0.05
```

`global rate` overrides this — and is almost always the wrong tool.

<!--
The rule Python actually follows: assigning to a name anywhere in a function
body makes that name local for the ENTIRE body, even on lines above the
assignment. That is why you can get an UnboundLocalError reading a variable
you thought was global.

The global keyword works and you should show it once, so they recognize it in
someone else's code. Then tell them plainly not to reach for it. A function
that quietly reaches out and rewrites module state is a function nobody can
call safely, test, or reason about.

The alternative is always the same and always better: take it as a parameter,
return the new value, let the caller decide what to do with it.
-->

---

## Passing a list is different

```python
# Lets rebind one parameter and mutate another
def reset(n):
    n = 0                   # rebinds a local -- caller never sees it

def add(cart):
    cart.append('mouse')    # mutates the object -- caller sees it
```

Rebinding a name is private. Mutating an object is not.

<!--
This is the subtlest idea in the chapter and it catches professionals, so
give it room.

Python passes the object, not a copy and not the variable. Rebinding a
parameter — the left-hand side of an assignment — only changes what that
local name points at, and the caller never sees it. Mutating the object the
parameter points at changes the one and only object, which the caller
absolutely does see.

So the question is never "is it passed by value or reference". The question
is: did the function REBIND the name, or MUTATE the object?

Immutable types — int, float, str, tuple — cannot be mutated, so they can
only ever behave like the left column. Lists, dicts and sets can do both.

Safe default habit for them: build and return a new list rather than
modifying the one you were handed. Surprise mutation is a nasty bug to chase
through someone else's code.
-->

# 6.13–6.14 Flexible arguments

<!--
This block is mostly mechanical and students enjoy it. Keep it moving, about
10 minutes, and spend the time you save on the scope block above.
-->

---

## Defaults make a parameter optional

```python
# Lets make the rate optional
def commission(sales, rate=0.05):
    return sales * rate

commission(1000)          # 50.0
commission(1000, 0.08)    # 80.0
```

Parameters with defaults must come **last** in the `def` line.

<!--
A default turns a required input into an optional one with a sensible
fallback. The house commission rate is 5 percent; say nothing and you get it.

The ordering rule is not arbitrary — Python fills positional arguments left
to right, so a parameter without a default sitting after one with a default
could never be reached. Python raises a SyntaxError at definition time rather
than letting you write it.

Advanced trap worth one sentence: never use a mutable default like an empty
list. It is created once at definition and shared by every call. Tell them it
exists, tell them to use None instead, do not go down the rabbit hole today.
-->

---

## Naming the argument at the call

```python
# Lets call the same function three legal ways
commission(1000, 0.08)
commission(sales=1000, rate=0.08)
commission(rate=0.08, sales=1000)
```

Keyword arguments can be reordered. Positional ones must come first.

<!--
The real argument for keyword arguments is readability at the call site.
Compare invoice(1000, 0.08, True, False) with invoice(sales=1000, rate=0.08,
rush=True, taxable=False). Six months later, only one of those is readable —
and you are the person reading it.

The other everyday use is skipping over a middle default: if a function takes
qty, price, tax and you only want to override tax, you name it and leave the
rest alone.

One rule to remember: every positional argument comes before every keyword
argument. Violate it and Python raises SyntaxError immediately.
-->

---

## `*args` — any number of values

```python
# Lets accept however many numbers we are given
def total(*args):
    return sum(args)

total(10)                    # 10
total(10, 20, 30, 40)        # 100
```

The `*` gathers every leftover positional argument into a **tuple**.

<!--
The star does the work; args is only a convention. You could name it
star-numbers and it would behave identically, but do not — everyone expects
args and deviating just confuses your reader.

Key insight to state plainly: inside the function, args is an ordinary tuple.
There is nothing exotic about it. Loop over it, len it, index it, sum it.

Zero arguments is legal and gives you an empty tuple, which is why total()
returns 0 rather than erroring.

They have already used this without knowing: print() takes any number of
values the exact same way.
-->

---

## `**kwargs` — any number of named values

```python
# Lets accept however many named values we are given
def profile(**kwargs):
    for key, value in kwargs.items():
        print(f'{key}: {value}')

profile(name='Ravi', region='West')
```

Two stars gather leftover *keyword* arguments into a **dictionary**.

<!--
One star gives you a tuple of values. Two stars give you a dict of names and
values. That is the entire difference, and framing it as a pair is what makes
both stick.

The order in a def line is fixed and Python enforces it: required, then
defaults, then *args, then **kwargs. Write it on the board. They will meet a
signature like this constantly in pandas and matplotlib, where **kwargs is
how a library accepts dozens of optional styling options without listing them
all.

That is the honest answer to "when would I ever write this myself" — maybe
rarely, but you will READ it every week for the rest of your career.
-->

# 6.15–6.17 Outputs, docs, and a real one

<!--
Closing block. End on the worked example so the last thing they see is a

-->

---

## Returning more than one value

```python
# Lets hand back three numbers at once
def stats(values):
    return min(values), max(values), sum(values) / len(values)

low, high, avg = stats([10, 20, 30])
```

Commas build a tuple, and unpacking takes it apart on the other side.

<!--
This closes the loop on the promise from the first block: every return hands
back exactly one object, and a tuple is one object carrying several values.
Python just lets you skip the parentheses.

Show both sides deliberately. Without unpacking you get a tuple and index it
with square brackets, which is legal but unreadable. With unpacking you get
three well-named variables on one line, which is what you actually want.

The count has to match or you get a ValueError. If you only need one of them,
underscore is the conventional name for "ignore this".

Alternative worth one sentence: when there are more than three values, or
they are not obviously ordered, return a dictionary instead so the caller
reads by name.
-->

---

## Leave a note the tools can read

```python
# Lets document what the function promises
def commission(sales, rate=0.05):
    """Return commission owed on a sales amount."""
    return sales * rate

help(commission)
```

A string on the first line of the body is a docstring, not a comment.

<!--
The distinction that matters: a hash comment is stripped and gone, while a
docstring is stored on the function object and can be read back at runtime by
help(), by shift-tab in Jupyter, and by every documentation tool.

Demo cue: this is the moment to show that shift-tab inside the parentheses of
any function pops the docstring. Then do it on a pandas function. Half of
them will start doing it for the rest of the semester, which is the real win
of this slide.

Content convention: one line saying what it RETURNS, phrased as an
instruction — "Return commission owed", not "This function calculates". Longer
ones add parameter descriptions below a blank line.

Their homework functions should have these from now on.
-->

---

## The whole chapter, doing one job

```python
# Lets price an order with everything we learned
def price(customer, *items, tax=0.0725, **opts):
    """Return the customer and the taxed total."""
    subtotal = sum(q * p for q, p in items)
    if opts.get('rush'):
        subtotal += 25
    return customer, subtotal * (1 + tax)
```

<!--
Do not read this line by line. Name the pieces and let them see it assemble:
a required parameter, *args for the line items, a keyword default for tax,
**kwargs for the extras, a docstring, and a tuple return.

Then call it live two ways — the minimal call with one item, and the maximal
call with several items plus rush=True — and show the same function handling
both without changing a line.

The point to land: this is not showing off. Every one of those pieces solves
a specific problem we named today, and a function like this is completely
ordinary in real code. They will read signatures exactly this shape in every
library they touch.

If the room is fried by now, skip the second call and go straight to
questions. Better to end early and clean.
-->

---

## Four things to take with you

- `print` is for humans, `return` is for your program
- Every `return` hands back exactly one object
- Assigning inside a function makes a local — mutating a list does not
- Name the argument at the call when the value is not self-explanatory

<!--
Read these out loud and let them write them down. Say plainly that the first
